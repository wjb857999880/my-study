## 2. 多线程与并发

### 题目1：[正确使用判断题] 以下代码是否安全？若不安全请指出问题。
```kotlin
var counter = 0
Thread { counter++ }.start()
Thread { counter++ }.start()
println(counter) // 可能输出 0、1 或 2
```
- A. 安全，因为 counter++ 是原子操作
- B. 不安全，counter++ 读取-修改-写入三步不是原子的，多线程竞态导致结果不确定
- C. 安全，Kotlin 默认线程安全
- D. 安全，只要用 val 而非 var 即可

### 题目2：[常见坑识别题] 以下哪种用法最容易导致死锁？
- A. 在主线程获取锁后，在子线程中释放
- B. 在同一线程中嵌套获取两把相同的 ReentrantLock
- C. 使用 CopyOnWriteArrayList 读写并发
- D. 使用 @Synchronized 注解修饰 suspend 函数

---
**答案要点**
1. B — `counter++` 包含读(LOAD)、增(INC)、写(STORE)三步，多线程并发时会发生竞态，结果不确定。
2. A — 锁的获取和释放在不同线程，且顺序错误（主线程获锁后异常，子线程永远阻塞），是经典死锁模式；B 中 ReentrantLock 可重入不会死锁；C 为线程安全列表；D 的 @Synchronized 不适用于协程场景但不会直接死锁。

## 3. Jetpack Compose

### 题目1：[用途认知题] Jetpack Compose 相比传统 View 系统最核心的改进是什么？
- A. 支持 XML 布局，便于设计师协作
- B. 通过声明式 UI 消除 imperative 状态同步问题，自动最优更新
- C. 完全兼容 View 系统，可以无缝迁移
- D. 提供运行时视图检查工具

### 题目2：[常见坑识别题] 以下 Compose 代码哪个最可能导致 recomposition 性能问题？
- A. 在 `LaunchedEffect` 中调用 `delay()` 延时任务
- B. 在 `remember` 中缓存不变的大型数据结构
- C. 在 Composable 函数内部直接创建 `mutableStateOf`，每次 recomposition 都会重新创建状态
- D. 使用 `derivedStateOf` 转换派生状态

---
**答案要点**
1. B — Compose 的核心价值在于声明式：开发者描述 UI 状态，框架自动计算最小更新集，避免 imperative 代码中手动同步状态的繁琐与遗漏。
2. C — 在 Composable 体内创建 `mutableStateOf` 会导致每次 recomposition 都生成新状态引用，破坏稳定性，引发无限 recomposition 或性能退化；应提升到函数参数或用 `remember` 包裹。

## 4. Room 数据库

### 题目1：[正确使用判断题] 以下 DAO 定义是否正确？
```kotlin
@Dao
interface UserDao {
    @Query("SELECT * FROM user WHERE id = :id")
    suspend fun getUserById(id: Long): User
}
```
- A. 错误，Room 不支持 suspend 函数
- B. 错误，Query 方法不能是 suspend 的
- C. 正确，Room 2.1+ 支持 suspend DAO 方法
- D. 正确，但需要在数据库构建时传入 CoroutineScope

### 题目2：[常见坑识别题] 迁移 Room 数据库时，以下哪种方式最容易导致用户数据丢失？
- A. 使用 `addMigrations` 提供渐进式迁移脚本
- B. 使用 `fallbackToDestructiveMigration()` 暴力重建数据库
- C. 在 `Migration` 中 `ALTER TABLE` 添加新列并提供默认值
- D. 使用 `AutoMigrations` 自动计算迁移

---
**答案要点**
1. C — Room 2.1 起支持 suspend 函数，DAO 方法可以是 suspend 的，配合协程调用；不需要手动传 Scope。
2. B — `fallbackToDestructiveMigration()` 会直接删除旧数据库再创建，所有用户数据均丢失；A 和 C 在正确编写迁移脚本情况下可保留数据；D 在简单变更时可接受，复杂场景需人工审查。

## 6. Hilt 依赖注入

### 题目1：[正确使用判断题] 以下 Module 定义是否正确？
```kotlin
@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    @Provides
    fun provideOkHttp(): OkHttpClient = OkHttpClient.Builder().build()
}
```
- A. 错误，`@Provides` 方法不能是 `fun`，必须是属性
- B. 正确，Hilt 支持 object Module 提供单例实例
- C. 错误，必须用 `@Binds` 替代 `@Provides`
- D. 错误，`@InstallIn` 参数大小写错误

### 题目2：[常见坑识别题] 以下哪种注入方式最容易导致内存泄漏？
- A. 在 `@AndroidEntryPoint` 的 Activity 中通过 `lateinit var` 注入 ViewModel
- B. 在 Fragment 中持有 `@Inject` 注入的长生命周期对象（Application Scope）
- C. 在 ViewModel 中 `@Inject constructor` 注入 Repository，ViewModel 自动受 Lifecycle 管辖
- D. 在 Application 中使用 `@EntryPoint` 手动获取短生命周期对象

---
**答案要点**
1. B — Hilt 支持 object Module + `@Provides` 提供单例（`@InstallIn(SingletonComponent::class)`）；单例在整个应用生命周期内有效。
2. B — Fragment 持有长生命周期对象会导致该对象无法被 GC 回收（Fragment 销毁但对象仍被引用），典型内存泄漏；A 中 `lateinit var` 在 Activity 销毁时随 Lifecycle 释放；C 由 Hilt 管理生命周期，正确；D 是临时获取，用完即释放。

## 7. WorkManager 后台任务

### 题目1：[用途认知题] WorkManager 相比 Thread 或 Handler 最核心的优势是什么？
- A. 更快，因为直接操作线程
- B. 不支持长时间运行任务
- C. 保证任务执行即使应用退出或设备重启，且遵循省电约束
- D. 自动管理网络请求

### 题目2：[常见坑识别题] 以下哪种约束条件组合最容易导致 WorkManager 任务"永久等待"？
- A. `setRequiredNetworkType(NetworkType.CONNECTED)` + 设备始终联网

## 8. RecyclerView 自定义组件

### 题目1：[正确使用判断题] 以下 ItemDecoration 实现是否存在问题？
```kotlin
class MyDecoration : RecyclerView.ItemDecoration() {
    override fun onDraw(c: Canvas, parent: RecyclerView, state: RecyclerView.State) {
        // 绘制分割线
    }
}
```
- A. 正确，`onDraw` 在 item view 之下绘制
- B. 错误，应重写 `onDrawOver` 而非 `onDraw`
- C. 错误，`onDraw` 签名应为 `onDraw(c: Canvas, parent: RecyclerView, state: RecyclerView.State)`
- D. 正确，但 Android 10+ 需要关闭硬件加速

### 题目2：[常见坑识别题] 自定义 LayoutManager 时，以下哪种做法最容易导致 RecyclerView 滚动卡顿？
- A. 在 `onLayoutChildren` 中正确调用 `detachAndScrapAttachedViews`
- B. 在 `scrollHorizontallyBy` 中对每个可见 item 调用 `measure` 和 `layout`
- C. 使用 `setHasFixedSize(true)` 优化
- D. 实现 `getExtraLayoutSpace` 返回合理值

---
**答案要点**
1. A — `onDraw` 在 item view 层级之下绘制（先于 item），适合背景分割线；`onDrawOver` 在 item 之上绘制；签名本身正确。
2. B — 每次滚动时对所有可见 item 重新 measure/layout 是性能杀手，应缓存尺寸并在 `measure`/`layout` 时复用；A、C、D 均为合理优化手段。

## 9. 动画与转场

### 题目1：[用途认知题] Android 动画体系中，Property Animation 与 View Animation 的核心区别是什么？
- A. View Animation 更快，因为不使用 CPU
- B. Property Animation 可以对任意对象（不只是 View）的任意属性做动画，且支持非线性插值
- C. Property Animation 只支持 View 的属性
- D. View Animation 支持 3D 旋转，Property Animation 不支持

### 题目2：[正确使用判断题] 以下 SharedElementTransition 代码是否正确？
```kotlin
val extras = FragmentNavigatorExtras(view to "shared_element")
navController.navigate(
    R.id.detail,
    bundleOf("id" to itemId),
    null,
    extras
)
```
- A. 正确，SharedElementTransition 通过 FragmentNavigatorExtras 传递
- B. 错误，SharedElementTransition 需要在 NavGraph 中显式声明 `<sharedElement>`
- C. 错误，第四个参数应为 `FragmentNavigatorExtras`
- D. 错误，只能用 `ActivityOptions` 而不能用 FragmentNavigatorExtras

---
**答案要点**
1. B — View Animation 仅支持 View 的限定属性（translate/alpha/scale/rotate），且改变的是绘制属性而非实际属性；Property Animation（ObjectAnimator/ValueAnimator）可对任何对象的任何属性做动画，支持自定义插值器，且动画结束后可选择保持最终状态。
2. B — SharedElementTransition 需要在 NavGraph 的 `<fragment>` 中声明 `<sharedElement>` 标签并指定 transitionName，代码中通过 FragmentNavigatorExtras 传递仅是第二步；A 忽略了 NavGraph 声明步骤。

- B. 使用 ConstraintLayout 配合 match_constraints (0dp) 百分比宽度

## 11. 混合开发与 WebView

### 题目1：[常见坑识别题] 以下哪种做法最容易导致 Hybrid 应用的安全漏洞？
- A. `WebView.setJavaScriptEnabled(false)` 禁用 JS
- B. `WebView.addJavascriptInterface` 暴露 Java 对象给 JS，且不限制可调用方法
- C. 使用 `shouldInterceptRequest` 过滤非 HTTPS 请求
- D. 启用 `WebView.setDatabaseEnabled(false)`

### 题目2：[用途认知题] JsBridge（H5 与 Native 通信的常见实现方式）主要解决什么问题？
- A. 加速 WebView 页面加载
- B. 让 JavaScript 可以调用 Native 功能（拨打电话、扫码、支付等），同时 Native 可以回调 JS
- C. 替代 WebView 直接渲染原生组件

---

## 12. NDK 与 JNI 开发

### 题目1：[正确使用判断题] 以下 JNI 代码是否正确？
```c
extern "C" JNIEXPORT jstring JNICALL
Java_com_example_MainActivity_getString(JNIEnv* env, jobject this) {
    return env->NewStringUTF("Hello");
}
```
- A. 正确
- B. 错误，`this` 参数应为 `jclass` 因为这是静态方法
- C. 错误，应返回 `jstring` 而非 `jobject`
- D. 错误，`JNIEXPORT` 应该写在返回类型之前

### 题目2：[常见坑识别题] 以下哪种做法最容易导致 JNI 层内存泄漏？
- A. 使用 `NewStringUTF` 创建 Java 字符串后立即返回
- B. 在 JNI 中调用 Java 方法时，将 local reference 存入全局变量（如 `static jobject`）
- C. 使用 `DeleteLocalRef` 主动释放不再使用的 local reference
- D. 在 `JNI_OnUnload` 中正确释放所有全局引用

---
**答案要点**
1. B — 实例方法签名中第二个参数是 `jobject`（代表 this），但静态方法中是 `jclass`；该代码若在实例方法中正确，在静态方法中则为 `jclass this`（参数名不匹配但编译器通过，运行时行为取决于调用方式）；严格来说应明确参数类型而非参数名。
2. B — Local reference 在方法返回后自动释放，但若存入 `static jobject` 全局变量则生命周期被延长，若不手动 `DeleteGlobalRef` 则导致 GC 无法回收，造成内存泄漏。

## 13. AOP 与字节码插桩

### 题目1：[用途认知题] AOP（面向切面编程）在 Android 中的主要应用场景是什么？
- A. 替代 Kotlin 协程处理异步
- B. 在编译期或加载期无侵入地插入日志、埋点、权限检查等横切逻辑
- C. 提高应用运行时的帧率
- D. 替代 RecyclerView 的缓存机制

### 题目2：[常见坑识别题] 使用 AspectJ 进行字节码插桩时，以下哪种情况最容易导致编译失败或运行时异常？
- A. 对 `private` 方法添加切面
- B. 对 `final` 类添加切面
- C. 切点表达式匹配到过多类和方法，导致 transform 阶段超时
- D. 在切面中使用 `withincode` 限定符

---
**答案要点**
1. B — AOP 的核心价值是将散落在各处的"横切关注点"（日志、埋点、权限、事务）集中管理，通过代理/字节码方式无侵入地织入，避免业务代码与横切逻辑耦合。
2. A — AspectJ 无法对 `private` 方法进行切面（因为 private 方法不可被子类继承访问，切面需要通过继承或代理实现），强制匹配会导致编译警告或织入失败；B 中 `final` 类若被 `within(FinalClass)` 匹配也会失败；C 是性能问题而非编译失败主因。

## 15. Gradle 构建配置

### 题目1：[正确使用判断题] 以下 build.gradle 配置是否存在问题？
```groovy
android {
    compileSdk 33
    defaultConfig {
        minSdk 21
        targetSdk 33
    }
}
dependencies {
    implementation 'androidx.core:core-ktx:1.9.0'
}
```
- A. 正确
- B. 错误，`compileSdk` 应低于 `targetSdk`
- C. 错误，`implementation` 应改为 `api`
- D. 错误，`minSdk` 不能低于 21

### 题目2：[常见坑识别题] 以下哪种 Gradle 同步方式最容易导致本地缓存污染？
- A. 使用 `gradle sync` 刷新依赖
- B. 删除 `.gradle` 目录后重新同步
- C. 依赖版本使用动态版本（如 `2.+`）且项目长期不清理缓存
- D. 使用 `gradlew --refresh-dependencies` 强制刷新

---

1. A — `withContext` 用于切换协程上下文（此处切到 IO 线程执行），是标准挂起函数用法；lambda 不需要是 suspend 的，`withContext` 本身就是 suspend 函数会等待内部执行完成。
2. B — `GlobalScope` 的生命周期与应用一致，不受 Activity/Fragment 生命周期管理，在其中启动的协程不会随 UI 销毁而取消，会导致协程持有的引用无法释放；应使用 `lifecycleScope`/`viewModelScope`（自动绑定 Lifecycle）。

## 30. RecyclerView 四级缓存

- B. Scrap 用于屏幕内不可见但可复用的 ViewHolder；Cache 用于即将可见的短期缓存；ViewCacheExtension 用于开发者自定义；Pool 用于不可见 ViewHolder 的复用池
- C. 四级缓存的作用完全相同，只是容量不同

## 32. 自定义 View 与绘制流程

### 题目1：[用途认知题] View 绘制流程（measure/layout/draw）中，measure 和 layout 的核心职责分别是什么？
- A. measure 确定大小，layout 确定位置
- B. measure 确定位置，layout 确定大小
- C. measure 和 layout 职责相同
- D. measure 只在 ViewGroup 中调用，layout 只在 View 中调用

### 题目2：[正确使用判断题] 以下自定义 View 实现是否正确？
```kotlin
class MyView @JvmOverloads constructor(
    context: Context,
    attrs: AttributeSet? = null,
    defStyleAttr: Int = 0
) : View(context, attrs, defStyleAttr) {

    override fun onMeasure(widthMeasureSpec: Int, heightMeasureSpec: Int) {
        setMeasuredDimension(200, 200) // 固定 200x200
    }
}
```
- A. 正确，固定尺寸的 View 应该重写 onMeasure
- B. 错误，`setMeasuredDimension` 应使用 `resolveSize` 处理 MeasureSpec
- C. 错误，不需要重写 onMeasure

2. D — 该实现硬编码 200dp，忽略了 parent 传入的 MeasureSpec，`match_parent` 会失效（始终 200dp）；正确做法应调用 `resolveSize(200, widthMeasureSpec)` 结合 spec 模式处理。

## 33. 事件分发机制

### 题目1：[用途认知题] ViewGroup 的 `dispatchTouchEvent` 与 `onInterceptTouchEvent` 在事件分发流程中各自的作用是什么？
- A. `dispatchTouchEvent` 负责拦截事件，`onInterceptTouchEvent` 负责分发事件
- B. `dispatchTouchEvent` 负责分发事件，`onInterceptTouchEvent` 在 `dispatchTouchEvent` 内部调用，决定是否拦截子 View
- C. 两者作用完全相同
- D. `onInterceptTouchEvent` 负责最终消费事件

### 题目2：[常见坑识别题] 以下哪种场景最容易导致子 View 无法接收到 touch 事件？
- A. 父 ViewGroup 重写 `onInterceptTouchEvent` 并在 `ACTION_DOWN` 时返回 `true`（拦截）
- B. 子 View 使用 `requestDisallowInterceptTouchEvent(true)` 禁止父 View 拦截
- C. 父 ViewGroup 未重写任何分发方法
- D. 子 View 处理了 `ACTION_DOWN`

---
**答案要点**
1. B — `dispatchTouchEvent` 是事件入口，负责调用 `onInterceptTouchEvent` 询问是否拦截，以及将事件分发给子 View/自己处理；`onInterceptTouchEvent` 是拦截询问方法，默认返回 false（不拦截）。
2. A — 一旦父 View 在 `ACTION_DOWN` 时拦截（返回 true），子 View 将永远不会收到 `ACTION_DOWN`（没有 down 就没有后续 move/up），即子 View 无法接收任何 touch 事件；B 是子 View 的保护机制；C/D 不会导致此问题。

## 34. MVVM

### 题目1：[用途认知题] MVVM 架构中，ViewModel 与 View（Activity/Fragment）的最佳交互方式是什么？
- A. View 直接持有 ViewModel 引用，通过 LiveData/StateFlow 观察状态，不直接操作 ViewModel 的业务方法
- B. View 直接调用 ViewModel 的所有 public 方法修改状态
- C. ViewModel 处理所有 UI 逻辑，包括动画和页面跳转
- D. View 持有 ViewModel 并在 `onDestroy` 中手动清空

### 题目2：[正确使用判断题] 以下代码是否正确体现了 MVVM 原则？
```kotlin
class MyViewModel : ViewModel() {
    val liveData = MutableLiveData<String>()

    fun loadData() {
        viewModelScope.launch {
            val data = repository.fetchData()
            liveData.value = data
        }
    }
}
```

## 36. MVI 与 Clean Architecture

### 题目1：[用途认知题] MVI（Model-View-Intent）与 MVVM 在数据流方向上的核心区别是什么？
- A. MVVM 是单向数据流，MVI 是双向
- B. MVI 是单向数据流（Intent → Model → View），状态不可变，View 完全由状态驱动；MVVM 中 ViewModel 可以直接修改 View
- C. MVI 和 MVVM 完全相同
- D. MVI 不需要 Intent

### 题目2：[正确使用判断题] Clean Architecture 中的 UseCase（Interactor）层应该处理哪种逻辑？
- A. 数据库的直接 CRUD 操作

- C. UI 布局逻辑

## 37. OkHttp 拦截器

### 题目1：[用途认知题] OkHttp 拦截器链中，`addInterceptor` 与 `addNetworkInterceptor` 的核心区别是什么？
- A. 两者完全相同
- B. `addInterceptor` 在请求发出前/响应返回后（全局）执行，`addNetworkInterceptor` 仅在网络连接建立时执行（重定向、缓存响应等）
- C. `addNetworkInterceptor` 比 `addInterceptor` 先执行
- D. `addInterceptor` 只能添加一个

### 题目2：[常见坑识别题] 以下哪种自定义拦截器实现最容易导致无限重试或性能问题？
- A. 在拦截器中正确打印请求和响应日志
- B. 在拦截器中根据响应状态码进行有限次重试（使用同步循环）
- C. 在拦截器中发起新的网络请求（嵌套网络调用）并同步等待
- D. 在拦截器中使用 `chain.request()` 获取原始请求

**答案要点**
1. B — `addInterceptor`：Application 拦截器，在整个请求生命周期（从发起到收到最终响应，包括重定向）中最先调用，常用于日志/统一 header；`addNetworkInterceptor`：Network 拦截器，在与服务器建立网络连接后调用（仅在真正有网络交互时），用于处理连接层事件（重定向/证书切换/透明压缩）。
2. C — 在拦截器中发起新的同步嵌套网络请求可能导致死锁、无限循环或重试风暴；B 的有限次重试配合退避策略是合理用法；A/D 是标准拦截器用法。

## 38. 图片加载架构

### 题目1：[用途认知题] 图片加载框架（如 Glide / Coil / Picasso）相比直接使用 `ImageView.setImageResource` 的核心优势是什么？
- A. 支持更多图片格式
- B. 提供加载生命周期管理（避免 Activity/Fragment 销毁后回调）、内存与磁盘缓存、请求优先级与取消、图片变换与占位图
- C. 运行速度更快
- D. 完全不需要网络请求

### 题目2：[常见坑识别题] 以下哪种图片加载用法最容易导致 OOM（内存溢出）？
- A. 使用 `Glide.with(context).load(url).into(imageView)` 加载网络图片
- B. 在 RecyclerView 的 ViewHolder 中直接加载原图（1920x1080）到 48dp 的 ImageView

## 答案要点汇总

### 题目类型说明
- **用途认知题**：考察对工具/框架解决的问题域是否理解准确
- **正确使用判断题**：考察 API 使用方式是否规范，是否触碰常见用法禁区
- **常见坑识别题**：考察对踩坑场景的预判能力

### 核心知识点速记
1. Kotlin-Java 互操作：渐进迁移 vs 重写
2. 多线程：`counter++` 非原子，`synchronized` / `AtomicInteger` 解决
3. Compose：声明式消除状态同步，Composable 内避免创建 `mutableStateOf`
4. Room：`fallbackToDestructiveMigration()` 会清空数据；suspend DAO 正确
5. Navigation：必须有 `startDestination`；SharedElement 需 NavGraph 声明
6. Hilt：`@InstallIn(SingletonComponent::class)` 提供单例；长生命周期对象注入短生命周期对象导致泄漏
7. WorkManager：约束永不满足时任务永远不执行
8. RecyclerView：`onBindViewHolder` 不代表真正可见；滚动时重 measure/layout 卡顿
9. 动画：Property Animation 可对任意属性动画，View Animation 仅改变绘制属性
10. 屏幕适配：动态窗口尺寸监听 vs 折叠屏场景
11. WebView：`addJavascriptInterface` 不限制方法 = RCE 漏洞
12. JNI：`static jobject` 全局引用不释放 = 泄漏
13. AOP：无法切 `private` 方法
14. CI/CD：未签名 APK 不可发布
15. Gradle：动态版本 `2.+` 导致缓存污染
16. 自动化测试：断言与代码"同源"的假测试无意义
17. AI 辅助：生成代码必须人工 review
18. 数据存储：Token 用 EncryptedSP；万级数据用 Room；敏感数据加密
19. 移动安全：Java 层代码无防反编译保护
20. 流式架构：Flow/StateFlow 实现响应式数据流
21. 数据埋点：`onBindViewHolder` ≠ 真正曝光
22. KMP：共享业务逻辑 + 平台原生 UI
23. Flutter：自研 Skia 引擎绘制 vs RN 调用原生控件
24. 鸿蒙：Stage 模型 + 多设备合一 HAP
25. 音视频：`ERROR_TRY_AGAIN_LATER` 表示编解码器忙，需重试
26. 端侧 AI：推理必须在后台线程
27. JVM vs ART：ART 安装时 AOT 编译 DEX，不走传统类加载
28. Flow：`catch` 捕获上游异常；`StateFlow` 需注意初始值生命周期
29. 协程：`GlobalScope` 不随 UI 销毁，取消需用 `lifecycleScope`
30. RecyclerView 四级缓存：结构性变化不通知导致重建
31. GapWorker：`setItemPrefetchEnabled(false)` 禁用预取
32. 自定义 View：`onMeasure` 需 `resolveSize` 处理 `match_parent`
33. 事件分发：`ACTION_DOWN` 被拦截则子 View 永不收到 touch 事件
34. MVVM：单向数据流，View 只观察不操作
35. 模块化：循环依赖（feature_a → feature_b → feature_a）编译失败
36. MVI：State 不可变单向驱动；UseCase 编排业务规则
37. OkHttp 拦截器：`addInterceptor` 全局，`addNetworkInterceptor` 仅网络层
38. 图片加载：`override(Target.SIZE_ORIGINAL)` 导致 OOM；加载到小 ImageView 应限制尺寸
