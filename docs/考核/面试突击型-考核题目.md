        for (int j = 0; j < nums.length; j++) {

**答案要点**

### 二叉树
1. **最大深度**：递归或 BFS 层序遍历。递归公式 `maxDepth(node) = 1 + max(maxDepth(left), maxDepth(right))`，空节点返回 0。时间 O(n)，空间 O(h)（递归栈）。
2. **BST 特性**：左子树所有节点 < 根节点 < 右子树所有节点；中序遍历有序。搜索/插入/删除：最好 O(log n)，最坏 O(n)（退化为链表）。
3. **序列化**：常用前序+中序，或层序（空节点用占位符标记）。关键是确定唯一重构条件（中序+前序/后序可唯一确定）。

### 哈希表
1. **两数之和**：遍历数组，用 HashMap 记录 `target - num` 与下标的映射，查找 O(1)，总 O(n)。
2. **哈希碰撞**：开放寻址法（线性探测、二次探测、双散列）、链地址法（Java HashMap 用此）、再哈希法。Java 8+ 对链表过长转为红黑树优化。
3. **LRU 缓存**：HashMap + 双向链表。HashMap 保证 O(1) 查找，链表维护顺序。get 时将节点移到尾部，put 时淘汰头部。

### 排序与二分查找
1. **二分查找**：经典模板，注意 `left <= right` 循环条件和中点更新逻辑，避免死循环。
2. **排序算法**：冒泡 O(n²)/O(n²)/O(1)，选择 O(n²)/O(n²)/O(1)，插入 O(n²)/O(n²)/O(1)（有序时 O(n)），归并 O(n log n)/O(n log n)/O(n)，快排 O(n log n)/O(n²)/O(log n)，堆排 O(n log n)/O(n log n)/O(1)。稳定排序：冒泡、插入、归并。
3. **旋转数组查找**：关键是判断 target 在左半还是右半。若 `nums[mid] > nums[left]`，左半有序；若 `target in [nums[left], nums[mid])`，搜左半；否则搜右半。

### 数组与字符串
1. **合并有序数组**：从后往前双指针，避免元素移动。时间 O(n+m)，空间 O(1)。
2. **String 系列**：String 不可变（final class，char[] 存在非堆区），线程安全；StringBuffer 线程安全但性能差（synchronized）；StringBuilder 非线程安全但性能好。字符串拼接编译器优化为 StringBuilder 操作。
3. **无重复字符最长子串**：滑动窗口+HashSet，右指针扩展，左指针收缩维护无重复窗口。时间 O(n)，空间 O(min(m, 字符集))。

### 栈与队列
1. **有效括号**：栈模拟，左括号入栈，右括号匹配栈顶。O(n) 时间，O(n) 空间。
2. **栈与队列应用**：栈用于函数调用栈、括号匹配、表达式求值、单调栈；队列用于 BFS、任务调度、消息队列、生产者消费者。栈 LIFO，队列 FIFO。
3. **两栈实现队列**：stackIn 和 stackOut。offer 时入 stackIn；poll/peek 时若 stackOut 为空则将 stackIn 全部倒入 stackOut，再从 stackOut 弹出/查看。均摊 O(1)。

### 链表
1. **反转链表**：迭代三指针 pre/cur/next；递归：head.next 反转后，将 head.next.next 指向 head。时间 O(n)，空间 O(n) 递归栈。
2. **链表 vs 数组**：链表内存离散、插入删除 O(1)（已知节点），但随机访问 O(n)；数组内存连续、随机访问 O(1)，插入删除 O(n)。ArrayList 随机访问多时优，LinkedList 插入删除多时优。
3. **环检测**：Floyd 快慢指针：slow 每次走1步，fast 走2步；相遇则有环。找入口：相遇后，将 slow 置回头节点，slow 和 fast 各走1步，再次相遇处为入口。数学证明：起点到入口距离 = n - 环内相遇点到入口距离。

### 动态规划
1. **爬楼梯**：dp[i] = dp[i-1] + dp[i-2]，可用滚动数组优化空间到 O(1)。斐波那契递推。
2. **DP 核心要素**：状态定义（dp[i] 表示什么）、转移方程（dp[i] = f(dp[j])）、初始化（dp[0] 等）、边界（遍历顺序）。与递归+记忆化同源，区别是自底向上 vs 自顶向下。
3. **LCS**：dp[i][j] 表示 text1[0..i) 和 text2[0..j) 的 LCS 长度。if text1[i-1]==text2[j-1]: dp[i][j]=dp[i-1][j-1]+1; else: dp[i][j]=max(dp[i-1][j], dp[i][j-1])。空间可用滚动数组优化。

### 回溯与贪心
1. **全排列**：回溯模板，`used` 数组标记，递归生成所有排列。`if (used[i]) return; used[i]=true; path.add(nums[i]); backtrack(); path.removeLast(); used[i]=false;`。
2. **回溯 vs 贪心**：回溯枚举所有可能，剪枝优化，适合组合/排列/搜索；贪心每步选局部最优，期望得到全局最优（如活动选择、哈夫曼编码）。不能用贪心时（如背包问题）需用回溯或 DP。
3. **分割回文串**：回溯，枚举每个子串起点，若为回文则继续递归；用 dp 预处理提前计算任意子串是否为回文以加速剪枝。

### 图 BFS 与 DFS
1. **岛屿数量**：遍历每个格子，若为 '1' 则 BFS/DFS 向四周沉没（置为 '0'），计数++。O(m*n)。
2. **BFS vs DFS**：BFS 用队列，层层扩展，适合最短路径、分层遍历；DFS 用栈/递归，适合连通性、拓扑排序、排列组合。BFS 空间 O(v)，DFS 空间 O(h)（递归栈深度）。BFS 找到的是最短路径（在无权图中）。
3. **课程表（环检测）**：建图，统计入度，用 BFS 拓扑排序。若最终处理节点数 < 总数，则有环。或者用 DFS 递归检测回边。

### Code Review 与代码质量
1. **Code Review 价值**：发现 bug、提升代码质量、知识共享、保证一致性、培养团队意识。维度：正确性、可读性、可维护性、性能、安全性、测试覆盖、架构设计、边界处理、命名规范、异常处理。
2. **低效代码问题**：暴力双重循环 O(n²)，应使用 Boyer-Moore 投票法 O(n)。该算法核心：维护 candidate 和 count，遍历时相消，最后验证。
3. **CR 规范**：流程（PR 描述规范、至少1人 Approve、CI 通过才能合入）、工具（GitHub PR/GitLab MR、静态分析）、评价标准（问题分级：must/should/could/wontfix）、常见问题处理（分歧升级、技术 Lead 仲裁）。

### 沟通协作与文档
1. **技术文档要素**：背景/目的、适用范围、接口/功能描述、数据格式、错误码、示例、版本历史。接口文档必须包含：请求/响应结构、字段说明、Content-Type、鉴权方式、调用限制。
2. **跨团队协作**：主动约会议对齐，明确依赖和接口；将问题升级给双方 TL；用书面形式（邮件/飞书）确认接口契约；预留 buffer 应对变更；定期同步进度。
3. **接手遗留项目**：快速止血（日志、监控、灰度）；读现有文档/代码；建立基础设施（单测、CI）；从小范围重构开始；与产品对齐优先级，逐步偿还技术债。

### 技术方案设计与评审
1. **TDR 流程**：方案预审（提前发出，reviewer 预读）→ 评审会议（背景、方案、权衡、开放问题）→ 纪要与 Action → 方案修订 → Tech Lead 批准。评审重点：架构合理性、风险与折中、边界情况、可扩展性、测试策略。
2. **网络层设计**：采用 Retrofit + OkHttp + Repository 模式；OkHttp 负责连接复用、拦截器（统一 Header、重试、日志）；Retrofit 定义接口；Repository 统一数据源（网络/本地缓存）；Mock 可用 MockWebServer 或接口开关。
3. **评审分歧处理**：先充分听取反对理由，用数据和场景支撑自己的判断；若确实是过度设计，坦然接受；组织小范围讨论对齐后再大评审；将非核心争议延后，聚焦核心决策。

### 面试与项目表达
1. **STAR 法则**：Situation（背景）、Task（任务）、Action（行动）、Result（结果）。示例：S 在用户增长压力下，T 需要提升分享功能转化率，A 我设计了裂变分享链路，优化了 App 唤起和落地页，R 最终分享率提升 40%。
2. **技术难点项目**：从业务背景→技术挑战→方案选型（对比多个方案）→落地难点→最终效果 5个方面展开，突出你的独立思考和攻坚能力。
3. **面试复盘**：维度：知识盲点（当场没答上来的）、表达方式（是否清晰有逻辑）、问题拆解（是否有效追问）、时间控制。改进：补充知识、模拟练习、录音复盘、找同学模拟面试。

### 项目排期与风险
1. **估点方法**：使用相对估算（Story Point）对比历史基准；影响准确性因素：需求清晰度、技术不确定性、依赖方响应、人员能力评估、变更频率。估算不准时：重新评估、拆解任务、上报风险、加班或砍需求。
2. **项目延期处理**：立即分析根因（技术难题？需求变更？资源不足？）；与 PM 对齐新排期；识别可并行任务争取时间；如影响上线，协调相关方（依赖方、测试、PM）同步信息；上线后复盘。
3. **风险识别**：需求蔓延风险（应对：需求冻结）、技术选型风险（应对：POC 验证）、人员流动风险（应对：知识文档化、结对编程）、第三方 SDK 不稳定（应对：封装隔离、备选方案）、兼容性问题（应对：机型覆盖矩阵、灰度发布）、线上故障风险（应对：监控告警、应急预案）。

### 带人与技术培养
1. **导师职责**：传道（思维方式）、授业（技术技能）、解惑（答疑支持）、以身作则。避免：事必躬亲（无成长）、只给评价不给方向、放任不管。
2. **低绩效辅导**：一对一以倾听为主，先共情；明确具体问题（不是"产出低"而是"PR 提交频率低/缺少单测/命名不规范"）；制定 30 天改进计划，包含明确目标和检查点；每周回顾；如仍无改善，引入 HR 和 TL 沟通。
3. **技术培养体系**：应届生→带教机制→独立完成功能模块；初中级→专项深耕（如性能优化、网络层设计）→独当一面；高级→架构设计、带团队→技术决策能力。评估方式：代码质量、方案设计、沟通协作、业务贡献。资源投入：内部分享、外部培训、Code Review 反馈、挑战性任务分配。

### 技术债与重构规划
1. **技术债分类**：按类型（代码债、架构债、测试债、文档债）、按来源（故意积累、疏忽导致、需求变更驱动）、按严重性（危机型、侵蚀型、战略型）。判断是否立即偿还：债息（维护成本）是否高于偿还成本；是否影响新功能开发；是否造成系统性风险。
2. **重构计划**：不破坏性重构（保持对外接口不变）；新增测试（先补单元测试）；分阶段推进（每次重构一个小模块）；新旧代码并行运行（Feature Toggle）；与产品协商重构窗口（不接新需求或减少需求）。
3. **重构风险控制**：测试覆盖（单元测试 80%+，关键路径覆盖）；灰度策略（先内部用户→ 5% → 20% → 50% → 全量）；回滚方案（开关一键切换、数据兼容性处理）；进度把控（每日 standup 同步，遇到阻塞立即升级）；监控告警（重构成败通过监控指标判定）。
