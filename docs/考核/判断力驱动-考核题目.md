## 答案要点

### 1. Binder 通信原理
1. **D** — Binder 只需 1 次拷贝（内存映射）、安全（Binder token 验证身份）、C/S 语义清晰；Socket 需要 2 次拷贝且无权限模型。
2. **正确** — Binder driver 运行于内核态，用户态通过 `/dev/binder` 的 ioctl 调用完成 IPC，mmap 实现零拷贝。
3. `Stub.onTransact` 根据 `code`（由 AIDL 编译时生成的 int 常量）匹配方法，分发到对应 `data.readString`/`data.readInt` 解析参数，再调用对应方法并将结果写入 `reply`。

### 2. Handler 消息机制
1. 每个线程有一个 `Looper` 持有 `MessageQueue`，线程通过 `Looper.loop()` 不断从 Queue 取消息；跨线程时，发送者通过 `Handler` 向目标线程的 Queue 写入 Message，实现线程间通信。
2. **有问题** — `post` 虽发送到主线程，但 `thread {}` 是工作线程，应使用 `runOnUiThread` 或让 Handler 绑定到主线程；当前写法虽然最终 Runnable 在主线程执行，但 `Thread.sleep(5000)` 在子线程，不会直接卡主线程，但要注意生命周期泄漏。
3. 使用 `epoll_wait`，通过 `pipe`/`eventfd` 唤醒；`nativeWake` 写入一个字节，`next()` 检测到即中断阻塞。

### 3. Android 四大组件与生命周期
1. A(onCreate) → B(onCreate) → A(onStop) → B(onStart) → B(onResume)；`onPause` 在 A 失去焦点时立即调用，`onStop` 在 A 完全不可见时调用。
2. **正确** — `startService` 多次只会增加引用计数，`stopService`/`stopSelf` 一次即可停止。
3. `ContentProvider.onCreate` 在 Application.onCreate 之前执行，因为 AMS 在启动进程后先创建 ContentProvider，Provider 初始化完成后才回调 Application.onCreate。

### 4. 启动优化
1. AMS 需要在应用进程启动后立即可用（AMS 依赖 Provider 报告已就绪），ContentProvider 的引用链更早，所以 onCreate 更先执行。
2. **D** — App Startup 可统一管理初始化顺序和懒加载，是当前最优实践；A/B/C 都有副作用（懒加载可能影响功能、异步初始化有依赖顺序问题）。
3. `AMS.startProcess` 在 `Process.start` 时 fork 新进程；zygote 预加载系统类和资源，减少每个子进程初始化时的 IO 和类加载开销。

### 5. 内存优化
1. 枚举是完整的类，每实例化一个枚举值会额外创建对象（Class 实例 + 实例字段），JVM 无法内联；int 常量在编译时内联为常量值，无额外对象开销。
2. **存在风险** — `window.decorView.postDelayed` 的 Runnable 在 Activity finish 后 10s 仍会执行，且 `lifecycleScope.launch` 在 Activity finish 后被取消，但如果 `finish()` 先于 Runnable 执行则无问题；主线程 `delay(10000)` 期间 finish 不会导致泄漏，但如果 Activity 被系统重建则 Runnable 持有的引用可能泄漏。
3. LeakCanary 通过 `ActivityLifecycleCallback` 监听 `onActivityDestroyed`，将 destroyed Activity 传入 `RefWatcher.watch`，WeakReference 持有对象并在 GC 后检查引用队列，若仍存活则 dump heap 分析。

### 6. 卡顿与流畅度优化
1. Display 每帧刷新时发出 VSYNC 信号，Choreographer 监听 VSYNC，在 `doFrame` 回调中触发 View 树的绘制；合理对齐动画和任务到 VSYNC 周期可避免 jank。
2. ① 复杂 item 布局（onBindViewHolder 耗时）② Bitmap 复用池 miss 导致频繁分配 ③ RecyclerView 频繁 `notifyItemChanged` 触发完整重绘。
3. `FrameCallback.doFrame` 在 UI 线程（Choreographer 所在线程）被调用；`Choreographer.postFrameCallback` 内部即通过 `postCallback` 将 FrameCallback 投入 `mCallbackQueue`，在 VSYNC 时取出执行。

### 7. Kotlin 协程
1. 挂起不阻塞线程，通过 `suspend` 关键字标记，CPS 变换将代码拆解为状态机；阻塞则直接让线程等待，挂起由 suspend函数 配合 `Dispatchers` 切换 coroutine 到其他线程继续执行。
2. 1 → 3 → 2 → 4 → 5；两个 launch 并发执行，delay 不会阻塞；coroutineScope 等所有子协程结束后才执行到 println("5")。
3. `Dispatchers.Main` 在 Android 基于 `Looper.getMainLooper().queue` 的 `Handler` 实现；Main 线程是单线程 Handler 循环，执行阻塞操作会卡住整个 UI 消息循环导致 ANR。

### 8. Kotlin Flow 与响应式编程
1. StateFlow 需要初始值，始终持有最新值给新订阅者（replay=1 且永不过期）；SharedFlow 无初始值，不缓存历史，只管新订阅者能收到「之后」的值，支持配置 replay 缓存大小但会过期。
2. 不会无限增长——`replay=1` 只保留最近一个值，新订阅者收到的是上一个值而非所有历史；但 `MutableSharedFlow` 本身可被多个收集者并发收集，不会爆内存。
3. 背压通过 `suspend` 机制自然处理——收集端在 `collect` 时挂起等待，下游处理完才继续取下一个；Flow 内部通过 `Channel` 作为缓冲，`BufferOverflow.SUSPEND` 实现背压。

### 9. Java 核心与 JVM 原理
1. `synchronized` 依赖 `ObjectMonitor`（内置锁），自动加锁解锁；`ReentrantLock` 基于 AQS，可中断、可超时、公平锁可配置。升级路径：偏向锁（无竞争）→ 轻量级锁（轻度竞争，CAS 自旋）→ 重量级锁（竞争激烈，调用 OS mutex）。
2. **线程安全** — `volatile` 防止指令重排序和可见性问题，双重检查锁定（DCL）正确实现了单例。
3. `WaitSet`：调用 `wait()` 的线程在此等待；`EntryList`：获取锁失败被阻塞的线程；`notify` 从 WaitSet 随机唤醒一个，被唤醒的线程移到 EntryList 重新竞争锁。

### 10. RecyclerView 四级缓存
1. `mAttachedScrap`：屏幕可见 ViewHolder，不参与复用只用于临时存放；`mCachedViews`：离开屏幕但可快速复用的 ViewHolder（默认 2 个）；`mViewCacheExtension`：自定义缓存扩展；`mRecyclerPool`：按 viewType 分组的 ViewHolder 池（默认 5 个/类型）。
2. `notifyDataSetChanged` 会清空 `mCachedViews`，因为 position 映射可能已失效。
3. `requestChildRectangleOnScreen` 在 `requestLayout` 或 scroll 时被调用，判断子 View 的矩形区域是否在可见区域内，和 `smoothScrollToPosition` 的滑动目标计算相关。

### 11. RecyclerView 预取源码（GapWorker）
1. `GapWorker` 在每帧 `dispatchDraw` 时计算即将可见的 item，通过 `PrefetchRegistry` 在下一帧前提前调用 `RecyclerView.getViewForPosition` 填充缓存。
2. 会受影响——嵌套时内层 RV 的预取被外层滚动事件打断，`PrefetchRegistry` 的 `post弓箭` 时序受父级滚动影响，预取和实际可见之间存在 race。
3. `dt` 是该 touch 事件距上一帧的时间差，`dt` 越小说明滑动越快，预取优先级越高。

### 12. 自定义 View 与绘制流程
1. 确保背景先绘制（裁剪区域），然后是内容、分发到子 View、前景装饰，避免覆盖问题。
2. **D** — A 必须做（避免内存泄漏），C 必须做（wrap_content 默认行为异常）；B 的 compress 取决于业务，不是必须的。
3. 不一定准确——`getLocationOnScreen` 在 `REL AYOUT` 之前调用会返回旧位置；应在 `ViewTreeObserver.OnGlobalLayoutListener` 或 `post(Runnable)` 中调用。

### 13. 事件分发机制
1. `dispatchTouchEvent` 遍历子 View 找到能接受事件的子 View，MOVE/UP 直接分发给该子 View，不需要再遍历。
2. 根本原因是嵌套方向相同（都是纵向），父 ViewGroup 拦截了子 View 的滑动事件；解决：子 View 调用 `parent.requestDisallowInterceptTouchEvent(true)` 请求父 View 不要拦截。
3. `interceptTouchEvent` 默认返回 false；有两种情况返回 true：① 父 View 认为当前事件是"滑动"（通过 `getX()-mInitialMotionX` 等判断）② `onInterceptTouchEvent` 被调用时发现子 View 没有处理 DOWN；ACTION_DOWN 返回 true 意味着父 View 拦截了后续所有事件，子 View 收不到任何 MOVE/UP。

### 14. MVVM
1. ViewModel 存储在 ViewModelStore，Activity recreate 时系统保留了 ViewModelProvider 的同一实例，数据不丢失；onSaveInstanceState 只能存储少量可序列化数据，且只用于 process death 场景。
2. 存在潜在问题——`data` 是 MutableLiveData，在 ViewModel 中直接暴露给外部破坏了封装性，应暴露 `LiveData` 只读接口。
3. `clear()` 在 ViewModelStore 的 `clear()` 中被调用，对应 `onCleared` 回调；`LoaderManager` 通过持有 `ViewModelStoreOwner` 间接持有 ViewModelStore，`destroy` 时遍历 clear 清理资源。

### 15. 组件化与模块化
1. 模块化关注代码拆分（物理层面），组件化关注业务边界复用和独立运行；模块化不一定组件化（只是代码分割），但组件化通常依赖模块化基础设施。
2. **B** — Gradle 配置缓存可以跳过未变化模块的重新计算，配合 `enableParallelBuild` 效果最好；A 治标不治本，C 不可能（模块间有依赖），D 不可行（业务模块不能编译为 aar）。
3. `Activation` 路由需要 ARouter 调用 `ARouter.getInstance().inject()` 激活，依赖编译时生成的 `$$ARouter$$Activation` 类；`Normal` 跳转是普通的 `navigation`；单组件编译时通过 `apt` 编译参数控制生成类的包含/排除。

### 16. MVI 与 Clean Architecture
1. MVVM 的数据流是双向的（View ↔ ViewModel），ViewModel 不知道状态变化的来源；MVI 强制单向数据流（Intent → State → View），所有状态变更都是可追溯的。
2. 数据层 Repository 属于 `data` 层，被 domain 层的 UseCase 依赖（依赖倒置）；异常通过 `Result<T>` 或 `Either<Failure, T>` 类型在 UseCase 层统一处理，不直接抛向 UI 层。
3. Reducer 必须是纯函数以保证确定性回放；若执行副作用，下次同 Intent 可能得到不同结果，违反 MVI 的可预测性。

### 17. OkHttp 拦截器
1. `BridgeInterceptor` 本身不处理重定向，它将 302 交给后续拦截器；`RetryAndFollowUpInterceptor` 负责根据 `Location` header 构建新请求并重试，跟踪重定向次数（默认 20 次）。
2. **不合理** — 同步写入磁盘会阻塞网络线程；应在拦截器外单独开线程处理，或使用 `Cache` 拦截器配合 `DiskLruCache`。
3. `RealInterceptorChain` 在 `proceed` 中创建新的 `RealInterceptorChain`（index+1）传入下一个拦截器，每个拦截器必须调用 exactly once 以确保所有拦截器都被执行。

### 18. 图片加载架构
1. LruResourceCache：内存缓存，按 LRU 淘汰；ActiveResources：正在使用的 View 的缓存（以弱引用持有，避免正在显示的图片被 LruCache 淘汰）；DiskLruCache：磁盘缓存。
2. 闪烁是因为 `RecyclerView` 在 `onBindViewHolder` 时没有清空 ImageView，直接 `setImageDrawable` 覆盖；解决：在 `Glide.with(context).load(url).into(imageView)` 前调用 `imageView.setImageDrawable(null)` 或使用 `RequestOptions.discardPlaceholder()`。
3. `key` 由 URL + 宽高 + 变化签名（signature）生成；BitmapPool 通过 key 匹配复用池中的 Bitmap，复用时需检查尺寸是否匹配（inMutable=true 且尺寸一致）。

### 19. 网络与离线缓存策略
1. `max-age=0`：每次使用缓存前都要验证（发送请求到服务器）；`no-cache`：强制所有请求跳过缓存直接到服务器。行为上：前者可能返回 304，后者一定会发送请求。
2. **A** — 先读缓存（避免白屏），再请求网络更新，缓存有效期 30s 满足实时性；离线时使用缓存但标注可能过期，兼顾离线体验。
3. 304 时使用 `cache-response`，body 为空但更新缓存新鲜度；新内容时优先使用 `network-response`（新鲜度更高），同时更新磁盘缓存；取舍逻辑在 `CacheStrategy.getCandidate` 中。

### 20. 推送与 IM 架构
1. 长连接（TCP）心跳用于保活和检测连接存活，MQTT 心跳是 keep-alive 机制；长连接单 TCP 连接省电（相比 WebSocket 多层封装），适合移动端推送场景。
2. 应等待服务端幂等处理——客户端发送后等待 ACK，超时后重发同一消息（携带相同 clientMsgId），服务端做去重，客户端收到 ACK 才清除重发队列。
3. seq 由服务器单点分配（趋势递增），通过 ZAB/Raft 等协议保证分布式下一致性；gap 出现时客户端应暂停本地渲染，等待服务器补发缺失消息或主动查询补全。

### 21. 移动端架构设计
1. 洋葱架构核心是层层依赖向外（内层不知道外层），Clean Architecture 核心是依赖倒置（entity → usecase → repository）；移动端倾向于扁平是因为移动端业务相对简单，过深层次影响性能。
2. **B** — 日活 1000 万需要网关层做流量分发和防护，业务层独立演进；A/C/D 不是必选项，会引入不必要的复杂度。
3. 服务端通过配置中心下发 FeatureFlag（key → rollout=0.05）；客户端 SDK 读取本地缓存的 Flag 并请求配置，满足条件则启用功能；服务端可动态调整百分比，无需客户端发版。

### 22. 性能与稳定性体系
1. 卡顿率 = 掉帧帧数 / 总帧数，通过 Choreographer 监听 VSYNC 周期，检测 `doFrame` 耗时就可计算；帧率通过 `SurfaceFlinger` 日志或 `dumpsys gfxinfo` 采集；Native 层通过 `Systrace` ATrace 标签上报关键事件。
2. **B** — SDK 在主线程发网络请求会直接导致 ANR（主线程阻塞），其他选项不会导致如此大幅度的 ANR 率升高。
3. `BlockCanary` 在 `Looper.loop` 前后设置 `Printer` 记录日志，检测 `msg.target.dispatchMessage` 的耗时；Android 10+ `Choreographer` 改为依赖 `SurfaceFlinger` 而非 `MessageQueue`，导致旧方案部分失效，需要切换到 `Choreographer.FrameCallback` 方式。
