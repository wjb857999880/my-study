# 组件化与模块化

## 概述
**组件化**是把大型单体 App 拆成可**独立开发 / 编译 / 测试 / 复用**的模块(壳工程 + 业务组件 + 基础组件),核心动机是解决单体工程的四大痛点:全量编译慢、模块强耦合、多人协作冲突、能力难复用。技术上要解决三个关键问题:**组件间通信与跳转**(以 **ARouter** 为代表,编译期生成 path→目标 映射表、运行期按表路由)、**依赖方向**(只能向下依赖、禁止业务组件横向直接依赖)、**单独调试与集成打包切换**(组件既能作 application 独立跑、又能作 library 集成)。它是高级岗架构能力的核心考察点。

## 核心原理 / 关键点

### 1. 为什么需要组件化(单体痛点)

单体工程(all in one module)随业务膨胀会:① 全量编译从几十秒涨到几分钟,拖慢开发;② 任意模块互相 import,改一处牵一片、边界模糊;③ 多人改同一工程频繁冲突;④ 业务能力无法被其他 App / module 复用。组件化把工程切成**高内聚低耦合的模块**,每个可独立编译、独立调试,从根本上缓解这四点。

### 2. 架构分层与组件类型

典型分层(依赖**自上而下**,禁止反向 / 横向):

- **壳工程(app)**:空壳,只负责初始化、集成各组件、装配 Application,不含业务。
- **业务组件(business module)**:各自一个完整业务(如 login / home / order),独立调试时是 app、集成时是 library。
- **基础 / 公共组件(base / common)**:网络、日志、UI 基类、工具,被业务组件依赖。
- **SDK / 三方库**:最底层。

依赖铁律:业务组件之间**不能直接依赖**,只能通过路由 / 接口下沉通信。

### 3. 组件间通信:ARouter 路由

**ARouter** 是最常用的路由方案,原理分两段:

- **编译期**:`@Route(path="/home/main")` 注解 + **APT**,为每个目标生成映射,汇总成一张「path → Class」表(路由表)。
- **运行期**:`ARouter.getInstance().build("/home/main").navigation()` → 查表 → 拿到目标 Activity / 服务 → 跳转或调用。

价值:调用方**只认 path 字符串**、不 import 目标类,从而解除编译期依赖——这就是组件化「跨组件跳转」的基础。

### 4. 页面跳转 vs 服务调用(数据通信)

- **页面跳转**:用 ARouter `navigation()` 跨组件启动 Activity / Fragment。
- **服务 / 数据调用**:跳转解决不了的场景(如 home 要调 account 的「取用户信息」)。解法是**接口下沉**:服务接口定义放公共 base 模块、实现留在业务组件,用 ARouter 的 `IProvider`(或 SPI)按接口暴露,调用方拿**接口实例**而非实现类。这样只依赖接口、不破坏隔离。

### 5. 单独调试与集成打包

- 用开关(如 `isRunAlone` / Gradle 变量):组件模块在调试时 `apply: 'com.android.application'`(配独立 Application + 假数据自己跑),集成时 `apply: 'com.android.library'` 被壳工程依赖。
- 组件可发布到 **Maven 仓库**(SNAPSHOT / release 版本),壳工程按版本依赖,实现编译隔离与版本管理。

### 6. 多模块下的 Gradle 配置

- **api vs implementation**:业务组件对底层库默认用 `implementation`(不向下游传递),只有「壳工程 / 下游要用」的才 `api`——否则一点改动引发雪崩重编。
- **公共配置收敛**:用 `buildSrc` / **Version Catalog**(`libs.versions.toml`)统一依赖版本与插件配置,各模块复用。
- **资源 / 签名**:壳工程统一配签名、buildTypes;`resourcePrefix` 给每个组件资源加前缀防冲突。
- 模块数变多后,**并行 + Configuration Cache** 对构建提速更关键。

### 7. 公共能力下沉与避免环形依赖

- 公共能力(基类、网络、日志、资源、埋点)下沉到 base / common,所有业务组件依赖它。
- **环形依赖**(A 依赖 B、B 又依赖 A)是组件化最常见陷阱:靠「接口下沉到 base + 事件总线」解耦,让依赖只指向更底层。
- 资源(public.xml、同名 drawable)冲突:`resourcePrefix` 强制前缀 + 命名规范。

### 8. 落地步骤与方案对比

- **渐进式落地**:先抽 base → 再按业务切模块 → 再上路由 → 最后单独调试 + Maven 发布。**不要一步推倒重来**。
- **方案对比**:ARouter(最通用)、WMRouter(美团)、自建路由;选型看团队规模与历史包袱。
- **粒度权衡**:太细(每小功能一组件)→ 模块爆炸、路由表臃肿;太粗 → 等于没拆。按「业务边界 + 团队分工」定粒度。

## 实践经验 / 踩坑

1. **组件间直接 import 业务类** —— 破坏隔离,编译期又耦合回去;用路由跳转 / 接口下沉,只依赖接口与 path。
2. **环形依赖** —— A↔B 互相依赖编译失败;接口下沉到 base 或用事件总线解耦。
3. **路由 path 管理混乱** —— 散落字符串、改名不同步;统一常量类 + 命名规范,跳转引用常量。
4. **资源同名冲突** —— 多组件同名 drawable / string 合并报错;`resourcePrefix` 强制前缀。
5. **全量编译仍慢** —— implementation 没收敛(全用 api)、没开 CC / 并行;按需依赖 + 提速四件套。
6. **单独调试缺数据 / 缺 Application** —— 组件独立跑时要造假数据 + 专用 Application,否则启动崩。
7. **粒度切太碎** —— 模块爆炸、路由表臃肿;按业务边界适度合并,别为组件化而组件化。
