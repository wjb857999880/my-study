# 技术方案设计与评审

## 概述
动手前先写技术方案:背景 / 目标、**方案选型与对比**(为何选 A 不选 B)、风险评估、里程碑、回滚预案。评审时讲清**权衡与取舍**,接受质疑并迭代。这是高级岗的核心产出——「想清楚再写」,而不是边写边返工。

## 核心方法 / 原则

### 1. 为什么要写技术方案

- 「想清楚再写」:动手前对齐目标、暴露风险、评估方案,避免边写边返工、上线救火。
- 方案是**沟通与决策的载体**:让评审者、PM、运维都理解你要做什么、为什么、代价是什么。
- 高级岗的核心产出之一就是高质量方案。

### 2. 方案的组成

一份完整方案通常包含:

- **背景与目标**:解决什么问题、成功指标(可度量)。
- **方案选型与对比**:2-3 个候选,各自的优缺点,**为何选 A 不选 B**(带权衡)。
- **整体设计**:架构图、数据流、关键接口、数据模型。
- **风险评估**:技术风险、兼容性、性能、安全,及应对。
- **里程碑 / 排期**:分阶段交付。
- **回滚预案**:上线失败如何回退。

### 3. 方案选型:讲清权衡

- 选型本质是**权衡(trade-off)**:没有最优,只有「在当前约束下最合适」。
- 每个候选列出**成本 / 收益 / 风险**,用表格对比清晰。
- 明确**决策依据**:为什么不选看起来更酷的 B(团队不熟 / 维护成本 / 过度设计)。

### 4. 设计文档与 RFC / ADR

- **设计文档**:完整方案详述。
- **RFC(Request for Comments)**:先抛草案征求反馈,迭代式对齐。
- **ADR(架构决策记录)**:记录「为什么这么决策」,留痕防日后遗忘 / 重复讨论。
- 沉淀文档 = 减少重复沟通、传承上下文。

### 5. 评审:对事不对人

- 评审聚焦**方案**(正确性、可读性、风险、是否过度设计),不针对人。
- 作者要**讲清取舍、接受质疑、坦诚说"没想清楚"**,评审者提**建设性**意见(给方向而非命令)。
- 区分 must-fix(必须改)与 nice-to-have(建议),避免评审无止境。

### 6. 可度量与边界

- 目标用**数据 / 指标**定义(如启动降 20%),避免「更好」「更快」这种模糊表述。
- 明确**做什么、不做什么**(out of scope),防止范围蔓延。
- 量化也让验收清晰。

### 7. 风险与回滚

- 提前识别风险:技术可行性(验证过吗)、依赖、兼容性、性能、安全。
- 每个**高风险点配应对**:验证 spike、灰度、降级开关。
- **回滚预案**是底线:上线出问题如何快速回退(版本回滚 / 开关 / 数据可逆)。

### 8. 迭代而非完美

- 方案是**活的**:评审、实现、上线中会演进,持续更新。
- 避免过度设计:解决当下 + 为可预见变化留扩展,不为想象中的需求过度抽象。
- 「先正确再优化」「先 MVP 再完善」。

## 实践经验 / 常见误区

1. **不写方案直接写代码** —— 边写边返工、上线救火;动手前先对齐。
2. **方案只有"怎么做"没有"为什么"** —— 缺选型对比与权衡;讲清为何这样选。
3. **目标模糊** —— "更好 / 更快"无法验收;用数据定义目标。
4. **过度设计** —— 为想象需求过度抽象;解决当下 + 适度扩展。
5. **没风险评估 / 回滚** —— 出事手忙脚乱;提前识别 + 回滚预案。
6. **评审针对人 / 无建设性** —— 变成挑刺;对事、给方向。
7. **方案写完不更新** —— 与实现脱节;随演进迭代文档。
