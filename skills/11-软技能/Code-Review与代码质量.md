# Code Review 与代码质量

## 概述
Code Review 是团队质量与知识共享的主阵地:看可读性 / 边界 / 异常 / 重复 / 命名 / 测试,提**建设性**意见,区分 must-fix 与 nit。同时建立质量门禁(Lint / 单测 / CI)把问题挡在合入前。好的 Review 既守质量,也培养作者。

## 核心方法 / 原则

### 1. CR 的目的

不只是找 bug,更是:**质量把关、知识共享、规范统一、培养作者**。一个人写代码的盲区 Review 能补;团队风格通过 CR 趋同;新人在 Review 反馈中成长。

### 2. 看什么(Review 清单)

- **正确性与边界**:逻辑对吗?边界(空、null、越界、并发)处理了吗?
- **可读性与命名**:别人能读懂吗?命名是否达意?
- **异常与错误处理**:异常被妥善处理还是吞掉?
- **重复与抽象**:重复代码该提取吗?是否过度抽象?
- **测试**:有没有覆盖关键路径?测试有效吗?
- **性能 / 安全**:明显隐患。

### 3. 建设性反馈

- **对事不对人**:评代码不评人;用「这段逻辑」而非「你」。
- **提建议而非命令**:「考虑用 X 因为 Y」比「改成 X」更易接受。
- **解释 why**:不只说改什么,说为什么(教育意义)。
- **肯定好的设计**:正向反馈同样重要。

### 4. 分级:must-fix vs nit

- **must-fix**(必须改):正确性 bug、安全问题、明显坏味道 —— 合入前必须解决。
- **should-fix**(建议):可读性、更好抽象 —— 强烈建议。
- **nit**(细枝末节):拼写、格式 —— 作者自行决定,不阻塞合入。
- 区分层级,避免评审无限拉长、主次不分。

### 5. 质量门禁(CI / Lint / 测试)

- 把**机器能查的交给机器**:Lint、格式化、单测覆盖率、静态分析,CI 自动跑。
- CR 聚焦机器查不了的:**设计、命名、业务逻辑、权衡**。
- 门禁把低级问题挡在合入前,提高 CR 效率与质量。

### 6. 小而频繁的 PR

- **小 PR** 易 Review、易发现问题、易回滚;大 PR 审不动、问题藏更深。
- 频繁小步合入 > 一次性大堆。
- 一个 PR 聚焦一件事(单一职责)。

### 7. 作者的责任

- 提交前**自审**一遍:别把明显问题丢给 Reviewer。
- 写清**PR 描述**:背景、做了什么、怎么测的、影响范围。
- 主动**回应反馈**:有异议就讨论,认同就改。

### 8. CR 文化

- CR 是**双向学习**:Reviewer 也在看别人怎么写、学新东西。
- 守住质量底线,但不吹毛求疵;尊重作者时间。
- 把好的 CR 沉淀为**规范 / 模板**,团队整体提升。

## 实践经验 / 常见误区

1. **CR 当挑刺大会** —— 针对人、无建设性;对事、给方向、说 why。
2. **不分级全是 must-fix** —— 评审拖沓、作者疲惫;区分 must-fix / nit。
3. **大 PR 审不动** —— 问题藏深处、回滚难;拆小、单一职责。
4. **机器能查的也人审** —— 格式 / Lint 占用 CR;交给 CI。
5. **作者不自审** —— 低级问题浪费 Reviewer 时间;提交前自查 + 写清描述。
6. **只找 bug 不分享知识** —— 错过 CR 的教学价值;解释 why、肯定好设计。
7. **CR 不看测试** —— 逻辑改了没测试覆盖;要求关键路径有测试。
