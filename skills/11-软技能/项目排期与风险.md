# 项目排期与风险

## 概述
拆解任务、估算工时(留 buffer)、识别**关键路径与依赖**、提前暴露风险、用 **Owner 意识**推动跨方协作。高级岗不只「写代码」,更要保证「按时、按质、可控地交付」——风险早暴露一次,胜过上线救火一周。

## 核心方法 / 原则

### 1. 排期的目的

不是为了"给个数字",而是:**把模糊需求拆成可执行任务、暴露依赖与风险、对齐预期、保证可控交付**。好的排期是沟通工具,让所有相关方对"什么时候交付什么"有共识。

### 2. 任务拆解(WBS)

- 把大目标**逐层拆解**成可估、可独立交付的小任务(工作分解结构 WBS)。
- 拆得越细,估算越准、依赖越清晰、风险越早暴露。
- 经验:单个任务最好在 1-3 天粒度。

### 3. 工时估算 + buffer

- 估算基于**拆解后的子任务**,不是拍脑袋给总数。
- 留 **buffer**(应对未知、联调、测试、修 bug):经验值约 1.2-1.5 倍。
- 给出**乐观 / 中性 / 悲观**区间,而非单点承诺。

### 4. 关键路径与依赖

- **关键路径**:决定总工期的最长任务链;关键路径上任何延期 = 项目延期。
- **依赖**:外部依赖(接口、设计、数据)、内部依赖(任务先后)。
- 识别关键路径 → 重点保障;识别依赖 → 提前推动,别卡在等。

### 5. 风险识别与暴露

- 主动想**会出什么岔子**:技术可行性、依赖方延期、需求变更、人员风险。
- **早暴露**:风险越早说,应对空间越大;"闷头扛到上线"最危险。
- 风险早暴露一次,胜过上线救火一周。

### 6. Owner 意识

- 不是"我只负责我这块",而是**对最终交付负责**:推动跨方协作、主动 follow 依赖、暴露阻碍。
- 识别**阻碍(blocker)**并推动解除,而非等待。
- Owner 是"兜底者",也是"协调者"。

### 7. 跟踪与调整

- 排期是**活的**:进度跟踪(站会 / 看板)、发现偏差及时调整。
- 进度**透明**:让相关方看到状态,延期早说,别到最后才爆。
- 用里程碑检查点,而非只看最终日期。

### 8. 跨方协作

- 技术不是孤岛:与 PM(需求 / 优先级)、设计(资源)、测试(用例 / 时间)、后端(接口)对齐。
- 接口 / 数据等**跨方依赖**提前约定、持续跟进。
- 文档化接口契约,减少口头沟通歧义。

## 实践经验 / 常见误区

1. **拍脑袋估总工期** —— 不准、藏风险;拆解子任务再估算。
2. **不留 buffer** —— 未知 / 联调 / 修 bug 把计划撑爆;留 buffer 或给区间。
3. **忽视依赖 / 关键路径** —— 被外部卡住才发现;提前识别并推动。
4. **风险闷头扛** —— 上线才爆雷;早暴露、早应对。
5. **只管自己一块** —— 缺 Owner 意识;对整体交付负责。
6. **进度不透明** —— 相关方不知道状态;透明 + 偏差早说。
7. **排期当死承诺** —— 不容调整;视为活的、持续校准。
