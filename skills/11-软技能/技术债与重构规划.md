# 技术债与重构规划

## 概述
识别技术债(架构腐化 / 重复代码 / 过时依赖),按「**影响 × 紧急**」排优先级,在业务迭代中**渐进式重构**(童子军原则:离开时比来时更干净),避免「推倒重来」。能向非技术方讲清「为什么现在要还这笔债、不还的代价」。

## 核心方法 / 原则

### 1. 什么是技术债

- 技术债 = 为了短期速度 / 业务而**欠下的、将来要还的**质量代价(混乱设计、重复、过时依赖、缺失测试)。
- 和金融债一样:有**有意识的债**(主动权衡,为快上线)与**无意识的债**(能力不足 / 偷懒)。
- 债不可怕,**不管理、不偿还才可怕**(利息 = 维护成本越滚越高)。

### 2. 技术债的来源

- **赶进度**:为快速上线牺牲设计。
- **需求变更**:原设计不适配新需求,补丁式修改。
- **架构腐化**:边界模糊、耦合累积。
- **过时依赖 / 技术**:框架版本老旧、无人维护。
- **缺少测试 / 文档**:改一处不敢动。

### 3. 识别与量化

- 把技术债**显性化**:记录到债务清单(哪里、影响什么、还的代价)。
- 尽量**量化**:这块债导致启动慢 X 秒 / 每次改动多花 Y 人天 / 隐患 crash 率。
- 没记录 = 隐形债务,永远不会主动还。

### 4. 排优先级:影响 × 紧急

- 按「**业务影响 × 紧急程度**」排序,不是看哪个"技术最酷"。
- 高影响(阻碍业务、频繁出 bug)+ 高紧急 → 优先还。
- 低影响 + 不紧急 → 可延后,记录即可。
- 与业务排期结合,争取重构窗口。

### 5. 渐进式重构 vs 推倒重来

- **推倒重来**几乎总是灾难:周期长、风险高、新旧并行痛苦、新代码也很快变烂。
- **渐进式重构**:小步、持续、每步可验证可回滚,在业务迭代中顺手改。
- 能不重写就不重写;重写是最后的、被证明必要后的选择。

### 6. 童子军原则

- 「**离开时比来时更干净一点**」:每次改这块代码,顺手改善一点(命名、提取重复、加测试)。
- 长期累积,代码库自然向好,而不是靠"重构专项"。

### 7. 向非技术方讲清"为什么还债"

- 业务方关心的是业务,不是技术洁癖。
- 把债翻译成**业务语言**:"不还 → 上线慢 / 改需求慢 / 易出 bug / 留不住人";"还 → 能更快做下个需求"。
- 争取把重构**嵌入业务迭代**(每个版本还一点),而非独立排期(常被砍)。

### 8. 防止新债

- 重构还旧债的同时,建立**防新债**机制:CI 门禁、CR 把关、设计评审、规范。
- 否则"边还边欠",永远还不完。
- 技术债纳入版本规划,常态化管理。

## 实践经验 / 常见误区

1. **技术债不记录** —— 隐形债务永远不会还;显性化到清单。
2. **追求"技术酷"重构** —— 为重构而重构,无业务价值;按影响排序。
3. **推倒重来** —— 几乎总是灾难;优先渐进式重构。
4. **重构独立排期被砍** —— 业务方不买账;嵌入业务迭代、每版本还一点。
5. **不会向业务方讲价值** —— 说"代码烂"无效;翻译成业务影响。
6. **只还旧不防新** —— 边还边欠;建立门禁与规范防新债。
7. **一次想还完** —— 风险大、周期长;小步持续、每步可回滚。
