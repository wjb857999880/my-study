## 核心原理 / 关键点

### 1. 二叉树与递归

- 二叉树是**递归定义**:一棵树 = 根 + 左子树 + 右子树。
- 多数树题骨架:「**当前节点做什么 + 交给左右子树递归**」,关键是想清**递归函数返回值的含义**。
- 两种视角:**遍历**(用外部变量记答案)vs **分解问题**(函数返回子问题的解,如 `max(左, 右)+1`)。

### 2. 四种遍历

- **前序**(根左右)、**中序**(左根右)、**后序**(左右根):DFS 递归,区别在「处理根」的时机。
- **层序**:BFS + 队列逐层。
- 中序遍历 BST 得**升序序列**(BST 重要性质)。
- 遍历是所有树题的基础操作。

### 3. BFS 层序 vs DFS 深度

- **层序 BFS**:队列、按层处理,适合「层相关信息」「最短 / 最小深度」。
- **DFS(前 / 中 / 后)**:栈 / 递归,适合「路径」「深度」「子树信息汇总」。
- 选择:求最浅层 → BFS;求所有路径 / 深度 → DFS。

### 4. 经典递归题

- **最大深度**:`max(depth(left), depth(right)) + 1`。
- **翻转 / 对称**:递归处理左右子树。
- **直径**:最长路径 = 左深 + 右深;后序遍历时用全局变量更新。
- **平衡判断**:左右子树高度差 ≤ 1 且都平衡(后序,提前返回 -1 剪枝)。

### 5. 最近公共祖先 LCA

- 递归:在左右子树找 p、q;若分散在两侧 → 当前节点是 LCA;若都在一侧 → LCA 在那侧。
- 思想是「自底向上」汇聚。

### 6. 二叉搜索树 BST

- 性质:**左 < 根 < 右**,中序升序。
- 查找 / 插入 / 删除 O(h)(h 树高;平衡则 logn,退化链则 n)。
- 高频:验证 BST(中序判升序)、第 k 小(中序)、范围和。
- 删除节点:分无子 / 一子 / 两子(用前驱或后继替换)三情况。

### 7. 路径与子树问题

- 路径和:前缀和(根到节点)+ 回溯;或递归「以当前节点为起点」。
- 子树判断:递归「两树是否相同」+ 在每个节点调用。
- 递归返回值设计是关键(返回高度 / 是否 / 路径数等)。

### 8. 递归 vs 迭代 + 复杂度

- 递归最自然但栈空间 O(h);可改**显式栈**迭代(前 / 中 / 后序用栈模拟)。
- 时间大多 O(n)(每节点访问一次),空间 O(h)(栈)。
- 退化成链(斜树)时 h = n;平衡树 h = logn —— 这就是平衡树(AVL / 红黑)存在的理由。

## 实践经验 / 踩坑

1. **递归返回值含义没想清** —— 写出来不对;先明确「这个函数返回什么」。
2. **遍历 vs 分解问题混用** —— 用遍历视角写分解问题,或反之;选一种贯彻到底。
3. **BST 忘中序升序性质** —— 验证 / 第 k 小都能用中序简化。
4. **LCA 没考虑 p 是 q 祖先** —— 边界;先判存在性。
5. **需要汇总子树信息却用前序** —— 应在后序(先有左右结果才能算当前)。
6. **删除 BST 节点忘处理两子情况** —— 要用前驱 / 后继替换。
7. **树退化成链 → O(n)** —— 不平衡 BST 性能差;理解为什么要有平衡树。

### 了解档
**Q1：前序、中序、后序遍历的区别本质是什么？为什么 BST 的中序遍历恰好得到升序序列？**

A：区别本质是**处理根节点的时机**不同（前序根最先、中序根居中、后序根最后）。BST 中序下「左子树（小）先访问、自己居中、右子树（大）后访问」，且这个性质**递归地在每个节点都成立**，所以整棵树遍历下来就是升序序列。

**Q2：层序遍历（BFS）和深度优先（DFS）各自适合解决什么类型的问题？**

A：BFS 按层处理，适合「层相关信息」「最短 / 最小深度」；DFS 适合「路径」「深度」「子树信息汇总」。

### 熟悉档
**Q3：写出中序遍历（递归）与层序遍历（队列逐层，每层输出一个 List）。**

A：

```kotlin
// (a) 中序遍历（递归，「分解问题」视角：返回子问题结果再合并）
class Solution {
    fun inorderTraversal(root: TreeNode?): List<Int> {
        if (root == null) return listOf()
        val result = mutableListOf<Int>()
        result.addAll(inorderTraversal(root.left))
        result.add(root.`val`)
        result.addAll(inorderTraversal(root.right))
        return result
    }
}

// (b) 层序遍历：进循环时快照当前层大小，循环中入队的新节点不会混层
class Solution {
    fun levelOrder(root: TreeNode?): List<List<Int>> {
        if (root == null) return listOf()
        val result = mutableListOf<List<Int>>()
        val queue = LinkedList<TreeNode>()
        queue.add(root)
        while (!queue.isEmpty()) {
            val subResult = mutableListOf<Int>()
            for (i in 0 until queue.size) {   // until 只求值一次 → 层大小快照（本题最易错点）
                val node = queue.poll()
                subResult.add(node.`val`)
                if (node.left != null) queue.add(node.left)
                if (node.right != null) queue.add(node.right)
            }
            result.add(subResult)
        }
        return result
    }
}
```

考官注：(a) 每次递归新建 List 再 addAll 有拷贝开销，可改为传可变 List 累积；(b) Kotlin 更地道的队列是 `ArrayDeque` + `removeFirst()`（`LinkedList` 是 Java 遗留风格）。

**Q4：在 BST 中查找目标值是否存在（利用性质走单枝，不要全树遍历）。**

A：

```kotlin
class Solution {
    fun searchBST(root: TreeNode?, target: Int): Boolean {
        if (root == null) return false
        return when {
            target == root.`val` -> true
            target < root.`val`  -> searchBST(root.left, target)
            else                 -> searchBST(root.right, target)
        }
    }
}
```

O(h) 时间，单枝下降。

### 掌握档
#### Q5（排障）：isValidBST「逐边检查」版有什么 bug？构造反例并修复

```kotlin
fun isValidBST(root: TreeNode?): Boolean {
    if (root == null) return true
    if (root.left != null && root.left.`val` >= root.`val`) return false
    if (root.right != null && root.right.`val` <= root.`val`) return false
    return isValidBST(root.left) && isValidBST(root.right)
}
```

A：**(a) bug 本质**——只检查了每条父子边的大小方向，但 BST 的定义是「左子树**所有**节点 < 根 < 右子树**所有**节点」的**全局约束**：孙子节点不仅要和父比，还要和爷爷、太爷爷……比。逐边检查验证的是更弱的性质，真正要传递下去的是**上下界**——原代码没有携带任何边界信息。

**(b) 反例**：

```
      5
     / \
    4   6
       / \
      3   7
```

节点 3 在 5 的右子树里，按定义必须 > 5，实际 3 < 5 → 不是合法 BST。但逐边检查每步都「局部正确」（4<5 ✓、6>5 ✓、3<6 ✓、7>6 ✓），返回 true 误判。中序遍历得 4,5,3,6,7 非升序，立刻露馅。

**(c) 修法**：递归携带 (low, high) 开区间，进左子树收紧上界、进右子树收紧下界；边界用 `Long`，避开节点值本身是 `Int.MIN_VALUE / MAX_VALUE` 时的翻车：

```kotlin
class Solution {
    fun isValidBST(root: TreeNode?): Boolean =
        valid(root, Long.MIN_VALUE, Long.MAX_VALUE)

    private fun valid(node: TreeNode?, low: Long, high: Long): Boolean {
        if (node == null) return true
        val v = node.`val`.toLong()
        if (v <= low || v >= high) return false   // 越界即不合法
        return valid(node.left, low, v) &&        // 左子树：上界收紧为 v
               valid(node.right, v, high)         // 右子树：下界收紧为 v
    }
}
```

#### Q6（独立实现）：实现 BST 删除节点 deleteNode(root, key)，处理三种情况；两子时选前驱还是后继，为什么？

A：两步走：① 利用 BST 性质沿一条路径定位目标；② 按子节点个数分情况。**返回值是新子树根**，让父节点重新接上——递归写法的关键。

- 无子（叶子）→ 直接删，返回 null（被「一子」分支自然覆盖）；
- 一子 → 父节点「跨过」它，直接接那个孩子；
- 两子 → 用**后继**（右子树最小值）顶替它的值，再去右子树删掉后继。

**选后继的理由（正确性论证）**：后继 = 右子树一路向左到底，由「最小」可知它**必然没有左孩子**（否则左孩子更小，矛盾），因此「删除后继」自动落入情况 1/2，不会无限递归——这是算法正确性的保证。前驱（左子树最大，必无右孩子）完全对称、效果等价。工程上若在意树形态，可交替使用前驱/后继，避免总砍同一侧使树越长越偏（普通 BST 不保证平衡，影响有限）。

```kotlin
class Solution {
    fun deleteNode(root: TreeNode?, key: Int): TreeNode? {
        if (root == null) return null                    // 没找到 key，原样返回
        if (key < root.`val`) {
            root.left = deleteNode(root.left, key)       // 去左子树删
        } else if (key > root.`val`) {
            root.right = deleteNode(root.right, key)     // 去右子树删
        } else {
            if (root.left == null) return root.right     // 无左子：右子顶上（叶子时 right 为 null，情况1一并覆盖）
            if (root.right == null) return root.left     // 无右子：左子顶上
            var succ = root.right!!                      // 找后继 = 右子树最小
            while (succ.left != null) succ = succ.left
            root.`val` = succ.`val`                      // 用后继的值顶替
            root.right = deleteNode(root.right, succ.`val`)  // 再去右子树删掉后继
        }
        return root
    }
}
```

考官注：删除后继时从右子树顶部**重新搜索**了一遍（又一次 O(h)）；若下降找后继时顺手记父节点，可直接剪接，省一半路径。

### 精通档
#### Q7（权衡）：AVL 查询更「极致平衡」，为什么工程界（Java TreeMap / C++ std::map / Linux 内核）几乎都选红黑树？

A：**结论先行**：两者查询都是 O(log n)，AVL 只是常数上更平；但 AVL 为这点平坦付出的代价是**删除时 O(log n) 次旋转**，红黑树把结构调整硬性限定在**常数次旋转**（插入 ≤2 次、删除 ≤3 次，其余只是变色）。通用库面对读写混合的真实负载，「查询略慢一点点、改结构便宜一大截」几乎总是划算。

**① 平衡差距比想象中小**：

| | 平衡定义 | 高度上界 | n=10⁶ 时高度 |
|---|---|---|---|
| AVL | 任意节点左右子树高度差 ≤1 | ≈1.44·log₂n | ≤29 |
| 红黑树 | 根到叶黑节点数相同（黑高一致） | ≤2·log₂n | ≤40 |

红黑树最长路径 ≤ 最短路径的 2 倍是最坏界，两者平均深度都接近 log₂n、实测平均只差 1 层上下；每走一层的主要成本是 cache miss（~100ns）而非指令数——AVL 的查询优势 ≈ 少访问一两个节点，几个百分点量级，很难穿透缓存效应被观测到。

**② 维持平衡的成本——差距在这拉开**：

| 操作 | AVL | 红黑树 |
|------|-----|--------|
| 插入 | 最多 1 次旋转，但路径上高度要重算 | 最多 2 次旋转，其余只是变色 |
| 删除 | **最多 O(log n) 次旋转**——回溯到根，每个失衡祖先都可能要转 | 最多 3 次旋转，其余只是变色 |
| 每节点额外信息 | 平衡因子（≥2 bit，须精确维护） | 1 个颜色 bit（可打包进父指针低位） |

AVL 的删除是痛点：高度信息必须精确维护，删一个节点可能牵动回溯路径上每个祖先。rotate 是真正贵的操作（改 3~6 个指针 + 破坏多个 cache line），变色几乎免费——红黑树的哲学是用 O(log n) 次极便宜的 bit 翻转，把指针结构调整钉死在常数次。

**③ 频率假设：通用库面对混合负载**。AVL 胜出的前提是「查询远多于增删」（只读字典、内存数据库索引、需严格最坏查询深度的场景）；但 TreeMap / std::map / 内核是通用容器，无法假设负载偏读。工程铁律：**渐近复杂度相同时，选「写便宜」的那个**——除非明确知道负载只读。Linux 内核（CFS 按 vruntime 插入移除、epoll 就绪列表、vma 管理）更新极频繁、删除占比高，正是 AVL 最吃亏的负载；且红黑树「常数次旋转」的简单性让侵入式实现（节点嵌入数据结构、`rb_insert_color` / `rb_erase`）正确性容易保证。并发视角：红黑树每次更新触碰的指针是常数个，更容易做出并发友好的变体。

**④ 边界之外**：磁盘上的有序结构（如 MySQL 索引）两个都不用，用 B/B+ 树按磁盘页大小分叉、一次 IO 拿一页——另一个维度的权衡。

#### Q8（原理深挖）：Morris 遍历如何做到 O(1) 空间的中序遍历？机制、复杂度、代价与局限？

A：**问题本质**：中序遍历的难点只有一个——下沉到左子树之后怎么回到自己。递归靠调用栈记（O(h) 栈帧）、显式栈自己记（O(h)），Morris **让树自己记——把回程地址写在树里**。关键观察：要进左子树的节点，其中序前驱（左子树最右节点）此刻的 right 指针必然为空（它是左子树里最后被访问的），这是一块就在树上的闲置内存。

**核心机制（线索化）**：下沉前把前驱的空 right 指回自己（建线索）；走完左子树后自然沿线索回到自己；再找前驱时发现 `pred.right == cur`，说明这条线索是自己建的——左子树已完工，于是拆线索还原树、访问自己、转右。线索是临时脚手架：建了就拆，遍历结束树恢复原样（线索二叉树思想的临时版）。

```kotlin
fun inorderMorris(root: TreeNode?): List<Int> {
    val res = mutableListOf<Int>()
    var cur = root
    while (cur != null) {
        if (cur.left == null) {                    // 情况A：无左子，直接访问
            res.add(cur.`val`)
            cur = cur.right                        // 可能是真孩子，也可能是线索
        } else {
            var pred = cur.left!!
            while (pred.right != null && pred.right !== cur) pred = pred.right!!  // 找前驱（左子树最右）
            if (pred.right == null) {              // 第一次来：建线索，下沉
                pred.right = cur
                cur = cur.left
            } else {                               // 第二次来（沿线索回来的）：拆线索
                pred.right = null
                res.add(cur.`val`)                 // 左子树完工，访问自己
                cur = cur.right
            }
        }
    }
    return res
}
```

**复杂度**：空间 O(1)（只有 cur / pred 两个变量，没有栈和队列）。时间看似每节点找前驱 O(h)、总 O(n·h)，实际**每条边最多被完整走过 2 遍**（建线索一遍、沿线索回来确认一遍），边总数 n−1 → 总时间 O(n)，常数约为普通遍历的 2 倍。

**代价 / 局限**：① 遍历中树被临时改坏（出现环）→ 线程不安全，别的线程此时读树可能死循环；② 不能中途退出——break / 抛异常时残留线索会永久改坏树；③ 遍历中不能做插删（与线索互相干扰），只读 val 可以；④ 时间常数 ~2 倍，时间换空间；⑤ 不能用于不可变 / 共享树（没有改指针的许可）；⑥ 只适合深度序——前序容易（访问时机挪到建线索之前），后序别扭（需逆序输出每条右链），层序做不了（按层必须缓存整层，O(1) 空间没地方放队列）；⑦ 「第二次到达」的判断、拆线索时机都是坑，代码易错而收益少。

**工程定位（诚实版）**：工程里极少用——递归/显式栈一般只有几十层（h ≈ log n ≈ 30~60），一个指针 8 字节，总共几百字节，现代内存下 O(h) 几乎免费。真正有价值的场景：内存极度受限（嵌入式、超大并发遍历器数量）、面试展示指针级理解；顺带引出正经的线索二叉树（Perlis & Thornton 1960 提出，Morris 1979 发表此遍历）。一句话：**把回程信息存在树上而不是栈上，用「临时破坏树结构」换 O(1) 空间——漂亮的手术刀，而非日常工具**。
