# 多线程与并发

## 概述
协程之外的**传统并发**基础(JVM/Android):**线程与 Runnable**、**线程池**(ThreadPoolExecutor:核心 / 最大线程数、队列、拒绝策略;Executors 几种池及其隐患)、**synchronized 与 ReentrantLock**、**volatile**(可见性、非原子)、**CAS 与 Atomic\***、**wait/notify**、并发集合(ConcurrentHashMap)。Android 主线程模型:UI 只能主线程更新,耗时任务必须异步。这些是理解协程(其调度基于线程池)、Handler、锁优化的前提。

## 核心原理 / 关键点

### 1. 线程基础
`Thread` / `Runnable`:实现 Runnable(无返回值、`run`)或继承 Thread。状态:NEW → RUNNABLE →(BLOCKED / WAITING / TIMED_WAITING)→ TERMINATED。守护线程(`setDaemon(true)`)随主线程退出而终止。`Thread.sleep` 不释放锁、`Object.wait` 释放锁(需在 synchronized 块)。Android 主线程即「UI 线程」,有其专属 Looper。

### 2. ThreadPoolExecutor 七参数与工作流程
构造:`corePoolSize / maximumPoolSize / keepAliveTime / unit / workQueue / threadFactory / handler(拒绝策略)`。
**任务提交流程**(关键考点):提交任务 → ① 线程数 < corePoolSize,新建核心线程执行;② 否则入 workQueue 排队;③ 队列满 → 线程数 < maximumPoolSize,新建非核心线程;④ 仍满 → 触发拒绝策略。
**四种拒绝策略**:Abort(默认,抛异常)、CallerRuns(调用线程自己跑,背压)、Discard(丢弃)、DiscardOldest(丢最老再入队)。
含义:核心线程数 = 平常态并发;队列缓冲;最大线程数 = 峰值扩容上限。

### 3. Executors 四种池及其隐患
- `newFixedThreadPool(n)`:核心 = 最大 = n,**队列是 LinkedBlockingQueue(无界)** → 任务堆积 OOM。
- `newSingleThreadExecutor`:单线程,同样无界队列 → OOM。
- `newCachedThreadPool`:核心 0、最大 Integer.MAX、SynchronousQueue → 瞬时海量线程 OOM。
- `newScheduledThreadPool`:定时 / 周期。
**隐患**:无界队列或无界线程易 OOM,且线程名默认 `pool-N-thread-M` 难定位。生产应**显式 new ThreadPoolExecutor** + 有界队列 + 命名线程工厂 + 明确拒绝策略。

### 4. synchronized 与锁升级
` synchronized` 是 JVM 内建可重入锁,锁对象(实例 / Class)。JDK6+ 引入**锁升级**(无锁 → 偏向 → 轻量 → 重量):
- **偏向锁**:假设单线程,记录线程 ID,无竞争近乎无开销;
- **轻量级锁**:少量竞争,用 CAS + 自旋避免内核态阻塞;
- **重量级锁**:竞争激烈,升级为 monitor(操作系统互斥量),未抢到者阻塞。
升级单向不可降级(JDK15+ 偏向锁逐渐废弃)。特点:JVM 自动加锁释放、不可中断、非公平。

### 5. volatile:可见性、有序性、非原子
- **可见性**:写后立刻刷主存、读强制从主存读(禁止线程缓存旧值)。
- **有序性**:禁止指令重排序(插入内存屏障)。典型用途——双重检查锁单例的 `instance` 加 volatile,防「对象未初始化完被发布」(分配 → 赋值 → 初始化 可能重排)。
- **不保证原子**:`i++` 是读-改-写三步,volatile 下仍非原子,需 `AtomicInteger` 或 synchronized。

### 6. CAS / Atomic / ABA
**CAS(Compare-And-Swap)**:原子地「比较当前值 == 预期则更新」,硬件 CMPXCHG 指令支持,是无锁编程基础;`AtomicInteger.incrementAndGet` 即 CAS 循环。
- **ABA 问题**:值 A→B→A,CAS 认为没变 → 用 `AtomicStampedReference`(版本号)解决。
- **高竞争自旋开销**:CAS 反复失败浪费 CPU → `LongAdder` 分段累加(基值 + Cell[])减少竞争,高并发计数优于 AtomicLong。

### 7. 显式锁 ReentrantLock / ReadWriteLock / Condition
`ReentrantLock`:API 层可重入锁(基于 AQS),比 synchronized 灵活——可公平 / 非公平、可中断(`lockInterruptibly`)、可限时(`tryLock`)、可绑多个 `Condition`(替代 wait/notify)。
`ReentrantReadWriteLock`:读读共享、读写 / 写写互斥,适合读多写少。
`StampedLock`(Java8):乐观读锁,读多写少性能更好,但不可重入、易踩坑。
**AQS(AbstractQueuedSynchronizer)**:ReentrantLock / 信号量 / CountDownLatch 的基石,核心是「state + CLH 等待队列」。

### 8. 并发集合与同步工具
- **ConcurrentHashMap**:并发安全 Map(见 [[Java 核心与 JVM 原理]])。
- **BlockingQueue**:`ArrayBlockingQueue` / `LinkedBlockingQueue` / `SynchronousQueue`,生产者-消费者首选(`put/take` 阻塞)。
- **CountDownLatch**:一次性,等 N 个任务完成(`await/countDown`)。
- **CyclicBarrier**:可复用,N 个线程相互等待到齐再一起走。
- **Semaphore**:许可证,限流并发数。
- **CompletableFuture**(Java8):异步编排、链式组合,声明式并发。

## 实践经验 / 踩坑

1. **Executors 的 OOM**:Fixed / Cached 池因无界队列或无界线程数易 OOM。生产一律显式 `ThreadPoolExecutor` + 有界队列 + 命名 ThreadFactory + 明确拒绝策略。
2. **submit 吞异常**:`execute` 抛出未捕获异常会终止线程并打印;`submit` 把异常封进 Future,`get` 时才抛 ExecutionException——排查易漏。务必设 `Thread.setUncaughtExceptionHandler`。
3. **锁字符串 / Integer 缓存**:`synchronized("abc")` 锁字符串常量(全 JVM 共享)→ 跨类意外互斥;`synchronized(Integer.valueOf(1))` 同理(缓存)。锁应用私有 final 对象。
4. **volatile 不原子**:`volatile int i; i++` 多线程下丢更新,改 `AtomicInteger`。
5. **wait/notify 信号丢失**:`notify` 先于 `wait` 执行则永久等待;用 `Condition`(带版本 / while 循环)或直接用 `BlockingQueue` 避免手写等待。
6. **线程池未关闭**:`shutdown()` 平滑停(跑完队列)、`shutdownNow()` 立即停(中断);忘关可能致 JVM 不退出或线程泄漏。
7. **Android 线程模型**:AsyncTask / HandlerThread 部分已弃用;子线程更新 UI 抛 `CalledFromWrongThreadException`;耗时任务应走协程(见 [[Kotlin 协程]])或线程池 + post 回主线程。

## 四档考核 Q&A(2026-08-24)

### 了解档
**Q:`ThreadPoolExecutor` 的七个构造参数是什么?提交一个任务时内部按什么顺序决定「用核心线程跑 → 入队 → 新建非核心线程 → 拒绝」?`Executors.newFixedThreadPool(n)` 和 `newCachedThreadPool()` 各有什么隐患?为什么生产环境建议显式 `new ThreadPoolExecutor`?**

A:七参数:`corePoolSize / maximumPoolSize / keepAliveTime / unit / workQueue / threadFactory / handler`(拒绝策略)。

任务提交流程(关键考点):① 线程数 < `corePoolSize`,新建核心线程执行;② 否则入 `workQueue` 排队;③ 队列满 → 线程数 < `maximumPoolSize`,新建非核心线程;④ 仍满 → 触发拒绝策略。

**Executors 隐患**:
- `newFixedThreadPool(n)`:**核心 = 最大 = n**,队列是 `LinkedBlockingQueue`(**无界**,容量 `Integer.MAX_VALUE`)→ 任务堆积 OOM。
- `newCachedThreadPool`:核心 0、最大 `Integer.MAX`、`SynchronousQueue` → 瞬时海量线程 OOM。
- `newSingleThreadExecutor`:单线程 + 无界队列 → OOM(同 fixed)。

**生产建议**:显式 `new ThreadPoolExecutor` + 有界队列(`ArrayBlockingQueue` 或 `LinkedBlockingQueue(capacity)`) + 命名 `ThreadFactory`(`pool-N-thread-M` 难定位) + 明确拒绝策略(默认 AbortPolicy 不一定合适)。

### 熟悉档
**Q:实现一个线程安全的延迟加载单例(全局 `AppConfig`)。要求:① 懒加载;② 多线程安全;③ 高并发下不要每次都排队;④ 防指令重排序导致对象未初始化就被发布。**

A:Kotlin 首选 `by lazy(LazyThreadSafetyMode.SYNCHRONIZED)`:

```kotlin
class AppConfig private constructor() {
    val apiBaseUrl: String = readApiBaseUrlFromDisk()
    val timeoutMs: Long    = readTimeoutFromDisk()

    companion object {
        val instance: AppConfig by lazy(LazyThreadSafetyMode.SYNCHRONIZED) {
            AppConfig()
        }
    }
}
```

备选:贴近 Java 写法的 DCL(理解原理用):

```kotlin
class AppConfig private constructor() {
    companion object {
        @Volatile
        private var instance: AppConfig? = null

        fun getInstance(): AppConfig =
            instance ?: synchronized(this) {
                instance ?: AppConfig().also { instance = it }
            }
    }
}
```

**`@Volatile` 在这里做了两件事,缺一件都跑偏**:

| 作用 | 解决什么问题 |
|---|---|
| 禁止指令重排序 | 让"对象初始化"必须发生在"引用赋值"之前 |
| 提供 happens-before | 让其他线程读到 `INSTANCE != null` 时,一定能看到完整的字段值 |

**为什么不可省**:`instance = new AppConfig()` 对应 JVM 三步——① 分配内存;② 调用构造函数初始化字段;③ 把地址赋给引用。没有 volatile 时,JIT 可能把 ②③ 重排(先赋值再初始化),线程 B 拿到非 null 引用但字段都是默认值 → 业务读到脏数据。

### 掌握档
**Q:审下面这段「并行下载文件分片」的代码,列出所有并发/资源问题并修复。**

```kotlin
class ParallelDownloader(
    private val outputFile: File,
    private val totalParts: Int = 8,
) {
    private val executor = Executors.newFixedThreadPool(4)
    private val completedCount = AtomicInteger(0)
    private val parts = arrayOfNulls<ByteArray>(totalParts)
    private val latch = CountDownLatch(totalParts)

    fun download() {
        for (i in 0 until totalParts) {
            executor.execute {
                try { parts[i] = downloadPart(i) }
                finally { completedCount.incrementAndGet(); latch.countDown() }
            }
        }
        latch.await()
        merge()
        executor.shutdown()
    }
}
```

A:**问题清单**(按严重度):

🔴 **P0 — 直接产线事故/资源泄漏**
1. `latch` 不区分成功失败 —— finally 里无论成败都 `countDown` → 失败也走 `merge`,产出损坏文件
2. `merge()` 不检查完整性 —— 即使修了 #1,任何一处 `null` 都会 NPE
3. 异常被静默吞 —— `executor.execute { }` 内部抛异常只写日志,排查事故找不到 stacktrace
4. `Executors.newFixedThreadPool` OOM 隐患 —— `LinkedBlockingQueue` 无界
5. `shutdown()` 不在 `finally` 里 —— 中途异常 → 线程池不释放

🟠 **P1 — 功能性/性能**
6. `latch.await()` 无限等待 → 某个分片假死时进程挂起
7. 4 线程 + 8 任务不是真并行 → 后 4 个排队,IO 阻塞时浪费
8. `outputFile` 直接写入,中途异常留下半成品
9. 没有重试 → 一次网络抖动报废整个下载
10. `parts[i] = ...` 普通数组写 → 内存可见性靠 `latch` 间接触发,可读性差
11. `merge()` 在调用线程执行 → 写大文件阻塞调用方(Android 上直接 ANR)
12. `completedCount` 声明了从不读取 → 死代码

🟡 **P2 — 锦上添花**
- 线程没命名(默认 `pool-N-thread-M`)→ jstack 难定位
- 无法中途取消 → 已决定放弃,在飞分片继续空跑
- `parts[]` 常驻内存 → 大文件 OOM
- 未处理 `RejectedExecutionException`
- 无进度回调
- `download()` 不防重入

**修复版(Kotlin)**:

```kotlin
class ParallelDownloader(
    private val outputFile: File,
    private val totalParts: Int = 8,
    private val maxRetries: Int = 2,
    private val overallTimeoutMs: Long = 60_000,
) {
    private val threadIdx = AtomicInteger(0)

    // 修 #4 / #7 / 命名:显式 ThreadPoolExecutor + 有界队列 + 命名线程
    private val executor: ExecutorService = ThreadPoolExecutor(
        totalParts, totalParts,           // 核心=最大=8,真并行
        0L, TimeUnit.MILLISECONDS,
        LinkedBlockingQueue(totalParts),  // 有界,防 OOM
        { r -> Thread(r, "downloader-${threadIdx.getAndIncrement()}").apply { isDaemon = true } },
        ThreadPoolExecutor.AbortPolicy(),
    )

    // 修 #10:AtomicReferenceArray 明确 happens-before
    private val parts = AtomicReferenceArray<ByteArray?>(totalParts)
    private val success = AtomicInteger(0)
    private val failed  = AtomicInteger(0)
    private val latch   = CountDownLatch(totalParts)

    @Throws(IOException::class)
    fun download() {
        try {
            for (i in 0 until totalParts) {
                try {
                    executor.execute { downloadOne(i) }
                } catch (e: RejectedExecutionException) {  // 兜住 Rejected
                    failed.incrementAndGet(); latch.countDown()
                }
            }
            if (!latch.await(overallTimeoutMs, TimeUnit.MILLISECONDS)) {       // 修 #6:加超时
                throw IOException("download timeout: success=$success failed=$failed")
            }
            if (failed.get() > 0) {                                              // 修 #1 / #2:失败不 merge
                throw IOException("refusing to merge: ${failed.get()}/$totalParts failed")
            }
            val missing = (0 until totalParts).count { parts.get(it) == null }
            if (missing > 0 || success.get() != totalParts) {
                throw IOException("inconsistent state: missing=$missing")
            }
            executor.submit { merge() }.get()                                    // 修 #11:merge 在 IO 线程做
        } finally {                                                              // 修 #5:finally 兜底
            executor.shutdown()
            executor.awaitTermination(5, TimeUnit.SECONDS)
        }
    }

    private fun downloadOne(index: Int) {
        try {
            val data = retry(maxRetries) { downloadPart(index) }                // 修 #9:重试
            parts.set(index, data); success.incrementAndGet()
        } catch (e: Throwable) {                                                 // 修 #3:不再静默吞
            failed.incrementAndGet()
            // 生产代码:logger.warn("part $i failed", e)
        } finally {
            latch.countDown()  // ✅ 这个位置仍然是对的
        }
    }

    private fun retry(times: Int, block: () -> ByteArray): ByteArray {
        var lastError: Throwable? = null
        for (attempt in 0..times) {
            try { return block() }
            catch (e: Throwable) {
                lastError = e
                if (attempt < times) Thread.sleep(100L shl attempt)  // 100/200/400
            }
        }
        throw lastError ?: IllegalStateException()
    }

    private fun merge() {
        val tempFile = File(outputFile.parentFile, "${outputFile.name}.part.${System.nanoTime()}")
        try {                                                                       // 修 #8:tempFile + rename 保原子
            FileOutputStream(tempFile).use { fos ->
                for (i in 0 until totalParts) {
                    val data = parts.get(i) ?: error("part $i missing")
                    fos.write(data)
                }
            }
            if (!tempFile.renameTo(outputFile)) throw IOException("rename failed")
        } catch (e: Throwable) {
            tempFile.delete(); throw e
        }
    }
}
```

**Bonus — 重试策略(分层控制)**:

| 层 | 策略 | 理由 |
|---|---|---|
| 单分片内 | 同分片重试 2~3 次,指数退避 100/200/400ms | 网络抖动是局部问题,重试大概率成功 |
| 整体放弃 | 失败数 ≥ totalParts/2 时立即取消其它下载 | 4/8 失败说明服务端可能挂了,继续等是浪费 |
| 超时兜底 | 整体 `latch.await(60s)` | 防部分线程假死 |

为什么不在 1 个失败就放弃?(太激进,1 次抖动报废 8 分片太浪费)。为什么等到全失败才放弃?(太迟,服务端已 500 时继续等是浪费带宽电量)。

**Bonus — 能不能 8 分片并行写同一文件?**

能,用 `RandomAccessFile` + `FileChannel`,每片下完直接 `seek(offset)` 写。但要预先知道 `contentLength / totalParts` 算 offset。

**Tradeoff**:

| 维度 | 先下完再 merge(本实现) | 下载完直接 RandomAccessFile 写 |
|---|---|---|
| 内存 | 8 分片常驻,大文件压力 | 写完即释放,内存友好 |
| 磁盘 IO | 一次大顺序写,效率高 | 8 分片分散写,可能随机写(SSD 影响小,HDD 显著) |
| 代码复杂度 | 简单 | 复杂(要 contentLength / 处理最后一片大小不一致 / RAF 多线程同步) |
| 故障恢复 | merge 前崩了 outputFile 还是干净旧版 | 中途崩了 outputFile 已乱,需清理 |
| 进度可观察 | 下载完才"开始合并",进度条卡最后一下 | 进度平滑持续上升 |

**实用建议**:文件 < 100MB 用本实现(简单);> 500MB 用 RandomAccessFile 边下边写;GB 级用 Channel 流水线(下载→校验→写盘→释放)。

### 精通档
**Q1:Java 21 虚拟线程(Virtual Threads, Project Loom)解决什么问题?实现原理是什么(continuation + carrier + mount/unmount)?它和 Kotlin 协程在「轻量」的本质、CPS 变换、挂起栈、阻塞调用处理上有什么相同和不同?**

A:**目标相同**——把"执行栈"从"OS 线程栈"剥离,放到堆上,需要时再调度回任意线程。**实现机制完全不同**:

| 维度 | Kotlin 协程 | Java 21 虚拟线程 |
|---|---|---|
| 代码变换 | 编译器 CPS 变换,每个 suspend fun 编译成状态机类 | **无代码变换**——字节码就是普通 Java |
| 挂起时存什么 | 状态机对象(一个 label + 几个 local val),**几百字节** | **整条调用栈(PC + 栈帧)序列化到堆**,几 KB 起步、按需增长 |
| 挂起点位置 | 只在 suspend 函数处 | **任意阻塞 JDK I/O 调用处**(JDK hook 了 Socket、FileChannel) |
| 恢复机制 | `Continuation.resumeWith()`,调度到 Dispatcher 指定线程 | 调度回 `ForkJoinPool`(carrier pool)中的 carrier thread |
| 调度器 | 用户显式选 `Dispatchers.Main/IO/Default` | 内置 `ForkJoinPool.commonPool()`,不可换;CPU-bound 需换 |
| 挂起/恢复开销 | 几十~几百纳秒(状态机 switch) | 1~10 微秒(栈拷贝 + 调度) |

**关键差别**:虚拟线程的栈是"完整的",包括所有方法调用的栈帧 —— 这是它能"**普通阻塞 API 自动挂起**"的根本原因(它就是真线程,只是 JVM 在背后做栈 snapshot/restore)。

**Q2:阻塞调用在两边分别怎么处理?**

A:**Kotlin 协程**:你必须自己避坑。`Thread.sleep` / 阻塞 socket / JDBC `executeQuery` 在协程里 = 真的卡底层线程,因为字节码没经过 CPS 变换,JVM 看到的就是普通"线程阻塞调用",会傻乎乎占用 OS 线程直到返回。**必须显式分流**(`withContext(Dispatchers.IO)`)。

**Java 虚拟线程**:JDK 帮你适配。JDK 在 `java.io` / `java.net` / `java.nio.channels` 内部改造过阻塞调用,碰到这些 API 时,JVM 检测到当前是虚拟线程,触发"挂起协议":snapshot 调用栈到 `Continuation` 对象,释放 carrier 回 ForkJoinPool;等 I/O 就绪再 schedule 回来 mount 到 carrier 上。

**但有 Pinning 钉死坑** —— 虚拟线程仍会卡住 carrier 的场景:
- `synchronized` 里阻塞 → 钉死 carrier(Java 21;Java 24 起大幅缓解)
- JNI 阻塞调用
- 某些底层系统调用

**实践**:用 `ReentrantLock` 替代 `synchronized`;跑虚拟线程前用 `-Djdk.tracePinnedThreads=full` 检查钉死点。

**Q3:结构化并发怎么管?**

A:**Kotlin 协程**:`CoroutineScope` + Job 树。父 Job 等所有子完成才完成;子失败 → 父取消所有兄弟 → 异常向上抛;SupervisorJob 可切断连带。**语言级**(suspend/launch/async),2017 起 GA,生产 7+ 年。

**Java 21 StructuredTaskScope(preview)**:

```java
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    var user    = scope.fork(() -> api.fetchUser(userId));
    var orders  = scope.fork(() -> api.fetchOrders(userId));
    var address = scope.fork(() -> api.fetchAddress(userId));

    scope.join();             // 等所有子任务结束
    scope.throwIfFailed();    // 任一失败 → 取消兄弟 → 抛
    return new Profile(user.get(), orders.get(), address.get());
}
```

| 维度 | Kotlin 协程 | Java StructuredTaskScope |
|---|---|---|
| API 风格 | 语言级 | 库 API(preview,可能改) |
| 成熟度 | 2017 起 GA | preview |
| 取消传播 | `Job.cancel()` + `CancellationException` | `ShutdownOnFailure` / `ShutdownOnSuccess` 两种内置策略 |
| 异常传播 | SupervisorJob 控制 | 手动 `throwIfFailed()` |
| 上下文传递 | CoroutineContext 透明传递 | 需手动 wrap |

Kotlin 结构化并发明显更优雅、更成熟。

**Q4:Android 上能用虚拟线程吗?为什么首选还是 Kotlin 协程?**

A:**现状:Android 暂不支持** —— ART 不是 OpenJDK,没跟进 Project Loom;Android 类库是 subset + 私有实现,JDK 那些 patched 的 I/O 类在 Android 上字节码/行为都不一样,套不上去。截至 2026 年,无官方支持的虚拟线程。

**为什么 Android 首选 Kotlin 协程 — 五个不可替代的理由**:

1. **生命周期深度耦合** —— `viewModelScope` / `lifecycleScope` / `repeatOnLifecycle` 一等公民,ViewModel 销毁自动取消所有协程。虚拟线程没有这种 lifecycle 集成,自己实现 `ExecutorService.shutdownWhen(Lifecycle.DESTROYED)` 样板代码爆炸。

2. **Jetpack 全家桶原语** —— `LaunchedEffect` / `produceState` / `rememberCoroutineScope` / `flowWithLifecycle` 全以协程为一等公民。换成虚拟线程要重写一整套。

3. **UI 线程模型硬约束** —— Android View 系统必须 main thread 访问。Kotlin 有 `Dispatchers.Main.immediate` 这种 UI-thread 优化;虚拟线程没有"main thread"概念,跟 UI 线程模型正交,**不能替代**。

4. **主流库 suspend 适配** —— Retrofit / Room / OkHttp / DataStore / WorkManager / Paging 全部官方 suspend 支持。换成虚拟线程要自己写 `CompletableFuture → suspend` 桥接。

5. **编译器层安全网** —— `suspend fun` 调用方必须在协程里(类型安全)。虚拟线程写普通方法就行,IDE 没法提醒"这应该挂起"。

**架构选型判断**:
- **服务端 Java**:虚拟线程 > Kotlin 协程(直接用阻塞 API,Spring Boot 3.2+ `spring.threads.virtual.enabled=true` 开箱即用,跟 JDK 类库深度集成)。例外:项目已在用 Reactor/RxJava/Kotlin 协程,迁移收益不大。
- **Android**:Kotlin 协程 = 唯一正确选择,未来 3-5 年不会有变化。即使 Google 跟进 ART 支持虚拟线程,它也只是"免配置的 `Dispatchers.IO`",**不会替代协程** —— 协程核心价值是「生命周期管理 + 线程切换 + UI 集成」,虚拟线程解决的是另一个问题。

**一句话总结**:虚拟线程是「更好的 Thread」,Kotlin 协程是「更好的并发模型」。两者解决不同维度的问题。在 Android 这种「生命周期复杂 + UI 线程硬约束 + 生态深度绑定」的场景,Kotlin 协程的「并发模型 + 生命周期 + 主线程切换」三位一体能力,虚拟线程再过十年也补不齐。**Android 选 Kotlin 协程,服务端 Java 选虚拟线程,各取所长。**
