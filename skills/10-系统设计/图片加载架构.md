# 图片加载架构

## 概述
图片框架(Glide / Coil)的核心:**三级缓存**(内存 LRU → 磁盘 → 网络)+ 异步解码 + 采样压缩(inSampleSize)+ 生命周期绑定 + Bitmap 复用。设计点:内存上限与淘汰、解码线程池、占位 / 圆角 / 转换、列表复用防错位与闪烁。

## 核心原理 / 关键点

### 1. 图片加载要解决什么

加载一张网络 / 本地图片要经历:**请求 → 网络 / 磁盘读 → 解码为 Bitmap → 采样压缩 → 显示**。这些步骤慢、耗内存、易错位,所以用图片框架统一管理:缓存、异步、采样、生命周期。手写极易 OOM 与错位。

### 2. 三级缓存

- **内存缓存(LRU)**:命中即直接显示,最快,但受内存上限、进程死即丢。
- **磁盘缓存**:命中免网络,App 重启仍在。
- **网络**:兜底,最慢。
- 查:内存 → 磁盘 → 网络;写回相反(网络结果写磁盘 + 内存)。

### 3. 解码与采样压缩

- 一张原图几千万像素,Bitmap 占 `宽×高×4B`,直接解码易 OOM。
- **inSampleSize**:按目标 View 尺寸采样,只解码所需分辨率。
- **RGB_565**:省一半内存(无需透明时);异步在子线程解码。

### 4. Bitmap 复用(inBitmap)

- 列表滚动时大量 Bitmap 进出,频繁分配 / 回收触发 GC 卡顿。
- **inBitmap**:复用已释放的 Bitmap 内存区域,减少分配。
- 框架内部用对象池自动管理。

### 5. 生命周期绑定

- 图片请求绑定到 Activity / Fragment 生命周期:**页面销毁自动取消请求**,避免泄漏与无效加载。
- 框架(Glide / Coil)通过添加无 UI Fragment 监听生命周期实现。

### 6. 列表复用防错位

- RecyclerView 复用 ViewHolder:异步解码返回时,该 holder 可能已显示别的 item。
- 解法:**回调时校验当前 item 的 key / url**,不匹配则不设图(框架内部用 RequestKey / Signature 处理)。
- 占位图 + 正确取消旧请求,防闪烁与错位。

### 7. 变换与占位

- **占位图**(placeholder)、**错误图**(error)、**淡入动画**(crossfade)提升体验。
- **变换**:圆角、圆形、模糊、裁剪 —— 框架提供 Transformations,基于 Bitmap 复用避免每帧分配。

### 8. 选型:Glide vs Coil

- **Glide**:Google 系生态成熟、功能全、社区大。
- **Coil**:Kotlin-first、协程驱动、API 简洁、体积小、Compose 友好。
- 新项目(协程 / Compose)倾向 Coil;存量 / 复杂场景 Glide 成熟稳定。
- 核心都是三级缓存 + 异步 + 采样 + 生命周期,原理一致。

## 实践经验 / 踩坑

1. **不用框架手写解码** —— 极易 OOM + 错位;直接用 Glide / Coil。
2. **原图直接加载** —— 内存爆;按目标尺寸采样。
3. **列表图片错位 / 闪烁** —— 复用未校验 key;框架已处理,别绕过。
4. **缓存无上限** —— 图片占满内存 OOM;设内存 LRU 上限。
5. **主线程解码** —— 卡顿;异步解码。
6. **页面销毁没取消请求** —— 泄漏 + 无效流量;用框架生命周期绑定。
7. **大量图片不释放** —— 滑出屏幕仍持有;`onTrimMemory` 时框架自动清缓存。
