## 核心原理 / 关键点

### 1. 列表架构的核心问题

长列表要解的几件事:**大数据分批加载**(不全量)、**高效滚动渲染**(复用,见 RecyclerView 四级缓存)、**状态完备**(加载中 / 错误 / 空 / 无更多)、**与数据源 / 缓存联动**。流式信息流还多了瀑布流、无限滚动、动态高度。

### 2. 分页策略:页码 vs 游标

- **页码分页**(offset/limit):简单,但数据变动时易错位、跳页。
- **游标分页**(cursor / nextToken):用上一页末尾标识取下一页,数据增删不乱序、性能稳,**信息流首选**。
- 取舍:稳定有序 / 大数据用游标;简单固定列表用页码。

### 3. Paging3

- Jetpack 分页库:`PagingSource`(数据源,定义如何加载一页)+ `PagingData`(响应式流)+ UI 层(LazyColumn / Adapter)。
- 自动处理:预加载、列表占位、加载状态、错误重试,UI 无需手写滚动监听。
- 适合数据量巨大、需本地 + 远程分页联动的场景。

### 4. 预加载与无限滚动

- **预加载阈值**:用户滚到接近底部时提前加载下一页,避免「滚到底再等」。
- 自己实现:监听滚动,「倒数第 N 项可见」时触发加载。
- Paging3 的 `prefetchDistance` 内置支持。

### 5. 状态完备

列表要显式处理四种状态,缺一不可:

- **加载中**(骨架屏 / 转圈)、**错误**(重试按钮)、**空**(空态插画 + 引导)、**无更多**(底部「没有更多了」)。
- 用枚举状态机管理,避免状态混乱。

### 6. 增量更新:DiffUtil

- 用 `DiffUtil` / `ListAdapter` 计算新旧列表差异,**只更新变化的项**,避免全量 `notifyDataSetChanged`(闪烁、丢动画、性能差)。
- 配合 RecyclerView(四级缓存)做高效 diff 更新。

### 7. 下拉刷新 + 上拉加载状态机

- 下拉刷新:重置到第一页(游标重置 / 页码归 1)。
- 上拉加载:基于当前页继续。
- 边界:加载中不重复触发、失败可重试、已无更多不再请求、刷新与加载并发处理。

### 8. 与缓存联动 + 流式特化

- 本地缓存(Room)+ 远程分页:Paging3 的 `RemoteMediator` 实现「先展示缓存、后台拉远程写回」。
- 瀑布流(StaggeredGrid):动态高度、防跳动。
- 图片占位防错位(见图片加载架构)。

## 实践经验 / 踩坑

1. **页码分页数据错位** —— 列表有增删时 offset 漂移;信息流改用游标。
2. **加载状态不全** —— 缺空态 / 错误 / 重试,用户卡死;四种状态都要有。
3. **全量 notifyDataSetChanged** —— 闪烁、丢动画;用 DiffUtil 精准更新。
4. **预加载阈值不当** —— 太晚用户干等、太早狂请求;按一屏高度调。
5. **刷新与加载并发** —— 同时触发请求竞态;用状态锁。
6. **列表复用错位** —— 异步图片回调时 item 已被复用;按 key 校验。
7. **跳页 / 重复加载** —— 快速滚动触发多次;加载中标志位防重入。

### 了解档

**Q1：页码分页（offset/limit）和游标分页（cursor/nextToken）各是什么？核心区别？为什么信息流首选游标？**

A：页码 = 绝对位置（`LIMIT 20 OFFSET 40`，"跳过前 40 条"）；游标 = 相对锚点（编码上页末条 `sort_key+id`，`WHERE (created_at,id) < (:last_time,:last_id)`，"从这条之后继续"）。核心区别四点：

| 维度 | 页码 | 游标 |
|---|---|---|
| 深翻页性能 | O(offset+limit)，越翻越慢 | 索引 seek，O(log N+limit)，深度无关 |
| 数据变动 | 头部插入/删除 → 重复或漏项 | 锚定已读位置，序列稳定 |
| 能力 | 跳页、总数、SEO | 只能顺序、无总数 |
| 适配 | 静态可随机定位 | NoSQL（DynamoDB）与推荐合成流原生 |

信息流选游标三理由：①数据活跃，页码必重复/漏项（无限滚动体验极差）；②无限滚动 = 纯顺序访问，跳页/总数两个短板用不上；③用户翻得深，offset 是 DB 杀手；且推荐流是合成排序，不透明 token 还能编码推荐上下文。反之后台/报表/搜索结果页（要跳页和总数、数据静态）仍用 offset。

### 熟悉档

**Q2：Paging3 拉游标信息流：PagingSource 骨架（首页/下一页怎么区分、prevKey/nextKey 怎么给）+ UI 怎么接线（cachedIn 放哪）？**

A：泛型 `<String, FeedItem>`（Key 即游标类型）。区分首页/下一页就一句：**`params.key == null` 即首页**——首次加载 Refresh 传 null，追加时 Paging 自动带上一次成功 Page 的 nextKey：

```kotlin
override suspend fun load(params: LoadParams<String>): LoadResult<String, FeedItem> {
    val cursor: String? = params.key            // null = 首页
    return try {
        val resp = api.fetchFeed(cursor, params.loadSize)
        LoadResult.Page(
            data = resp.items,
            prevKey = resp.prevCursor,           // 不支持向上就 null
            nextKey = resp.nextCursor,           // ★ null 即到底，Packing 不再 append
        )
    } catch (e: Exception) { LoadResult.Error(e) }  // 供 retry() 重跑同 key
}

override fun getRefreshKey(state: PagingState<String, FeedItem>): String? =
    state.anchorPosition?.let { state.closestPageToPosition(it)?.prevKey }
    // 信息流下拉刷新回顶：直接 return null 更常用
```

接线：`Pager(config, pagingSourceFactory).flow.cachedIn(viewModelScope)`——cachedIn 必须放 ViewModel（配置变更不重拉、多 collector 共享），且是**链上最后一个操作符**。Compose 侧 `collectAsLazyPagingItems()` + `items(items, key={it.id})`，翻页态看 `loadState.append`、首屏态看 `loadState.refresh`；View 体系 `PagingDataAdapter` + `repeatOnLifecycle(STARTED){ collectLatest { adapter.submitData(it) } }`，头尾加载态用 `withLoadStateHeaderAndFooter`。

**Q3：不用 Paging 库：「滚到倒数第 3 项可见自动加载」怎么写？怎么防重？notifyDataSetChanged 怎么改 DiffUtil？**

A：滚动监听用 `onScrolled`（每帧回调不漏阈值）而非 `onScrollStateChanged`：

```kotlin
recyclerView.addOnScrollListener(object : RecyclerView.OnScrollListener() {
    override fun onScrolled(rv: RecyclerView, dx: Int, dy: Int) {
        if (dy <= 0) return                       // 只管向下
        val lm = rv.layoutManager as LinearLayoutManager
        if (lm.itemCount - lm.findLastVisibleItemPosition() <= 3)
            viewModel.loadNext()                  // 监听器只喊一声，闸门在 VM
    }
})
```

防重：闸门放**状态持有方**——`if (isLoading || !hasMore) return` + 成功才推进游标（失败重试拉同一页不漏数据）；viewModelScope 默认 Main 单线程，普通 Boolean 即线程安全。坑：列表不满一屏不发生滚动，数据回来后要手动补查阈值。DiffUtil 改造 = 换 `ListAdapter`：`areItemsTheSame` 用稳定业务 id 定身份配对（识别增删移），`areContentsTheSame` 定同条内容是否变了（变了才重绑，true 连重绑都跳过）；提交必须**新 List 实例**——`AsyncListDiffer` 对同引用 submitList 直接短路。

### 掌握档

**Q4（排障）：一段生产风格的分页 ViewModel，找出至少 4 个 bug 及线上后果，怎么修？**

A：5 个 bug：

1. **无 isLoading 闸门** → 滚动加载期间同页并发请求 → 重复条目（重复 id 还会搞乱 DiffUtil）+ page 多次 ++ 跳页漏数据；
2. **`_items.value!!.addAll()` 后 `_items.value = _items.value` 同引用提交** → LiveData 会重通知，但 `AsyncListDiffer.submitList` 引用相等直接 return → **数据到了、界面永不动**（最难查的"看起来都对"型 bug）；且暴露 MutableList 破坏封装；
3. **无 try/catch** → suspend 抛 IOException → launch 未捕获 → **弱网一次即 crash**；
4. **refresh 与在途 loadNext 竞态** → 旧页响应后到 addAll 进新列表 → 新旧混排、page/hasMore 错乱；
5. **refresh 成功后 page 停在 1** → 下次 loadNext 整页重拉首页。

修复核心：不可变 List + `_items.value = old + new`（新实例）；try/catch/finally 复位 isLoading，失败不推进游标；**世代号 generation**——refresh 时 `generation++`，load 响应落地前校验 `gen != generation` 直接丢弃（比 cancel 更稳：拦得住"响应已在回程路上"）；refresh 成功后 `page = 2`。

**Q5（设计）：把「下拉刷新 + 上拉加载」收敛成显式状态机：状态/事件/核心转移，哪些必须拒绝，刷新后「无更多」要不要复位？**

A：状态：`IDLE / REFRESHING / LOADING_MORE / REFRESH_ERROR / LOAD_MORE_ERROR / NO_MORE / EMPTY`；事件：`UserRefresh / UserLoadMore / UserRetryLoadMore` + 携带**世代号 gen** 的四类完成事件。核心转移：IDLE→刷新/加载；完成事件由响应决定 IDLE / NO_MORE（nextCursor==null）/ EMPTY（0 条）。四个指定场景：刷新中上拉 → **拒绝**（追加基准正在被推翻，防混排）；加载失败后下拉 → REFRESHING（刷新天然清错）；首屏失败重试 ≡ UserRefresh → REFRESHING；NO_MORE 下拉 → **必须允许**（"到底"是旧快照结论，拒了就永远看不了新内容）。必拒转移与防的 bug：REFRESHING+LoadMore（混排）、重复 Refresh / LOADING_MORE+LoadMore（重复请求）、NO_MORE+LoadMore（请求风暴）、空表+LoadMore（无锚点）、过期 gen 完成事件（响应乱序落地）。两条不变量：**加载类事件只能从"有锚点且空闲"状态发起；完成类事件只被对应进行中状态、当前世代接受**。「无更多」刷新成功后**必须复位**：它是旧游标链的快照结论，不复位则"允许刷新却不许翻"自相矛盾；复位后由新响应重新推导（首页 nextCursor==null → 再次 NO_MORE，由事实置位不由记忆置位）。边界：prepend 型刷新（保留已读位置）语义不同，不复位——跟着刷新语义走。

### 精通档

**Q6（架构）：offline-first 信息流（离线可读、刷新期间旧数据可见、失败不丢）：Room + 远端双层分页怎么组织？**

A：原则一句话：**UI 只从 Room 读，网络只往 Room 写**——UI 的流由 DAO 的 `PagingSource` 支撑；`RemoteMediator` 不给 UI 供数，只在本地数据耗尽/刷新时补库，写库后 Room 自动 invalidate 推新快照。`initialize()` 二选一：缓存够新 `SKIP_INITIAL_REFRESH`（秒开缓存、滚到底才联网、免疫进出页面刷新风暴）否则 `LAUNCH_INITIAL_REFRESH`。**remote_keys 单独一张表**（PK=label，存 nextKey/prevKey/lastRefreshMillis），游标挂最后一条 entity 上有四个坑：①空表/首页 0 条时**不存在"最后一条"**，游标无处安放，且无法区分"从未同步"（无行）与"服务端确认空"（nextKey=null）；②刷新清表连游标一起蒸发；③每页推进游标 = 频繁 UPDATE 内容行，与 upsert 耦合还污染 DiffUtil；④并发丢失更新。**事务**：items 插入 + key 推进同一 `db.withTransaction`，不变量"游标推进 ⇔ 对应页已完整落库"；REFRESH 必须**先拿到响应、再在事务里整体替换**（清表+写入+重置 key），绝不"先清表再联网"——失败则事务不开启，旧数据原封不动。不白屏四层：结构性（UI 只认 Room，白屏路径写不出来）、事务性（MediatorResult.Error 无痕，UI 在旧列表上盖提示）、initialize 时机（首屏先渲染缓存）、Paging 3.3 `Pager.refresh()`（只让 RemoteMediator 跑 REFRESH、不动本地流，写完由 invalidation 自动顶上新数据；注意 `loadState.mediator` vs `source` 之分）。

**Q7（原理）：(a) 为什么 PagingData 的 map/filter 必须放 cachedIn 之前？cachedIn 缓存的是什么？(b) Room 写库后 UI 自动收到新列表的 invalidate 链路？**

A：(a) `PagingData` 不是数据，是**指向内部 PageEvent 通道的句柄**（已加载页缓冲、loadState、与 PagingSource 的连接）。`cachedIn(scope)` ≈ `conflate().shareIn(scope, replay=1)`：上游只收集一次 + 组播重放**最近一个 PagingData 实例**——新 collector 附上同一实例重放缓冲事件，旋转屏零重载不闪。转换放它后面 = 缓存的永远是原始流，每个新 collector 现场重新转换（全量 mapper 重跑、对象重分配、图片 URL 处理引发闪烁）、多 collector 各建 wrapper 行为不一致、`insertSeparators` 对重放事件二次处理易错乱。**cachedIn 是终点站，必须是最后一个操作符**。(b) 六步链路：①事务提交后 Room 生成代码上报 `InvalidationTracker`（每张表单调版本号 ++，diff 观察者集合）——**回调在提交后**，读库必读到新数据，无撕裂；②`LimitOffsetPagingSource` 注册的观察者被回调 → `pagingSource.invalidate()`；③invalidate 只打标记 + 广播 `InvalidatedCallback`（解耦：PagingSource 不知道 Pager 存在）；④Pager 收到广播 → 丢弃旧 fetcher → **`pagingSourceFactory` 造全新 source**（复用旧实例刷新就死了）→ 发射新 PagingData；⑤cachedIn 组播，`submitData` 切到新实例发起 initial REFRESH 重读库；⑥PageEvent.Refresh → DiffUtil 增量刷新。整条链没有一行手写通知——单一事实源架构里数据自动流动的全部秘密。
