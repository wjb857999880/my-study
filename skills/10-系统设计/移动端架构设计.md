# 移动端架构设计

## 概述
决定 App 的分层与模块边界:单模块 → 多模块 → **组件化**(壳工程 + 业务 / 基础组件)。选型权衡:耦合 vs 独立编译、路由方案(ARouter 等)、依赖方向、公共能力下沉。目标是各模块可**独立开发 / 编译 / 测试**,团队并行、构建提速、职责清晰。

## 核心原理 / 关键点

### 1. 架构的层次:分层 + 模块化

- **分层**:UI 层 → 领域 / 业务层 → 数据层(Repository)。层间单向依赖,上层不知下层实现。
- **模块化**:按业务 / 功能把代码切成 module,降低单工程复杂度。
- 分层解决「关注点分离」,模块化解决「工程规模与并行」。

### 2. UI 层架构演进

- **MVC → MVP → MVVM → MVI**:核心是把 UI 逻辑从 View 抽离、状态如何流动。
- MVVM 用 LiveData / Flow + DataBinding / Compose,ViewModel 持状态、View 订阅。
- MVI 强调「单向数据流 + 不可变状态」,状态可预测、易测。详见 MVVM 专题。

### 3. 数据层:Repository 模式

- Repository 作为数据唯一出口,内部封装「本地(Room)+ 远程(网络)」,上层只认接口。
- **单一数据源(single source of truth)**:UI 只从 Repository 读,不直接碰网络 / DB。
- 配合离线优先策略(见网络与离线缓存策略)。

### 4. 多模块 / 组件化的边界

- 从**单 module → 多 module → 组件化**(壳 + 业务组件 + 基础组件),随团队与规模演进。
- 组件化关键:组件间通信(ARouter 路由)、依赖只能向下、单独调试与集成切换。详见组件化与模块化专题。

### 5. 依赖方向与解耦

- 依赖只能从上到下;业务组件间**禁止横向直接依赖**,通过路由 / 接口下沉通信。
- 接口下沉:服务接口定义在公共层、实现在业务组件,调用方依赖接口。
- 避免环形依赖(A↔B):用接口 + 事件总线解耦。

### 6. 依赖注入(DI)

- 用 Hilt / Dagger 注入依赖,解耦创建与使用,便于替换实现(测试 mock)与统一生命周期。
- ViewModel / Repository / Retrofit 都通过 DI 提供。详见 Hilt 专题。

### 7. 异步与响应式

- Kotlin **协程 + Flow** 作为默认异步 / 响应式方案:结构化并发、取消传播、背压。
- UI 层用 Flow / LiveData 订阅状态;数据层用 Flow 暴露变化。
- 替代 Handler / AsyncTask / RxJava(大部分场景)。

### 8. 选型原则与演进

- **没有银弹**:架构服务于业务与团队规模,过度设计比简单方案危害更大。
- 演进式:从能跑的最简单方案开始,随痛点(编译慢、耦合、难测)逐步引入分层 / 模块化 / DI。
- 优先「可测、可维护、可演进」,而非追新。

## 实践经验 / 踩坑

1. **过度设计** —— 小项目就上组件化 + 多 module + DI 全家桶,徒增复杂度;按规模演进。
2. **业务组件横向依赖** —— 破坏隔离;用路由 / 接口下沉。
3. **数据层绕过 Repository** —— UI 直接调网络,DB 与网络两套状态不一致。
4. **层间反向依赖** —— 数据层回调 UI 层;保持单向。
5. **状态散落各处** —— 多个 LiveData 各存一份真相,难一致;收敛状态源。
6. **DI 用错作用域** —— 状态串台或频繁重建;按生命周期选 scope。
7. **追新弃稳** —— 为用 Compose / 新架构而重构,引入风险;价值驱动。
