# 数据埋点与 A/B 实验

## 概述
数据驱动闭环:从「拍脑袋」到「科学决策」。**埋点**是地基(没有数据,分析 / 实验都是空谈),**A/B 实验**是科学验证手段(随机分流 + 显著性,因果而非相关)。Android 端工程化的核心是:统一 SDK + 协议化 schema + 可靠上报 + 与 AOP/实验平台/隐私合规深度集成,让数据「采得准、传得稳、用得科学、收得合规」。

## 核心原理 / 关键点

### 1. 数据驱动闭环

- 闭环:**采集 → 分析 → 假设 → 实验 → 决策 → 迭代**,数据 → 洞察 → 行动。
- **埋点是地基**:没数据一切免谈,先有量再有质。
- **北极星指标**(North Star Metric):唯一核心指标,聚焦战略方向(如日活、次日留存、GMV),防止局部最优。
- 指标分层:北极星 → 二级指标 → 监控指标,逐层拆解可执行。

### 2. 埋点数据模型

- **事件 event**:用户行为,如 `click_buy`(点击购买);**属性 property**:上下文,如 `page` / `item_id` / `source`(来源渠道)。
- 维度:用户维度(谁)、会话维度(一次访问)、页面维度(在哪)、时间维度(何时)。
- **核心指标**:
  - **UV**(独立访客,去重用户数)/ **PV**(页面浏览量,不去重)。
  - **留存**(次留 / 7 留 / 30 留,衡量粘性)。
  - **漏斗**(转化各环节的流失率,如 浏览→加购→下单→支付)。
  - **时长**(会话 / 页面停留)。
- **事件命名规范 + 事件字典**:统一口径(如 `view_home` 不写 `home_view`),避免同义不同名、同名不同义;字典由数据团队维护,版本化。

### 3. 采集方式

- **代码埋点**(手写 SDK 调用):精确可控、可带业务参数;但侵入强、人力成本高、易漏易错。
- **全埋点 / 无痕埋点**(SDK 自动采集所有 `onClick` / 页面切换):省人力、可回溯圈选;但**噪声大、数据量爆炸、隐私敏感、动态参数采不到**。
- **可视化埋点**(运营在 UI 截图上圈点动态下发配置):介于二者之间,免发版。
- **服务端埋点**:关键转化(下单、支付)在服务端记录更准、防篡改。
- **混合策略**:核心漏斗用代码埋点 + 全链路无痕兜底,通常组合使用。

### 4. 埋点工程

- 统一埋点 **SDK + 协议**:事件 / 属性走 schema 校验,字段类型 / 必填 / 枚举值强约束,防脏数据。
- **上报策略**:
  - 批量(攒一批再传,省流量)/ 压缩(`gzip`)/ 失败重试 + 指数退避 / 降级丢弃(网络差时丢低优事件)。
  - 节流 / 去重(高频事件如滑动合并采样),按事件优先级分级上报。
  - **事件队列持久化**:崩溃 / 杀进程前落盘(SQLite / 文件),防丢,重启补传。
- 时区 / 时钟 / 顺序:**本地时间不可信**(用户改时区 / 不联网),关键时间戳用服务端时间或事件携带 `event_time` 校验,统一 UTC 存储、展示按地区转换。
- 与 **AOP 字节码插桩结合**(`ASM` / `AspectJ`):在 `onClick` / `Activity` 生命周期处统一织入,实现无痕埋点,解耦业务代码。
- **数据准确性校验**:埋点自查(自测 checklist)、与后端对账(订单数对账)、采样比对(线上抽样回放)、埋点自动化测试(遍历 UI 校验事件触发)。

### 5. A/B 实验

- **假设 + 指标**:先写假设(「红色按钮提升点击率」),定**核心指标**(点击率)+ **护栏指标**(性能 / 崩溃 / 留存不能恶化)。
- **分流**:对用户 id 做 **hash 进桶**(如 `hash(uid) % 100 < 50` 为实验组),对照组 vs 实验组;需**均匀**(SRM 检测)且**可重复**(同一用户每次进同组)。
- **分层正交**(overlapping / 层域):不同实验在不同「层」,层间 hash 互不干扰,流量可复用(同一用户可同时在 UI 层和推荐层实验)。
- **显著性**:**p-value < 0.05** + **置信区间**;样本量由 **功效(power)** 反推,样本不足会假阴性。
- **护栏指标**:性能 / Crash / 留存 / 收入任一恶化即否决,防「核心指标涨、全局亏损」。
- **坑**:**辛普森悖论**(分组结论与汇总相反)、**新奇效应**(短期涨长期回落)、实验周期太短(覆盖一个完整周期 / 节日效应)、**互干涉**(同层多实验争抢流量需分层正交解决)。

### 6. 灰度与实验平台

- **服务端配置下发**:实验分组、功能开关、动态参数从服务端下发,客户端 SDK 拉取 / 长连接推送,免发版。
- **feature flag**(功能开关):远程一键开关功能,支持 A/B 分流、灰度放量、紧急关闭。
- **强制更新 / 降级**:线上出问题秒级关停功能,止血优先于发版。
- **实验平台**:创建(配置分流规则)→ 分流 → 指标计算 → 报告闭环,自动化报告 + 显著性判定。
- 客户端 SDK 启动时**同步拉取**实验配置(避免首屏闪烁),可缓存到本地、监听服务端推送更新分组。

### 7. 隐私合规

- **用户授权**:首次启动**隐私弹窗**(工信部要求明确告知、最小必要),用户同意后才采集。
- **最小化采集**:只采必要数据,与功能无关的不采。
- **脱敏**:用户 id / 手机号 / ip / 设备 id 做哈希或不可逆处理,不传明文。
- **合规法规**:《个人信息保护法》(**PIPL**)、**GDPR**、苹果 **ATT**(App Tracking Transparency)、Android **广告 id 限制**(Android 13+ `AD_ID` 权限、隐私沙箱 `Privacy Sandbox`)。
- **SDK 安全**:第三方 SDK 审计,不让其乱采乱传(尤其商业化 / 推送 SDK),默认拒绝、白名单放行。

## 实践经验 / 踩坑

1. **埋点口径不统一** —— 同一指标多名 / 多义,数据对不上;事件字典 + schema 校验。
2. **核心漏斗只前端埋点** —— 前端丢点 / 用户关页,转化率虚低;关键转化服务端兜底。
3. **无痕埋点滥用** —— 数据爆炸且隐私风险高;核心路径用代码埋点。
4. **崩溃前事件丢失** —— 队列只在内存;持久化落盘 + 重启补传。
5. **A/B 样本不足就看结论** —— 假阳性 / 假阴性;先算样本量,等达到再判显著性。
6. **只看核心指标无护栏** —— 点击涨但留存 / 收入跌;必带护栏指标否决线。
7. **实验周期太短** —— 新奇效应掩盖真实效果;覆盖完整周期 + 节假日。
8. **第三方 SDK 偷偷采集** —— 合规事故;SDK 审计 + 字节码扫描 + 网络抓包核查。
9. **分流不均匀(SRM)** —— hash 函数选不好或缓存导致实验组 / 对照组样本严重失衡,结论全错;上线先做 SRM 检测。
10. **本地时区错乱** —— 留存率算错;统一 UTC 落库,展示层转换。
