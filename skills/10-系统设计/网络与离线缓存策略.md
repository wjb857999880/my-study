# 网络与离线缓存策略

## 概述
设计弱网 / 离线可用的数据层:HTTP 缓存(OkHttp `CacheControl`)、本地 DB 兜底、请求合并 / 重试 / 超时退避、数据同步(拉取 / 推送 / 冲突解决)、**先展示本地再后台刷新**。核心是用本地数据保证可用性,用同步策略保证最终一致。

## 核心原理 / 关键点

### 1. 离线优先的核心思想

- 弱网 / 断网时 App 仍要可用:**优先用本地数据展示**,后台再尝试同步远程。
- 数据层保证**可用性**(总能看到内容)+ **最终一致性**(联网后逐渐同步正确)。
- 这是 Repository 模式的典型用法:本地是 single source of truth。

### 2. HTTP 缓存(OkHttp)

- OkHttp 的 `Cache` + `CacheControl` 按 HTTP 缓存语义(Cache-Control / ETag / Last-Modified)缓存响应。
- 适合**纯查询、可幂等**的 GET;**不适合**动态个性化数据。
- 配置缓存目录与大小,按策略(网络优先 / 缓存优先 / 仅缓存)控制。

### 3. 本地 DB 兜底

- 真正离线可用要落本地(Room):网络失败时从 DB 读兜底展示。
- 网络成功后写回 DB,DB 通过 Flow 通知 UI —— UI 始终订阅 DB,不直接依赖网络结果。详见 Room 专题。

### 4. 请求可靠性:重试 / 超时 / 退避

- **超时**:连接 / 读 / 写超时,防请求挂死。
- **重试**:失败自动重试(限定次数),网络抖动场景必要。
- **退避**:重试间隔指数退避,避免雪崩;配合 OkHttp 拦截器实现。

### 5. 请求合并与防抖

- **请求合并**:同一资源并发请求时合并成一个(debounce / 去重),省流量。
- **防抖**:高频触发(搜索框)时等用户停顿再请求。
- 用 Flow 的 debounce / OkHttp 拦截器实现。

### 6. 数据同步策略

- **拉取(pull)**:客户端主动拉(轮询 / 定时 / 进入页面刷新)。
- **推送(push)**:服务端有更新时通知客户端(推送 / WebSocket)。
- **冲突解决**:多端编辑同一数据时,按时间戳 / 版本号合并,或服务端权威裁定。

### 7. 先展示本地再刷新

- 经典模式:进页面先从 DB 读**立即展示**(快、可用),同时后台请求网络,**成功后更新 DB → UI 自动刷新**到最新。
- 体验:立即可见 + 后台静默更新,无白屏等待。

### 8. 网络层封装

- Retrofit + OkHttp 封装:统一 BaseUrl、拦截器(日志 / 鉴权 / 缓存 / 重试)、错误转换、序列化。
- 详见 OkHttp 拦截器专题。封装后上层只调接口,不碰底层。

## 实践经验 / 踩坑

1. **HTTP 缓存用错场景** —— 动态 / 鉴权数据被缓存串数据;只缓存幂等 GET。
2. **网络失败直接崩 / 白屏** —— 没 DB 兜底;离线优先用本地兜底。
3. **UI 直接依赖网络结果** —— 状态难一致;UI 订阅 DB,网络写回 DB。
4. **重试不退避** —— 雪崩;指数退避 + 限次。
5. **无超时** —— 请求挂死 UI 卡;配连接 / 读超时。
6. **同步冲突不处理** —— 多端覆盖丢数据;版本号 / 时间戳冲突解决。
7. **高频请求不防抖** —— 输入即请求,浪费流量;debounce。
