# 推送与 IM 架构

## 概述
长连接方案选型:厂商推送(FCM / 华米 OV)、自建 TCP / WebSocket、MQTT。设计点:**连接保活与心跳**、消息可靠送达(ACK / 重传 / 去重)、离线消息补偿、电量与后台限制(Android 后台策略)、多端消息同步。IM 还要考虑消息序号、已读、存储分库。

## 核心原理 / 关键点

### 1. 推送 vs IM 的区别

- **推送**:服务端 → 客户端的**单向通知**(活动、消息提醒),多借厂商通道。
- **IM**:双向**实时通信**(聊天),自建长连接,要求低延迟、可靠送达、有序。
- 推送重「送达率」,IM 重「实时 + 可靠 + 有序」。

### 2. 长连接方案选型

- **厂商推送通道**(FCM / 华为 / 小米 / OV / vivo):系统级长连接、保活强、省电,国内需聚合多家。
- **自建 TCP / WebSocket**:可控、功能全(IM 必需),但要自己处理保活 / 重连。
- **MQTT**:轻量发布订阅,适合物联网 / 简单推送。
- 选型:通知用厂商推送,IM / 实时用自建长连接。

### 3. 连接保活与心跳

- NAT / 防火墙会清理空闲连接,**心跳**定时发包维持连接。
- 心跳间隔权衡:太频繁耗电耗流量,太长易掉线;**自适应心跳**(网络差时更密)。
- Android 后台限制(Doze / 后台限制)使保活更难,长连接常借前台服务 / 厂商推送。

### 4. 消息可靠送达

- **ACK 机制**:接收方收到回 ACK,发送方超时未收 ACK 则**重传**。
- **去重**:消息带唯一 ID,接收方记录已收 ID 避免重复。
- **顺序**:消息带序号(seq),按序处理 / 展示,乱序时缓冲等待。

### 5. 离线消息补偿

- 客户端断线期间的消息,服务端**存储**,重连后按「最后收到 seq」**补偿下发**。
- 离线消息有保留期,超期清理。

### 6. 多端消息同步

- 多设备登录(手机 + 平板 + Web):消息多端同步、已读状态同步、撤回一致。
- 用统一的消息 ID / seq,各端按需拉取同步。

### 7. 电量与后台限制

- Android 8.0+ 后台限制严格:后台长连接易被系统杀 / 限网。
- 应对:前台服务(带通知)维持连接、WorkManager 定时任务、厂商推送通道兜底。
- 不要靠「各种黑科技保活」(已基本失效且伤口碑)。

### 8. IM 进阶

- 消息存储:本地(Room)+ 服务端分库分表,按会话 / 时间分片。
- 已读回执、撤回、@、富文本、消息搜索。
- 群消息扩散:写扩散 vs 读扩散。
- 安全:端到端加密、传输加密(TLS)。

## 实践经验 / 踩坑

1. **长连接没心跳** —— 被 NAT 清理,「消息收不到」;定时心跳 + 自适应。
2. **不 ACK 不重传** —— 消息丢失无感知;ACK + 超时重传。
3. **不处理乱序 / 重复** —— 消息乱、重;seq 排序 + ID 去重。
4. **忽略离线消息补偿** —— 断线期间消息丢;重连按 seq 补偿。
5. **靠黑科技保活** —— Android 限制下基本失效且耗电伤口碑;用合规方案(前台服务 / 厂商推送)。
6. **IM 消息不有序** —— 聊天顺序错乱;统一 seq 排序。
7. **未考虑多端同步** —— 一端已读另一端未同步;统一状态同步。
