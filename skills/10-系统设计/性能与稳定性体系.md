# 性能与稳定性体系

## 概述
从单点优化到体系建设:启动 / 内存 / 卡顿 / 包体的**指标与基线**,稳定性(Crash / ANR 率)采集与**归因**、APM 监控大盘、灰度发布与降级、报警与 oncall。目标是「**可度量、可回归、可快速止血**」——优化不再是凭感觉,而是数据驱动 + 流程兜底。

## 核心原理 / 关键点

### 1. 从单点优化到体系

- 单点优化(启动、内存、卡顿、包体)解决了「当下」,但易回归。
- **体系** = 指标 + 基线 + 监控 + 流程,把性能 / 稳定性变成「可度量、防回归、可止血」的常态化工程。

### 2. 性能指标与基线

- 各维度定**量化指标 + 目标基线**:启动时长、帧率 / 掉帧率、内存峰值、包体积、Crash 率、ANR 率。
- 没有度量就没有优化:定基线后才能判断「优化有效」「是否回归」。
- 用基准测试(Macrobenchmark)与线上 APM 采集。

### 3. 启动 / 内存 / 卡顿 / 包体

- 四大单点详见各自专题:启动优化、内存优化、卡顿与流畅度优化、包体积优化。
- 体系下它们共享「指标 + 基线 + 监控 + 防回归」的方法论。

### 4. 稳定性:Crash 与 ANR

- **Crash 率**:Java 崩溃 + Native 崩溃,采集堆栈、符号化还原、聚合归因。
- **ANR**:主线程阻塞超阈值,系统弹「应用无响应」;采集 ANR 时的主线程堆栈。
- 目标:降 Crash / ANR 率,且能快速定位根因。

### 5. APM 监控大盘

- **APM**(应用性能监控):线上采集启动 / 帧率 / 内存 / Crash / ANR / 网络等,聚合到大盘。
- 按版本 / 机型 / 地域维度看趋势,异常自动报警。
- 工具:自研 APM / Bugly / Firebase / 第三方 APM。

### 6. 灰度发布与降级

- **灰度**:新版本先小流量(按比例 / 白名单),观察指标无异常再放量,降低事故面。
- **降级 / 熔断**:线上出问题时(某功能崩溃 / 慢),远程开关快速关闭该功能,**止血优先**。
- 功能开关 + 热修复能力。

### 7. 报警与 oncall

- 关键指标(Crash 突增、ANR、启动变慢)自动报警,关联到人 oncall。
- 建立应急流程:发现 → 止血(降级 / 回滚)→ 排查 → 复盘。

### 8. 防回归与文化

- **防回归**:CI 卡基线(性能基准测试、包体积阈值)、代码审查,防悄悄变差。
- 复盘机制:线上事故写复盘,沉淀到规范 / 工具。
- 文化:性能稳定性是全员长期投入,不是「优化周」一次性的事。

## 实践经验 / 踩坑

1. **优化不量化** —— 凭感觉,无法判断效果 / 回归;定指标 + 基线。
2. **只优化不防回归** —— 这版优化下版回退;CI 卡基线 + 趋势监控。
3. **Native 崩溃不符号化** —— 看不懂堆栈;用符号表还原。
4. **无灰度直接全量** —— 出事故全量受灾;灰度放量。
5. **无降级能力** —— 线上出问题只能紧急发版;预留功能开关 + 热修复。
6. **报警缺失 / 泛滥** —— 关键问题不报警或被噪音淹没;精准报警 + 关联 oncall。
7. **性能当一次性任务** —— 「优化周」完事就放;建立常态化监控与复盘。
