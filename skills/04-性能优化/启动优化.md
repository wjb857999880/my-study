# 启动优化

## 概述
App 启动是用户的第一印象,优化目标是缩短**冷启动**从进程创建到首屏可见(乃至可交互)的耗时。冷启动经过 fork 进程 → `Application.onCreate` → `Activity` 创建 → 布局/测量/绘制 → 首帧上屏等阶段,任一环节在主线程上的重活(初始化 SDK、同步 IO、复杂 inflate)都会拉长耗时。手段分两条线:**砍主线程关键路径上的串行工作**(异步/延迟/按需初始化、合并 ContentProvider、简化首屏),以及**让每次执行更快**(Baseline Profiles 引导 AOT 预编译、Macrobenchmark 量化回归)。核心是「先量化、再优化、有回归守护」。

## 核心原理 / 关键点

### 1. 启动阶段划分

- **冷启动(cold)**:进程不存在,从 zygote fork 进程开始,最慢,是优化重点。
- **温启动(warm)**:进程在、但 Activity 要重建。
- **热启动(hot)**:进程与 Activity 都在,直接 `onResume`,最快。
- 冷启动时序(简化):zygote fork 进程 → `ActivityThread.main` → 创建所有 `ContentProvider` → `Application.onCreate()` → `Activity` 创建(`onCreate`/`onStart`/`onResume`)→ `ViewRootImpl` 布局/测量/绘制 → 首帧上屏 → 首帧可见。
- 两个关键时间点:**首帧可见**(Displayed)、**可交互**(`reportFullyDrawn()`)。

冷启动各阶段(简化)与对应优化抓手:

| 阶段 | 主线程关键工作 | 常见耗时点 / 优化抓手 |
|---|---|---|
| fork 进程 → bindApplication | 创建 Application、初始化全部 ContentProvider | 三方 SDK 各塞 ContentProvider → 用 App Startup 合并 |
| `Application.onCreate()` | SDK 初始化 | 串行 init 一堆 SDK → 异步 / 延后 / DAG |
| Activity 创建 | `onCreate` → inflate 首屏布局 | 复杂 inflate / 同步解码大图 → 简化 + 异步 inflate |
| 布局 / 测量 / 绘制 | `ViewRootImpl` traverse | 层级深 / 过度绘制 → 简化首屏 |
| 首帧上屏 | (Displayed) | 没设 `windowBackground` → 黑白屏,加闪屏主题 |
| 可交互 | `reportFullyDrawn()` | 非首屏初始化 → 延到 `IdleHandler` / 按需 |

### 2. 衡量工具(先量化)

- `adb shell am start -W <pkg>/<activity>`:输出 WaitTime / TotalTime(到 displayed)。
- logcat:`ActivityTaskManager: Displayed ... +Xms`。
- **Perfetto**(替代已弃用的 systrace):抓系统+应用 trace,看主线程每段在干嘛。
- Android Studio **CPU Profiler**:函数级火焰图。
- **Jetpack Macrobenchmark**:`StartupMode.COLD/WARM/HOT` 自动多次测启动,出统计结果,适合 CI。
- 要点:本地手测波动大,以 Macrobenchmark 多次取统计为准。

### 3. 关键路径(Critical Path)与异步化

把启动期主线程上的工作画成**关键路径**(串行依赖链上耗时最长的路径)。优化方向:①砍掉非必要、②可并行的挪到子线程、③非首屏必需的延后。能异步的前提:任务不碰 UI、不依赖尚未初始化的东西。

### 4. 启动框架(App Startup / 自建 DAG)

- **Jetpack App Startup**:用一个统一的 `InitializationProvider`(ContentProvider)集中跑各 `Initializer`,替代「每个三方 SDK 各塞一个 ContentProvider」;仍默认主线程执行,但可声明依赖顺序、支持按需懒初始化。
- **自建启动框架**:把初始化任务建成**有向无环图(DAG)**——节点=任务、边=依赖;拓扑排序后把无依赖任务丢进线程池并发,有依赖的等前置完成;主线程只留「必须主线程 + 首屏依赖链」。业界方案(AndroidStartup 等)核心都是 DAG + 线程调度 + 环检测。

### 5. Application / ContentProvider 优化

- 所有 `ContentProvider` 在 `Application.onCreate` **之前**各自初始化,串行累加、有开销(尤其每个三方 SDK 塞一个)。
- 合并:用 App Startup 的 `InitializationProvider` 收编,或手动集中初始化。
- `Application.onCreate` 别做重活;能延后的延后。
- MultiDex:旧机型安装 dex 有开销,可用 R8/minSdk 或预提取规避。

### 6. 首屏渲染优化

- **窗口背景**:`windowBackground` 设闪屏 drawable,避免冷启动白/黑屏。
- 简化首屏布局层级、减少过度绘制。
- **异步 inflate**:`AsyncLayoutInflater`(或新版 ViewTree 机制)把首屏布局 inflate 挪到子线程。
- `ViewStub` 延迟 inflate 非首屏区。
- Android 12+ 用官方 **SplashScreen API**。

### 7. 延迟初始化 / 按需初始化

非首屏必需的三方 SDK 延后到首页渲染后(`IdleHandler` 空闲时)或进入对应功能时再 init;懒加载用到的才初始化。注意:别把首屏依赖的延后了,否则白屏更长。

### 8. Baseline Profiles + 指标守护

- **Baseline Profiles**:ART 首次运行靠 JIT + 解释执行(慢);Baseline Profiles 是「预录制的热点类/方法路径」,安装时(AOT)提前编译成机器码,显著缩短冷启动(官方示例约 30%,因应用而异)。用 Macrobenchmark 生成,或 AGP 自动集成。
- Macrobenchmark 在 CI 跑 startup,设基线 + 阈值告警,防回归。
- `StrictMode` 检测启动期主线程 IO/网络。

## 实践经验 / 踩坑

1. **Application.onCreate 串行初始化一堆 SDK** —— 主线程阻塞;异步/延后/DAG。
2. **ContentProvider 过多** —— 每个在 Application 前初始化、累加开销;用 App Startup 合并。
3. **首屏复杂 inflate / 同步解码大图** —— 拖慢首帧;简化布局 + 异步 inflate。
4. **启动期同步 IO**(大 SharedPreferences、网络)—— 主线程卡。
5. **优化了不量化** —— 凭感觉;用 Macrobenchmark/Perfetto 定基线 + CI 回归。
6. **没用 Baseline Profiles** —— ART 首跑 JIT+解释慢,Profile 提速明显。
7. **白/黑屏** —— 没设 `windowBackground` 闪屏主题。
