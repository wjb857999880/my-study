# 内存优化

## 概述
**内存优化**的目标是降低内存峰值、预防 **OOM**、定位并修复**内存泄漏**。Android 应用内存受每个进程上限约束,超限即 OOM 崩溃;而泄漏让无用对象久不释放、内存水位持续上涨,最终在峰值时(切大图、列表滚动)触发 OOM。排查三板斧:**Memory Profiler** 看内存曲线与对象分布、**LeakCanary** 自动监控常见泄漏、**MAT / hprof** 顺引用链找到 GC Root。其中 **Bitmap** 通常是内存大头,靠采样(`inSampleSize`)、复用(`inBitmap`)与交给图片框架托管来治理。

## 核心原理 / 关键点

### 1. Android 内存模型与 GC

- 每个 App 进程有独立堆(ART / Dalvik),受进程内存上限约束(机型不同,约 192MB~512MB+,`largeHeap` 可更高)。
- ART 的**分代 GC**:年轻代(频繁、快)、老年代(慢、Full GC);对象存活多次 GC 后晋升老年代。
- 系统紧张时 **LMK(Low Memory Killer)** 按优先级杀后台进程腾内存。
- 关注点:堆占用、**GC 频率**(频繁 GC = 卡顿 + 耗电)、native 内存(不进 Java 堆但计入进程上限)。

### 2. OOM 本质与常见场景

`OutOfMemoryError` = 进程在堆上限内**申请不到足够内存**。两类触发:① **瞬时峰值**(一次加载大量 / 超大对象,如未采样的 Bitmap、列表全量数据);② **泄漏累积**(无用对象久不释放,水位涨到上限后任何分配都崩)。高发:Bitmap 未采样、列表一次性加载海量 item、长生命周期对象持有短生命周期、native 大 buffer。

### 3. 内存泄漏类型

泄漏 = **长生命周期对象持有本该回收的对象**,使其无法被 GC:

- **静态 / 单例持有 Activity / View**:单例注册回调未解绑、静态变量持 Context。
- **Handler / 匿名内部类**:非静态内部类隐式持有外部 Activity,延迟消息未移除。
- **监听 / 广播 / EventBus 未注销**。
- **WebView**:持有 Activity,需独立进程或手动 destroy。
- **静态集合 / 缓存**只增不减。

关键:不需要 UI 的地方用 **Application Context** 替代 Activity Context。

### 4. 排查工具

- **Memory Profiler**(Android Studio):实时内存曲线、堆 dump、按类查对象数与大小、看引用。
- **LeakCanary**:自动监听 Activity / Fragment / ViewModel 等的销毁,检测泄漏并 dump 出引用链,**开发期最省力**。
- **MAT / Profiler hprof**:顺「对象 ← 引用链 ← GC Root」找到谁持有了它。
- `dumpsys meminfo <pkg>` / `procrank`:看进程整体内存分类(native / dalvik / graphics)。
- **内存指标三口径**:RSS(共享+非共享页,重复计共享,偏高)、USS(仅非共享页,进程死后真正可回收,偏低)、**PSS(非共享 + 共享均摊,官方推荐口径)**——衡量应用实际占用看 TOTAL PSS;Java dump 里数 Bitmap 的 `byteCount` 总量可实锤 native 层像素占用(8.0+ 像素在 native,Java 曲线会骗人)。

### 5. Bitmap 内存(最大头)

- 一张 Bitmap 占用 ≈ `宽 × 高 × 每像素字节`(ARGB_8888 = 4 字节),一张 4000×3000 ≈ **48MB**。
- **采样 `inSampleSize`**:按目标显示尺寸缩放解码,避免解码原图。
- **复用 `inBitmap`**:复用已有 Bitmap 的内存区域,减少分配。
- **RGB_565**(2 字节):对透明度无要求时省一半。
- **交给 Glide / Coil 托管**:自动按 View 尺寸采样、复用、按生命周期释放,远比手写安全。

### 6. 内存峰值治理

- **对象池 / 复用**:频繁创建的对象(消息、ViewHolder、byte[])用池。
- **分页 / 懒加载**:列表别一次性全加载,用 Paging / 游标分页。
- **避免一次性大集合**:流式处理代替全量读进内存。
- **`onTrimMemory` 释放缓存**:系统紧张时主动清图片 / 数据缓存,降峰值。

### 7. 低内存与后台回收

- `onTrimMemory(level)`:要分清两类信号。**`TRIM_MEMORY_UI_HIDDEN` 是生命周期信号**(UI 不可见、在 `onStop` 前回调,适合释放 UI 相关资源),**不是**内存压力级别——别当"最轻压力"处理;真正的内存压力级别是 `TRIM_MEMORY_BACKGROUND` / `MODERATE` / `COMPLETE`(后台时,越后越紧张)与 `RUNNING_LOW` / `RUNNING_CRITICAL`(运行中紧张),按级别从轻到重释放。
- `largeHeap="true"`:机型允许时申请更大堆,**是兜底不是解法**(泄漏不修照样 OOM,还拖累整机)。
- 后台保活与内存的矛盾:常驻占内存、易被 LMK 杀;按需用 WorkManager 而非常驻。

### 8. 持续监控与防回归

- 内存优化不能「调一次完事」:定**内存峰值基线**,CI / 灰度监控,超阈值告警。
- LeakCanary 集成进开发流程,泄漏随发现随修。
- 线上用 APM 采集 OOM / 内存水位 / GC 频率,关联版本做回归。

## 实践经验 / 踩坑

1. **LeakCanary 报的泄漏不修** —— 开发期嫌烦忽略,上线累积成 OOM;随报随修。
2. **Bitmap 不采样** —— 一张原图几十 MB,几张就峰值 OOM;按目标尺寸采样。
3. **静态 / 单例持 Activity Context** —— 改用 Application Context;回调及时解绑。
4. **匿名 Handler 持 Activity** —— 延迟消息 + 内部类泄漏;静态内部类 + 弱引用 + `removeCallbacksAndMessages`。
5. **监听 / 广播 / EventBus 未注销** —— 在 onDestroy / onPause 反注册。
6. **缓存无上限、不清** —— 内存涨;设上限(LRU)+ `onTrimMemory` 释放。
7. **优化不量化** —— 凭感觉调;用 Profiler 定峰值基线 + 线上监控防回归。

### 了解档

**Q1：衡量应用内存占用的 RSS / PSS / USS 分别是什么？实际该用哪个？**

A：**RSS** = 应用使用的共享 + 非共享页面总量（共享部分被重复计算）；**PSS** = 非共享页面 + 共享页面的均摊（三个进程共享 3MB 则各记 1MB）；**USS** = 独占的非共享页面（进程被杀后系统真正能收回的部分）。**Android 官方口径用 PSS** 衡量应用实际占用——RSS 高估、USS 低估，PSS 是「公平记账」。拿法：`adb shell dumpsys meminfo <pkg>`（看 TOTAL PSS 行）。

考官注：定义部分答对，但漏了落点——口径选择（用哪个）与工具（怎么拿到）。

**Q2：OOM 的本质是什么？内存泄漏和 OOM 是什么关系？**

A：本质：进程在内存上限内**申请不到足够内存**（机型差异约 192MB~512MB+，`largeHeap` 可更高）。泄漏是慢性病：不立即崩溃，但无用对象久不释放、水位持续上涨，最终在峰值时（切大图、列表滚动）触发 OOM。

考官注：补第二条路径——**瞬时峰值**（未采样 Bitmap、一次性全量加载）在零泄漏下也能直接 OOM；泄漏累积只是两条路径之一。

### 熟悉档

**Q3：ImageView 实际显示 200×200，原图 4000×3000，写出采样解码套路。**

A：两段式解码 + 官方对半缩算法，本例算出 `inSampleSize=8`、结果 500×375（高度受宽边 2 次幂约束）：

```kotlin
fun decodeSampledBitmap(path: String, reqW: Int = 200, reqH: Int = 200): Bitmap {
    val opts = BitmapFactory.Options()
    // ① 第一次解码：只要尺寸
    opts.inJustDecodeBounds = true
    BitmapFactory.decodeFile(path, opts)
    // ② 对半缩到「刚好覆盖目标」
    var inSampleSize = 1
    val halfW = opts.outWidth / 2
    val halfH = opts.outHeight / 2
    while (halfW / inSampleSize >= reqW && halfH / inSampleSize >= reqH) {
        inSampleSize *= 2
    }
    // ③ 第二次解码：真解
    opts.inJustDecodeBounds = false
    opts.inSampleSize = inSampleSize
    // 无透明要求的照片可再省一半：opts.inPreferredConfig = Bitmap.Config.RGB_565
    return BitmapFactory.decodeFile(path, opts)
}
```

考官注：工程上交给 Glide/Coil 自动做（按 View 尺寸采样），但底层套路就是这段。

**Q4：Activity 里 `handler.postDelayed({ updateUi() }, 60_000)`，泄漏点在哪、怎么修？**

A：泄漏链：主线程 MessageQueue → 延迟 Message → lambda（引用 `updateUi()` 即捕获 Activity `this`），60 秒内 Activity 无法回收。修法——`onDestroy` 清空待处理消息：

```kotlin
override fun onDestroy() {
    handler.removeCallbacksAndMessages(null) // null = 该 handler 全部消息与回调
    super.onDestroy()
}
```

考官注：Kotlin lambda 引用外部成员即隐式捕获 `this`，与 Java 匿名内部类同性质；更现代写法 `lifecycleScope.launch { delay(60_000); updateUi() }`，销毁自动取消。

#### Q5（排障）：Java heap 曲线平稳、LeakCanary 不报，但 PSS 持续上涨、最终 OOM——泄漏在哪层？怎么定位？

A：**native/graphics 层**（8.0+ Bitmap 像素在 native，Java 曲线会骗人）。四步：

1. `dumpsys meminfo` 分桶定位 Native Heap 还是 Gfx 在涨；
2. Memory Profiler native 录制 / Perfetto `heapprofd` 抓分配调用栈；
3. 场景归因（如聊天列表 → 无上限图片缓存 / Bitmap 池）；
4. 实锤技巧：**像素虽在 native，Bitmap 壳对象还在 Java 堆**——Java dump 里数 Bitmap 对象的 `byteCount` 总量即知谁占的。

#### Q6（设计）：图片内存缓存——内存上限 + 系统紧张时让出 + 线程安全。

A：选型先说「不手写 LRU，用 `LruCache`」：它原生带 access-order LRU、全方法 synchronized、`sizeOf` 自定义计量单位，三个需求覆盖两个，第三个用 `onTrimMemory` 补。

```kotlin
class ImageMemoryCache(maxSizeBytes: Int = defaultSize()) {
    companion object {
        // 常规做法：进程上限 1/8 + 绝对上限防大内存机型无脑涨
        fun defaultSize(): Int =
            (Runtime.getRuntime().maxMemory() / 8L).toInt()
                .coerceAtMost(64 * 1024 * 1024)
    }

    private val cache = object : LruCache<String, Bitmap>(maxSizeBytes) {
        // 容量按字节算，不按条数——图片大小差异巨大，按条数限流等于没限
        override fun sizeOf(key: String, value: Bitmap): Int = value.byteCount
        // 被淘汰的 Bitmap 可还回 BitmapPool 复用
        // （需引用计数确认无 View 在画；硬件位图不能 recycle）
        override fun entryRemoved(evicted: Boolean, key: String,
                                  old: Bitmap, new: Bitmap?) { /* bitmapPool.put(old) */ }
    }

    fun get(key: String): Bitmap? = cache.get(key)

    fun put(key: String, bmp: Bitmap) {
        if (bmp.byteCount > cache.maxSize()) return // 超大图拒收，防 put 完即逐出
        cache.put(key, bmp)
    }

    fun trim(level: Int) {
        when (level) {
            ComponentCallbacks2.TRIM_MEMORY_RUNNING_CRITICAL,
            ComponentCallbacks2.TRIM_MEMORY_RUNNING_LOW
                -> cache.trimToSize(cache.size() / 2)  // 前台紧张：砍半
            ComponentCallbacks2.TRIM_MEMORY_UI_HIDDEN,
            ComponentCallbacks2.TRIM_MEMORY_BACKGROUND,
            ComponentCallbacks2.TRIM_MEMORY_COMPLETE
                -> cache.evictAll()                    // 已不可见：全让
        }
    }
}
```

接线：缓存类没有生命周期，在 Application 里 `registerComponentCallbacks` 挂系统回调（Activity 的 `onTrimMemory` 只覆盖前台阶段）。

线程安全两层论——LruCache 自身方法级安全，但 **check-then-act 复合操作不安全**（两线程同 miss → 同图解码两次）。修复：miss 后 `ConcurrentHashMap.computeIfAbsent` 原子去重 in-flight 任务，**解码放在锁外**（放进锁则并发全串行化）：

```kotlin
private val inFlight = ConcurrentHashMap<String, Job>()

fun loadAsync(key: String, cb: (Bitmap) -> Unit) {
    cache.get(key)?.let { cb(it); return }
    inFlight.computeIfAbsent(key) { decodeAsync(key) { bmp ->
        inFlight.remove(key); put(key, bmp); cb(bmp)
    }}
}
```

### 精通档

#### Q7（原理讲透）：Android 8.0 为什么把 Bitmap 像素从 Java 堆搬回 native？解决了什么、靠什么保证安全释放、引入什么新代价？

A：一句话框架：**螺旋上升——native → Java → native，第三次回到 native 能成立，是因为补上了生命周期绑定机制。**

| 版本 | 像素放哪 | 释放机制 | 死法 |
|------|---------|---------|------|
| ≤2.3 | native（malloc） | finalize() / 手动 recycle() | finalizer 不可靠、释放滞后，GC 看不到 native 占用，越用越大 |
| 3.0–7.1 | Java 堆（byte[]） | GC 自动管理 | 挤占小得多的 Java 堆预算，OutOfMemoryError |
| 8.0+ | native，但用 **NativeAllocationRegistry（NAR）** 绑定生命周期 | Cleaner + 字节数记账 | 新代价（见下） |

3.0 搬进 Java 堆当时是对的（生命周期挂到 Java 对象、告别 finalizer），但留下三个结构性问题：① **Java 堆预算小且与普通对象共享**——12MP 照片 ARGB 就 48MB，而进程 Java 堆上限常见 192–512MB，相册滑几下就 OOM，哪怕设备还剩几个 GB；② **大分配制造 GC 抖动**——几十 MB 数组反复进出堆，分配速率是并发 GC 的第一信号，图片密集页 GC 飙升掉帧（`inBitmap` 就是那个时代的补丁）；③ **像素对 GC 毫无价值**——不含引用的纯字节放进追踪引用、移动对象的堆，等于让收集器为不需要其语义的数据付管理和搬移成本。8.0 搬回 native：堆预算还给普通对象、分配速率不再骚扰 GC，还解锁 **Hardware Bitmap**（像素以 AHardwareBuffer 落 GPU 显存、免上传——只有脱离 Java 堆后才可能干净地做）。

**安全释放：NAR 双通路**（与 ≤2.3 的本质区别——GC 与 native 两个方向的通路都接通）：

- ① **Cleaner**（虚引用 + 专用队列的 daemon）：wrapper 被 GC → 引用队列唤醒 → 在 GC 关键路径之外调 freeFunction。不是 finalizer：不允许复活、不阻塞 GC，finalizer 的老毛病（滞后、线程积压、复活）全规避；`Bitmap.finalize()` 在 8.0 被删除换成 NAR。
- ② **`VMRuntime.registerNativeAllocation(byteCount)` 记账反馈回路**：每注册一笔 native 字节 ART 记一笔账，native/Java 堆比例超标时主动发起并发 GC → 回收 wrapper → 触发 ①。GC 从「看不见 native」变成「被记账驱动」。
- 辅助：freeFunction 指针校验必须落在已知 native 库代码区间（防任意指针注册的安全加固）；`recycle()` 保留供需立即释放的场景手动触发。

**新代价（区分度所在）**：

1. **可观测性整体搬家**：Java dump 里只剩几十字节 wrapper，像素大小只在 native 计账里；LeakCanary 的 Java 引用链分析天然失明，须改看 `dumpsys meminfo` Native Heap 桶 + native heap profiler / heapprofd（AS 后来加 Native Size 列是被迫跟进）。
2. **释放时机被动且滞后**：像素死在「wrapper 被 GC + Cleaner 执行」两步之后；Java 堆很闲时 GC 迟迟不来而 native 在涨——Glide/Coil 至今保留 BitmapPool 并主动 recycle 的理由：纯靠 GC 不够体面。
3. **崩溃语义变了**：从可捕获的 OutOfMemoryError 变成 malloc 失败（decode 时才抛 OOM）或 lmkd 直接 SIGKILL——后者连捕获机会都没有，只能靠线上坟墓日志排查。
4. **native 堆不会压缩整理**：Java 堆有 moving GC 对抗碎片，native 只有分配器（jemalloc→scudo）的自愈，长期运行碎片只增不减。
5. **Hardware Bitmap 限制外溢**：`getPixel`/画到软件 Canvas 直接抛异常，跨线程读需要 fence。

考官注：一处小瑕疵——LOS（大对象空间）在 ART 是不参与 compaction 的非移动区，「加重 compaction 负担」不如说「LOS 独立膨胀、只增不缩，靠 GC 压力间接治理」。

#### Q8（体系设计）：线上内存监控体系，要能回答：(a) 版本有没有恶化？(b) 恶化在哪层、归因到谁？(c) 要不要拦发布？

A：三层各自闭环：

- **指标（恶化检测）**：结果指标（OOM 率）定红线；**场景化分位数 PSS** 看趋势——不用会被稀释的全局均值；分桶看层级（Java / native / graphics）；**斜率抓泄漏**——重复进出场景的单调上涨才是泄漏指纹，水位高不一定是泄漏。
- **归因**：OOM 五分法——Java / native / lmkd / **fd 耗尽** / **线程耗尽**（后两类也是线上 OOM 族谱成员：`Too many open files`、`pthread_create` 失败）；Java 走 hprof，native 走 **malloc hook + 环形分配栈**，Bitmap 业务打标，最终落到模块 owner。
- **决策（拦不拦发布）**：基线 = 上一版本**机型×场景**存的分布（防高端机均值掩盖低端机恶化）；灰度同期 A/B 对比，**P90 + 置信区间**判定（防样本量噪音）；三级阈值对应**放量 / 暂停 / 回滚**的自动门禁。
