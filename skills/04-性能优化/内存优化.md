# 内存优化

## 概述
**内存优化**的目标是降低内存峰值、预防 **OOM**、定位并修复**内存泄漏**。Android 应用内存受每个进程上限约束,超限即 OOM 崩溃;而泄漏让无用对象久不释放、内存水位持续上涨,最终在峰值时(切大图、列表滚动)触发 OOM。排查三板斧:**Memory Profiler** 看内存曲线与对象分布、**LeakCanary** 自动监控常见泄漏、**MAT / hprof** 顺引用链找到 GC Root。其中 **Bitmap** 通常是内存大头,靠采样(`inSampleSize`)、复用(`inBitmap`)与交给图片框架托管来治理。

## 核心原理 / 关键点

### 1. Android 内存模型与 GC

- 每个 App 进程有独立堆(ART / Dalvik),受进程内存上限约束(机型不同,约 192MB~512MB+,`largeHeap` 可更高)。
- ART 的**分代 GC**:年轻代(频繁、快)、老年代(慢、Full GC);对象存活多次 GC 后晋升老年代。
- 系统紧张时 **LMK(Low Memory Killer)** 按优先级杀后台进程腾内存。
- 关注点:堆占用、**GC 频率**(频繁 GC = 卡顿 + 耗电)、native 内存(不进 Java 堆但计入进程上限)。

### 2. OOM 本质与常见场景

`OutOfMemoryError` = 进程在堆上限内**申请不到足够内存**。两类触发:① **瞬时峰值**(一次加载大量 / 超大对象,如未采样的 Bitmap、列表全量数据);② **泄漏累积**(无用对象久不释放,水位涨到上限后任何分配都崩)。高发:Bitmap 未采样、列表一次性加载海量 item、长生命周期对象持有短生命周期、native 大 buffer。

### 3. 内存泄漏类型

泄漏 = **长生命周期对象持有本该回收的对象**,使其无法被 GC:

- **静态 / 单例持有 Activity / View**:单例注册回调未解绑、静态变量持 Context。
- **Handler / 匿名内部类**:非静态内部类隐式持有外部 Activity,延迟消息未移除。
- **监听 / 广播 / EventBus 未注销**。
- **WebView**:持有 Activity,需独立进程或手动 destroy。
- **静态集合 / 缓存**只增不减。

关键:不需要 UI 的地方用 **Application Context** 替代 Activity Context。

### 4. 排查工具

- **Memory Profiler**(Android Studio):实时内存曲线、堆 dump、按类查对象数与大小、看引用。
- **LeakCanary**:自动监听 Activity / Fragment / ViewModel 等的销毁,检测泄漏并 dump 出引用链,**开发期最省力**。
- **MAT / Profiler hprof**:顺「对象 ← 引用链 ← GC Root」找到谁持有了它。
- `dumpsys meminfo <pkg>` / `procrank`:看进程整体内存分类(native / dalvik / graphics)。

### 5. Bitmap 内存(最大头)

- 一张 Bitmap 占用 ≈ `宽 × 高 × 每像素字节`(ARGB_8888 = 4 字节),一张 4000×3000 ≈ **48MB**。
- **采样 `inSampleSize`**:按目标显示尺寸缩放解码,避免解码原图。
- **复用 `inBitmap`**:复用已有 Bitmap 的内存区域,减少分配。
- **RGB_565**(2 字节):对透明度无要求时省一半。
- **交给 Glide / Coil 托管**:自动按 View 尺寸采样、复用、按生命周期释放,远比手写安全。

### 6. 内存峰值治理

- **对象池 / 复用**:频繁创建的对象(消息、ViewHolder、byte[])用池。
- **分页 / 懒加载**:列表别一次性全加载,用 Paging / 游标分页。
- **避免一次性大集合**:流式处理代替全量读进内存。
- **`onTrimMemory` 释放缓存**:系统紧张时主动清图片 / 数据缓存,降峰值。

### 7. 低内存与后台回收

- `onTrimMemory(level)`:要分清两类信号。**`TRIM_MEMORY_UI_HIDDEN` 是生命周期信号**(UI 不可见、在 `onStop` 前回调,适合释放 UI 相关资源),**不是**内存压力级别——别当"最轻压力"处理;真正的内存压力级别是 `TRIM_MEMORY_BACKGROUND` / `MODERATE` / `COMPLETE`(后台时,越后越紧张)与 `RUNNING_LOW` / `RUNNING_CRITICAL`(运行中紧张),按级别从轻到重释放。
- `largeHeap="true"`:机型允许时申请更大堆,**是兜底不是解法**(泄漏不修照样 OOM,还拖累整机)。
- 后台保活与内存的矛盾:常驻占内存、易被 LMK 杀;按需用 WorkManager 而非常驻。

### 8. 持续监控与防回归

- 内存优化不能「调一次完事」:定**内存峰值基线**,CI / 灰度监控,超阈值告警。
- LeakCanary 集成进开发流程,泄漏随发现随修。
- 线上用 APM 采集 OOM / 内存水位 / GC 频率,关联版本做回归。

## 实践经验 / 踩坑

1. **LeakCanary 报的泄漏不修** —— 开发期嫌烦忽略,上线累积成 OOM;随报随修。
2. **Bitmap 不采样** —— 一张原图几十 MB,几张就峰值 OOM;按目标尺寸采样。
3. **静态 / 单例持 Activity Context** —— 改用 Application Context;回调及时解绑。
4. **匿名 Handler 持 Activity** —— 延迟消息 + 内部类泄漏;静态内部类 + 弱引用 + `removeCallbacksAndMessages`。
5. **监听 / 广播 / EventBus 未注销** —— 在 onDestroy / onPause 反注册。
6. **缓存无上限、不清** —— 内存涨;设上限(LRU)+ `onTrimMemory` 释放。
7. **优化不量化** —— 凭感觉调;用 Profiler 定峰值基线 + 线上监控防回归。
