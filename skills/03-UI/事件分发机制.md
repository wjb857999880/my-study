# 事件分发机制

## 概述
触摸事件(`MotionEvent`)从 Activity → ViewGroup → View 的分发:`dispatchTouchEvent` → `onInterceptTouchEvent`(ViewGroup) → `onTouchEvent`,构成「分发 - 拦截 - 消费」的 U 型链。关键是理清三个方法与返回值语义。高频应用:**解决滑动冲突**(内外同方向 / 不同方向,靠拦截策略或 `requestDisallowInterceptTouchEvent`)、自定义手势、点击与长按判定。

## 四档考核 Q&A

### 了解

**Q1: 事件分发机制解决的是什么问题？`dispatchTouchEvent`、`onInterceptTouchEvent`、`onTouchEvent` 三个方法各自的职责与返回值语义是什么？**

- **`dispatchTouchEvent(ev)`**：**分发**事件。Activity / ViewGroup / View 都有；ViewGroup 在此决定「自己拦截」还是「下发给子 View」。返回值：本层是否消费了事件。
- **`onInterceptTouchEvent(ev)`**：**拦截**判断，**只有 ViewGroup 有**。返回 true 表示父布局要把事件留给自己（不再下发）。
- **`onTouchEvent(ev)`**：**消费 / 处理**事件。返回 true 表示消费了这个事件；返回 false 表示不处理，事件回传给父布局。

**解决什么问题：** 多个嵌套 View（如 ScrollView 里套 RecyclerView）同时想响应触摸时，必须有一套规则决定事件交给谁。Android 用「事件分发机制」把一个 `MotionEvent` 从外到内传递、再决定由谁消费，避免多个 View 抢事件。

**Q2: 什么是「U 型链」？为什么 DOWN 事件没消费的话，后续 MOVE/UP 就收不到了？**

事件从 Activity → ViewGroup → … → View 逐层 `dispatchTouchEvent` 下传；若到最底层没人消费（`onTouchEvent` 都返回 false），则反向逐层上传由父层处理，形成「U 型」。

**DOWN 决定整串事件归属：** 一个触摸序列从 `ACTION_DOWN` 开始。消费了 DOWN 的 View 会在 `mFirstTouchTarget` 中被记录，从而收到后续 MOVE / UP。若 DOWN 返回 false，则 `mFirstTouchTarget == null`，父布局直接拦截后续所有事件，子 View 收不到任何后续事件。

### 熟悉

**Q3: 用「外部拦截法」解决 ScrollView（父）嵌套 RecyclerView（子）的滑动冲突，关键代码是什么？何时返回 true（拦截）、何时 return super（放行）？**

```java
public class CustomScrollView extends ScrollView {
    private float mLastY;

    @Override
    public boolean onInterceptTouchEvent(MotionEvent ev) {
        int action = ev.getActionMasked();
        switch (action) {
            case MotionEvent.ACTION_DOWN:
                mLastY = ev.getY();
                return false;  // 必须先让子 View 拿到 DOWN

            case MotionEvent.ACTION_MOVE: {
                float dy = ev.getY() - mLastY;
                mLastY = ev.getY();

                // 子 View 已滚到顶部，且继续下拉 → 父拦截
                if (!recyclerView.canScrollVertically(-1) && dy < 0) {
                    return true;
                }
                // 子 View 已滚到底部，且继续上拉 → 父拦截
                if (!recyclerView.canScrollVertically(1) && dy > 0) {
                    return true;
                }
                break;
            }

            case MotionEvent.ACTION_UP:
            case MotionEvent.ACTION_CANCEL:
                return false;  // 让子 View 处理 fling 和点击
        }
        return super.onInterceptTouchEvent(ev);
    }
}
```

| 事件 | 条件 | 返回值 | 原因 |
|------|------|--------|------|
| ACTION_DOWN | 任何情况 | `false` / `super` | 必须先让子 View 拿到事件初始化触摸状态 |
| ACTION_MOVE | 子 View 还能往滑动方向滚动 | `super.onInterceptTouchEvent(ev)` | 放行 |
| ACTION_MOVE | 子 View 已到边界且继续往该方向拉 | `true` | 父布局接管 |
| ACTION_UP / CANCEL | 任何情况 | `false` / `super` | 让子 View 处理 fling 和点击 |

**Q4: `OnTouchListener.onTouch` 返回 `true` vs 返回 `false` 时事件走向有何不同？为什么返回 `true` 会导致 `onClick` 不触发？**

View 处理事件优先级（从高到低）：`onTouch`（TouchListener）→ `onTouchEvent` → `onClick`。

- **`onTouch` 返回 `true`**：事件被消费，`dispatchTouchEvent` 直接返回 true。`onTouchEvent()` **不会被调用**，`performClick()` 也**不会触发**，`onClick()` 永远不会执行。
- **`onTouch` 返回 `false`**：事件未消费，继续调用 `onTouchEvent()`。在 `ACTION_UP` 时 `performClick()` → `onClick()` 被触发。

```java
// onClick 在 onTouchEvent 的 ACTION_UP 中触发
public boolean onTouchEvent(MotionEvent event) {
    switch (action) {
        case MotionEvent.ACTION_UP:
            if (clickable) {
                notifyEnterOrExitForAutoScrollIfNeeded();
                performClick();  // ← onClick() 在这里被调用
            }
            break;
    }
    return true;
}
```

### 掌握

**Q5: 在外部拦截法中，父布局在 ACTION_MOVE 时拦截，子 View 会收到什么事件？fling（惯性滚动）会怎样？**

子 View 会收到 **`ACTION_CANCEL`**，fling 会**停止**。

父布局在 `dispatchTouchEvent` 中检测到 `intercepted == true` 且 `mFirstTouchTarget != null` 时，会调用 `dispatchTransformedTouchEvent(ev, cancel=true, child)`，向子 View 发送 `ACTION_CANCEL`。子 View 收到 CANCEL 后会调用 `onTouchEvent` 处理它，重置所有触摸相关标志位（包括 `mPrivateFlag3.PRESSED`、VelocityTracker 状态等），**正在执行的 fling 动画会停止**。

**Q6: 内部拦截法中，`requestDisallowInterceptTouchEvent(true)` 为何要求父布局对 ACTION_DOWN 返回 false？如果父布局对 ACTION_DOWN 返回 true 会怎样？**

`requestDisallowInterceptTouchEvent` **只对 `ACTION_DOWN` 之后的拦截生效**。因为 disallow 标志位是在子 View 处理 DOWN 事件的过程中被设置的。

- 父布局对 **ACTION_DOWN 返回 `false`**：子 View 的 `onTouchEvent` 能收到 DOWN 并返回 true，此时 disallow 标志位才有机会被设置。
- 父布局对 **ACTION_DOWN 返回 `true`**：子 View 根本收不到 DOWN，`mFirstTouchTarget == null`，disallow 标志位从未被设置，整个内部拦截法失效。父布局在 DOWN 时拦截了整串事件，后续 MOVE 不会再询问子 View 的意愿。

### 精通

**Q7: `NestedScrollingChild` 和 `NestedScrollingParent` 的协作流程是什么？fling 时嵌套滚动如何让父布局同步响应？请结合源码讲清完整协作链。**

核心角色：
- **NestedScrollingChild**：`startNestedScroll` → `dispatchNestedPreScroll` → `dispatchNestedScroll` → `stopNestedScroll` 四步接口
- **NestedScrollingParent**：响应子 View 滚动，实现父-子联动

**完整协作链（以 fling 为例）：**

```
① startNestedScroll(VERTICAL)
   子 View 向上广播："我要开始 fling 了，父布局准备好接应"
   ↓
② dispatchNestedPreScroll()
   父布局优先消耗滚动距离（如 CoordinatorLayout 跟着滚动）
   consumed[] 告知子 View 父用掉了多少
   子 View 拿到的量 = 原始量 - consumed
   ↓
③ dispatchNestedScroll(dxConsumed, dyConsumed, dxUnconsumed, dyUnconsumed)
   子 View 告知父布局最终消耗结果 + 未消耗量（到边界了）
   父布局可接着处理 dxUnconsumed/dyUnconsumed
   ↓
④ stopNestedScroll()
   清理状态，结束嵌套滚动
```

**dispatchNestedPreScroll vs dispatchNestedScroll：**
- `dispatchNestedPreScroll`：父**先**滚，子后滚（父优先模式）
- `dispatchNestedScroll`：子**先**滚，父后滚（子回告模式）

两者构成双向通信：父先伸手 → 子消耗剩余 → 子回告结果 → 父可接续处理未消耗量。

**Q8: 子 View 消费了 ACTION_DOWN，但父布局拦截随后的 ACTION_MOVE，此时框架如何安全地向子 View 发送 ACTION_CANCEL？`mFirstTouchTarget` 在其中起什么作用？**

父布局通过 **`mFirstTouchTarget`** 链表记住「哪个子 View 消费了 DOWN」，从而精确地找到那个子 View 并发送 CANCEL。

```java
// ViewGroup.dispatchTouchEvent 关键逻辑
if (action == ACTION_DOWN) {
    mFirstTouchTarget = null;  // 每次 DOWN 开始时清空
}

// 遍历子 View，寻找消费 DOWN 的那个
for (int i = childrenCount - 1; i >= 0; i--) {
    if (child.onTouchEvent(ev)) {
        mFirstTouchTarget = TouchTarget.obtain(child);  // 记录下来
        break;
    }
}

// 在 MOVE 阶段判断是否拦截
if (intercepted && mFirstTouchTarget != null) {
    // 子 View 消费过 DOWN，框架安全地向它发 CANCEL
    dispatchTransformedTouchEvent(ev, cancel=true, target.child);
}
```

**`mFirstTouchTarget != null` 的隐含确认：**
1. 子 View 接收过 ACTION_DOWN
2. 子 View 处于「触摸处理状态」
3. 子 View 有能力接收 ACTION_CANCEL

父布局不需要主动探测子 View 状态——`mFirstTouchTarget` 的存在本身就隐含确认了子 View 可以安全接收 CANCEL。

## 核心原理 / 关键点

### 1. 事件分发解决什么

多个嵌套的 View(如 ScrollView 里套 RecyclerView)同时想响应触摸时,必须有一套规则决定**事件交给谁**。Android 用「事件分发机制」把一个 `MotionEvent` 从外到内传递、再决定由谁消费,避免多个 View 抢事件。

### 2. 三个核心方法

- `dispatchTouchEvent(ev)`:**分发**事件。Activity / ViewGroup / View 都有;ViewGroup 在此决定「自己拦截」还是「下发给子 View」。
- `onInterceptTouchEvent(ev)`:**拦截**判断,**只有 ViewGroup 有**。返回 true 表示父布局要把事件留给自己(不再下发)。
- `onTouchEvent(ev)`:**消费 / 处理**事件。返回 true 表示消费了这个事件。

### 3. U 型传递链与返回值语义

事件从 Activity → ViewGroup → … → View 逐层 `dispatchTouchEvent` 下传;若到最底层没人消费(`onTouchEvent` 都返回 false),则反向逐层上传由父层处理,形成「U 型」。

- `dispatchTouchEvent` 返回值:本层是否消费了事件。
- `onInterceptTouchEvent` 返回 true:事件不再下发、交给自己 `onTouchEvent`。
- `onTouchEvent` 返回 true:消费,后续 MOVE / UP 都发给它;返回 false:不处理,事件回传给父布局。

### 4. DOWN / MOVE / UP 的分发与消费

- 一个触摸序列从 `ACTION_DOWN` 开始,中间若干 `ACTION_MOVE`,以 `ACTION_UP`(或 `ACTION_CANCEL`)结束。
- **DOWN 决定「谁消费这串事件」**:消费了 DOWN 的 View 会收到后续 MOVE / UP。
- 若父布局在 DOWN 之后才想拦截(MOVE 阶段),子 View 会收到 `ACTION_CANCEL`(被迫中断,要清理手势状态)。

### 5. onTouchListener / onTouchEvent / onClick 优先级

View 处理事件的优先级(从高到低):`onTouch(View, MotionEvent)`(TouchListener)→ `onTouchEvent` → `onClick`。

- 设了 `OnTouchListener.onTouch` 且返回 true → 拦截,后续 `onTouchEvent` / `onClick` 都不触发。
- 这解释了「为什么 onTouch 返回 true 就不响应 click」。

### 6. 滑动冲突:同方向 vs 不同方向

- **同方向冲突**:两层都纵向滑动(ScrollView 嵌 ListView),需按「谁该响应」判断(如子列表滑到边界交给外层)。
- **不同方向冲突**:一横一纵(ViewPager 嵌 RecyclerView),按滑动方向的角度 / 距离判定归谁。
- 本质问题:谁拦截、按什么条件拦截。

### 7. 解决滑动冲突:外部拦截法 / 内部拦截法

- **外部拦截法(推荐)**:逻辑在父布局的 `onInterceptTouchEvent` 里,按条件决定是否拦截——清晰可控。
- **内部拦截法**:子 View 不想被父拦截时,调 `parent.requestDisallowInterceptTouchEvent(true)` 禁止父拦截,配合父在 `onInterceptTouchEvent` 对 `ACTION_DOWN` 不拦截。逻辑分散在父子两端、较易出错。
- 经验:优先用外部拦截法。

### 8. 常见场景与现代方案

- ScrollView 嵌 ListView / RecyclerView:列表滑到边界时交给外层滚动。
- ViewPager 嵌 RecyclerView:横向翻页 vs 纵向列表,按方向判定。
- **现代方案**:`NestedScrolling` 机制让子 / 父协作滚动(RecyclerView / CoordinatorLayout 已内置),优先于手写拦截。

## 实践经验 / 踩坑

1. **`onInterceptTouchEvent` 只在 ViewGroup 有** —— 普通 View 没有此方法,直接走 `onTouchEvent`。
2. **DOWN 没消费,后续收不到** —— DOWN 决定整串事件归属;DOWN 返回 false 则 MOVE / UP 不会来。
3. **拦截后子 View 收到 CANCEL** —— 父中途拦截,子收到 `ACTION_CANCEL` 而非 UP,要处理好手势清理。
4. **`requestDisallowInterceptTouchEvent` 时机** —— 必须在父处理 DOWN 之后;且父对 DOWN 不拦截才有效。
5. **滑动冲突方案选错** —— 不分内外拦截法、逻辑乱;优先外部拦截法,集中在父布局。
6. **onTouch 返回 true 吞掉 click** —— 设了 OnTouchListener 且返回 true,onClick 不触发;按需返回。
7. **手写拦截不如 NestedScrolling** —— 新需求优先用内置嵌套滑动机制,少自己造轮子。
