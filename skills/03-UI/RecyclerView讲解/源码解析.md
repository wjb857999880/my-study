# RecyclerView 源码解析(Recycler / RecycledViewPool)

## 概述
本篇直读 `androidx.recyclerview` 源码的两个核心:`Recycler`(内部类,负责「按四级缓存链取/造 ViewHolder」)与 `RecycledViewPool`(跨 RecyclerView 共享的终极回收站)。一切收敛到**一个方法** `Recycler.tryGetViewHolderForPositionByDeadline(position, dryRun, deadlineNs)`——它就是 [[RecyclerView 四级缓存]] §3 那条优先级链的真身。读完能答清:为什么命中 scrap / mCachedViews **不 rebind**、命中 Pool **必 rebind**;`stableId` 怎么改变命中方式;GapWorker 的 prefetch `deadline` 从哪里钩进来。

## 核心原理 / 关键点

> 下方源码均**简化改写自 AOSP / androidx**(保留结构与关键调用,非逐字),行号/字段以最新 master 为准。

### 1. Recycler 的字段:四级缓存的真身

| 缓存级 | 字段 | 生命周期 | 命中后 |
|---|---|---|---|
| ① Scrap | `mAttachedScrap` / `mChangedScrap`(`ArrayList<ViewHolder>`) | **单次 layout**,layout 结束 `clearScrap()` 清空 | 直接复用,不 rebind |
| ② mCachedViews | `mCachedViews`(`ArrayList`,容量 `mViewCacheMax`,默认 **2**) | 跨 layout 保留(最近滑出的几个) | 命中不 rebind |
| ③ Extension | `mViewCacheExtension` | 用户自定义 | 通常需 rebind |
| ④ Pool | `mRecyclerPool`(`RecycledViewPool`) | 长期、可跨 RV 共享 | **必 rebind**(数据是旧的) |

- `mChangedScrap` 仅 pre-layout 阶段用(配合 `notifyItemChanged` 的预测动画);`mAttachedScrap` 是 layout 期间临时剥离的屏幕内 holder。
- Scrap 与 mCachedViews 的区别:Scrap 只活一次 layout;mCachedViews 跨 layout 保留,默认 2,`setItemViewCacheSize(n)` 可调。

### 2. 入口:`getViewForPosition` → `tryGetViewHolderForPositionByDeadline`

```java
// 简化自 Recycler
public View getViewForPosition(int position) {
    return tryGetViewHolderForPositionByDeadline(position, false, FOREVER_NS).itemView;
}
```

三个参数决定行为:
- **`position`**:要取的可见位置。
- **`dryRun`**:「探测」用——true 时只查、不从 scrap 里真正取走(用于 prefetch 可行性判断、`findHolderForPosition`)。
- **`deadlineNs`**:绑定截止时刻(纳秒)。普通取值 `FOREVER_NS`(不限);**GapWorker 预取时传入当前帧的剩余预算**(见 §5)。

### 3. 查找链:六级优先级(源码骨架)

```java
// 简化自 Recycler.tryGetViewHolderForPositionByDeadline(非逐字)
ViewHolder tryGetViewHolderForPositionByDeadline(int position, boolean dryRun, long deadlineNs) {
    // ① pre-layout:从 mChangedScrap 按 position 找
    if (mState.isPreLayout()) {
        holder = getChangedScrapViewForPosition(position);
    }
    // ② 从 mAttachedScrap / mCachedViews 按 position 精确找
    if (holder == null) {
        holder = getScrapOrHiddenOrCachedHolderForPosition(position, dryRun);
    }
    final int type = mAdapter.getItemViewType(offsetPosition);

    // ③ 开了 stableId:从 scrap + cached 按 itemId 找(即使换了 position)
    if (holder == null && mAdapter.hasStableIds()) {
        holder = getScrapOrCachedViewForId(mAdapter.getItemId(offsetPosition), type, dryRun);
    }
    // ④ 自定义 ViewCacheExtension
    if (holder == null && mViewCacheExtension != null) {
        View view = mViewCacheExtension.getViewForPositionAndType(offsetPosition, type);
        ...
    }
    // ⑤ RecycledViewPool 按 viewType 找(不限 position)
    if (holder == null) {
        holder = getRecycledViewPool().getRecycledView(type);
    }
    // ⑥ 全都没有 → adapter 新建
    if (holder == null) {
        holder = mAdapter.createViewHolder(RecyclerView.this, type);
    }

    // —— 是否需要 rebind,见 §4 ——
    if (需要绑定) {
        tryBindViewHolderByDeadline(holder, offsetPosition, position, deadlineNs);
    }
    return holder;
}
```

记忆:①②③ 命中**免 rebind**;④⑤⑥ 命中**需 rebind**(其中⑥还要先 create)。

### 4. 是否 rebind 的判定

- **①②命中(position 精确)**:holder 仍认为「绑定的数据有效」→ 直接复用,**跳过** `onBindViewHolder`。
- **③stableId 命中**:同一个 `itemId` 的 holder 即便换了 position 也复用;type 一致即可,通常仍按需 rebind。
- **⑤Pool 命中 / ⑥新建**:数据无效 → 走 `tryBindViewHolderByDeadline` → `adapter.bindViewHolder` → `onBindViewHolder`。

**为什么 Pool 的 holder 一定 rebind?** 因为入 Pool 前会 `resetInternal()`:清掉 position、bound 等标志位(见 §8),Pool 只记得 `viewType`、不记得 position/数据,所以拿出来必须重绑。这正是 Pool 能跨 position、跨 RV 复用的前提。

### 5. `deadlineNs`:prefetch 的底层钩子

```java
// 简化自 Recycler.tryBindViewHolderByDeadline
private void tryBindViewHolderByDeadline(VH holder, int offset, int pos, long deadlineNs) {
    if (deadlineNs != FOREVER_NS && System.nanoTime() > deadlineNs) {
        return;   // 超过帧预算:本轮不绑定,留给真正 layout 那一帧
    }
    mAdapter.bindViewHolder(holder, offset);
    ...
}
```

- 普通 `getViewForPosition` 传 `FOREVER_NS`,永远绑定。
- **GapWorker 预取**传「当前帧剩余时间」:有富余就 create+bind 提前做完,没有就只 create 或干脆跳过——绝不抢当前帧的绘制。详见 [[RecyclerView 预取源码(GapWorker)]]。

### 6. RecycledViewPool 结构

```java
// 简化自 RecyclerView.RecycledViewPool(非逐字)
public static class RecycledViewPool {
    static class ScrapData {
        ArrayList<ViewHolder> mScrapHeap = new ArrayList<>();
        int mMaxScrap = DEFAULT_MAX_SCRAP;   // 默认 5
    }
    SparseArray<ScrapData> mScrap = new SparseArray<>();  // 按 viewType 分桶
    int mAttachCount = 0;                                   // 被几个 RV 共享

    public ViewHolder getRecycledView(int viewType) {
        ScrapData d = mScrap.get(viewType);
        if (d != null && !d.mScrapHeap.isEmpty())
            return d.mScrapHeap.remove(d.mScrapHeap.size() - 1);  // LIFO 弹最后一个
        return null;
    }
    public void putRecycledView(ViewHolder scrap) {
        ScrapData d = getScrapDataForType(scrap.getItemViewType());
        if (d.mScrapHeap.size() < d.mMaxScrap) d.mScrapHeap.add(scrap);  // 超容量则丢弃
    }
    public void setMaxRecycledViews(int viewType, int max) { getScrapDataForType(viewType).mMaxScrap = max; }
}
```

- 按 **viewType** 分桶(`SparseArray`),每桶默认上限 **5**(`setMaxRecycledViews` 按 type 调)。
- 取用 **LIFO**(弹末尾),命中率高的 type 自然留在桶里。
- `mAttachCount` 记录被几个 RV 共享;引用计数用于多 RV 场景下的生命周期管理。

### 7. 共享 Pool(多 Tab / ViewPager 提升复用)

```kotlin
val sharedPool = RecyclerView.RecycledViewPool()
tab1RecyclerView.setRecycledViewPool(sharedPool)
tab2RecyclerView.setRecycledViewPool(sharedPool)
```

- 多个列表共享同一 Pool:Tab1 滑出的 holder 进 Pool,Tab2 能直接取,省 create+inflate。
- **前提:各列表 viewType 语义全局一致**,否则 A 的布局被 B 按 type 复用 → 错乱/崩溃。

### 8. 回收入口:`recycleView` → 进 cache 还是进 Pool

- `recycleView(view)`:滑出屏幕的 holder 默认先进 **mCachedViews**(最近滑出的几个);当 mCachedViews 满(`> mViewCacheMax`)→ `recycleCachedViewAt` 把**最旧**的挪进 Pool。
- 进 Pool 前 `resetInternal()` 清标志 → 这就是 §4「Pool 的 holder 必 rebind」的根因。
- Scrap 是 layout 期间临时容器,layout 结束自动 `clearScrap()`,不进 Pool。

## 实践经验 / 踩坑

1. **`getItemViewType` 必须稳定** —— Pool 按 type 分桶;type 不稳定/越界,复用时拿错布局甚至崩。type 要稳定、唯一。
2. **`setHasStableIds(true)` 后 stableId 必须唯一且稳定** —— 否则 §3 ③ 的「按 id 找」命中错误 holder。开了就要给每个 item 返回稳定 id。
3. **共享 Pool 前确认 viewType 语义一致** —— 多列表共享 Pool,type 冲突会串布局。
4. **别手动持有 ViewHolder** —— 复用由 Recycler 统管,外部强引用 holder 会破坏缓存、导致重复 addView 崩溃。
5. **调大 mCachedViews 省的是 rebind,不是 create** —— `setItemViewCacheSize` 增大命中免 rebind 的范围,但吃内存;按列表 item 复杂度权衡(默认 2)。
