# 自动化测试

## 概述
高级岗要求能建立测试体系:**单元测试**(JUnit + Mockito / Robolectric,测纯逻辑)、**Instrumentation 测试**(跑在设备上,AndroidX Test)、**UI 测试**(Espresso 测 View 体系、Compose UI test 测 Compose)。分层:可测性从架构做起(依赖注入、Repository 抽象)。目标不是 100% 覆盖,而是关键业务逻辑 + 回归保护。配合 CI 在每次提交跑测试,把缺陷挡在合入前。

## 核心原理 / 关键点

### 1. 测试金字塔与分层策略
经典**测试金字塔**:底层多而快、顶层少而慢。
- **单元测试(多)**:纯逻辑、ViewModel / Repository / 工具类,本地 JVM 跑,毫秒级。
- **集成测试(中)**:组件协作(如 Room + DAO),Robolectric 或设备。
- **UI / 端到端测试(少)**:真实交互流,设备上跑,慢、易 flaky。
原则:**逻辑下沉到可单测的 pure function / ViewModel**,UI 层尽量薄,让多数测试在金字塔底层快速跑完。

### 2. 单元测试(JUnit + MockK/Mockito)
JUnit4(或 JUnit5)+ 断言库(Truth/assertj)。隔离外部依赖用 **MockK**(Kotlin 友好,支持 suspend / final 类)或 Mockito。测 ViewModel 时 mock Repository,验证状态流转:

```kotlin
@Test
fun `load emits Loading then Content`() = runTest {
    val repo = mockk<Repo>()
    every { repo.load() } returns flowOf("data")
    val vm = MyViewModel(repo)
    vm.state.test { /* 断言 Loading → Content */ }
}
```

单测应**快、独立、可重复**(不依赖网络 / 数据库 / 真实时间)。

### 3. Robolectric(本地 JVM 跑 Android 依赖)
真机 / 模拟器跑测试慢。**Robolectric** 在本地 JVM 提供模拟的 Android 框架(Context、Looper、SharedPreferences、部分 View),使依赖 Android API 的逻辑能当单测跑,无需设备。常配 `@RunWith(RobolectricTestRunner::class)`。局限:不渲染真实像素、依赖系统服务的部分行为是 stub。

### 4. Instrumentation 测试(AndroidX Test)
跑在真机 / 模拟器的测试 APK 里,能访问真实 Android 环境。用 `androidx.test`、`ApplicationProvider`、`@RunWith(AndroidJUnit4::class)`,代码放 `src/androidTest/`。比单测慢得多,留给真正需要设备环境的场景(真实数据库、跨进程、UI 交互)。

### 5. Espresso(View 体系 UI 测试)
测传统 View 交互:`onView(withId(R.id.x)).perform(click()).check(matches(isDisplayed()))`。核心三段:**find(找控件)→ perform(操作)→ check(断言)**。配合 **IdlingResource** 等待异步任务结束,避免在加载完成前断言导致 flaky。

### 6. Compose UI 测试
Compose 专用测试 API(同样在 `androidTest`,跑在设备):

```kotlin
@get:Rule val rule = createComposeRule()

@Test fun clickIncrements() {
    rule.setContent { Counter() }
    rule.onNodeWithText("0").assertExists()
    rule.onNodeWithTag("inc").performClick()
    rule.onNodeWithText("1").assertExists()
}
```

三段同 Espresso:**finder(`onNodeWithText` / `onNodeWithTag` / `onNodeWithContentDescription`)→ action(`performClick` / `performTextInput`)→ assertion(`assertExists` / `assertIsDisplayed` / `assertCountEquals`)**。Compose 测试基于 **semantics(语义树)**而非 View 树。优先用 `testTag` 而非文案匹配(文案随多语言 / 改版易碎)。

### 7. 可测性设计(架构层面)
测试能力是**架构**决定的:
- **依赖注入**:ViewModel 依赖 Repository 接口,测试时注入 mock / fake,而非真实网络。
- **Repository 抽象**:数据源换实现(fake 数据)即可测业务逻辑。
- **pure function / 状态缩减**:把逻辑抽成无副作用的纯函数 / Reducer(MVI 思路),单测覆盖全。
- **单一职责**:类越小、依赖越少越好测。
不可测的代码通常耦合过重——测试驱动反过来改进架构。

### 8. 在 CI 中跑测试与覆盖率
单测在 CI 每次提交跑(快);Instrumentation / UI 测试可夜间或发版前跑(慢)。覆盖率工具(JaCoCo / Kover)产出报告,**覆盖率是参考不是目标**——追求关键路径、边界、回归保护,而非数字。失败的测试必须阻断合入(branch protection 必过检查),否则 CI 形同虚设。

## 实践经验 / 踩坑

1. **测试跑在哪**:纯逻辑用 JVM / Robolectric(快、CI 友好);只有必须用真实设备环境的才放 androidTest。别把所有测试都丢模拟器。
2. **依赖真实网络 / 数据库 = flaky**:测试会因网络抖动随机失败。Mock 或用内存 / fake 数据源隔离。
3. **Compose 用文案匹配易碎**:文案改一个字测试就挂、多语言下更甚。用 `Modifier.testTag("submit")` + `onNodeWithTag` 定位。
4. **别用 Thread.sleep 等异步**:`sleep` 让测试又慢又 flaky。用 `composeTestRule.waitUntil { }` / `waitForIdle()`,Espresso 用 IdlingResource。
5. **测试间状态泄漏**:单例 / 静态状态会让测试相互影响。每个测试独立,`@Before` 重置或用依赖注入重建。
6. **追覆盖率而非质量**:100% 覆盖不等于测对了场景;关键是边界、异常路径、回归用例。
7. **suspend 函数测试**:`runTest`(kotlinx-coroutines-test)控制虚拟时间,不要真等 delay。
