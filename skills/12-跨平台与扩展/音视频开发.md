# 音视频开发

## 概述
音视频是 specialized 方向:**采集 → 编码 → 传输 → 解码 → 渲染** 全链路。核心概念:容器格式(MP4 / FLV)、编解码(H.264 / H.265 / AAC)、**MediaCodec**(硬件编解码 API)、**ExoPlayer / Media3**(Google 播放器)、直播(RTMP / HLS / WebRTC)、OpenGL / 滤镜渲染。直播 / 短视频 / IM 语音赛道需求大。门槛高(信号处理 + C/C++ + Android 多媒体 API),按目标赛道决定是否深入。

## 核心原理 / 关键点

### 1. 全链路:采集 → 编码 → 传输 → 解码 → 渲染
音视频核心是这条管线:**采集**(Camera / AudioRecord)→ **前处理**(滤镜 / 降噪 / 混音)→ **编码**(压缩)→ **传输 / 存储**(网络 / 文件)→ **解码**(还原)→ **渲染**(显示 / 播放)。每一环都有专门技术与权衡。

### 2. 容器与编解码
- **容器格式**:MP4 / FLV / MKV / TS——封装音视频流与元数据。
- **视频编码**:H.264(AVC,主流)、H.265(HEVC,更省带宽)、AV1(开源、新)。
- **音频编码**:AAC(主流)、Opus(低延迟,直播 / WebRTC 常用)。
编码决定画质 / 码率 / 延迟 / 兼容性的权衡。

### 3. MediaCodec 硬件编解码
Android 的**硬件编解码 API**:直接与设备 codec 交互,性能远超软解。输入 / 输出用 Surface + ByteBuffer,异步回调模式。**坑:芯片 / 系统编解码能力参差,需探测支持格式并准备软解 fallback**。

### 4. 播放器(Media3 / ExoPlayer)
Google **Media3(含 ExoPlayer)** 是主力播放器:抽象 DataSource / Extractor / Renderer,支持自适应流(DASH / HLS)、DRM、自定义渲染扩展。相比 MediaPlayer 更灵活、可定制、支持低延迟。

### 5. 直播推拉流(RTMP / HLS / WebRTC)
- **RTMP**:推流主流协议(直播推流端)。
- **HLS / DASH**:HTTP 自适应拉流(点播 / 直播播放,延迟较高)。
- **WebRTC**:超低延迟(连麦 / 会议),P2P + SFU 架构。
低延迟(秒开)是短视频 / 直播的核心挑战。

### 6. 渲染(OpenGL / SurfaceTexture / 滤镜)
视频 / 摄像头画面经 **SurfaceTexture** 接入 OpenGL ES 纹理,做滤镜 / 美颜 / 特效(GPU 着色器 shader)。短视频的特效栈基于此。

### 7. 低延迟与变速播放
- **低延迟**:用 LL-HLS / WebRTC / 减小缓冲,目标秒开。
- **变速变调**:播放速率调整(time-stretching,保持音调),用于倍速播放。

### 8. 门槛与赛道
音视频门槛高:**信号处理 + C/C++ + Android 多媒体 API + 协议**。赛道需求大:直播、短视频、IM 语音 / 视频、会议、点播。按目标赛道决定深入方向。

## 实践经验 / 踩坑

1. **编解码兼容性参差**:芯片 / 系统支持的 profile / 格式不同,生产需探测 + 软解 fallback(FFmpeg)。
2. **音视频同步**:以音频时钟或 PTS 为基准对齐,错位导致「音画不同步」。
3. **大缓冲 OOM**:流式处理,别一次性把整段视频读进内存;用 Surface / 分片。
4. **后台 / 息屏播放受限制**:系统省电策略会暂停后台音视频;前台服务 + 通知维持播放。
5. **权限与硬件占用**:相机 / 麦克风需权限且独占,切换前后台、来电时正确释放。
